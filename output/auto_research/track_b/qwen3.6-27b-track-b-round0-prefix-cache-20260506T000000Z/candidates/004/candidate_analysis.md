# Candidate 004 Analysis

- speed_thesis: Set request shaping to target concurrency 3 as a conservative batching point below the known concurrency-6 and concurrency-8 serial-vs-batched divergence failures. Candidate 001 showed concurrency 4 can exceed the 15 tok/s target, and serial decode was about 7 tok/s, so concurrency 3 should still have enough aggregate warm-cache decode parallelism to clear the target while reducing scheduler interleaving pressure.
- expected_affected_counter: Aggregate warm decode tok/s should land above the 15 tok/s target with concurrent_requests fixed at 3. Scheduled decode tokens per iteration, active sequences, and prefix-cache hit/query counters should be lower than the 4/6/8-request experiments but still reflect warm-cache reuse on repeated long prefixes.
- quality_risk: Quality risk is low because this changes only serving request shape; target weights, tokenizer, logits, and sampling behavior remain preserved. The remaining risk is batching-boundary sensitivity in the runtime scheduler, but concurrency 3 gives fewer simultaneous long-prefix continuations than the failed 6 and 8 runs.
- why_not_prior_failure: This does not revisit the exhausted CUTLASS schedule, tile, stage, or caller mutation path that produced sub-0.25% warm decode lifts. It changes the available serving surface by using smaller bounded batching over prefix-cache-hit requests, and it explicitly backs away from the higher-concurrency Track B failures that diverged at B-3.
