- speed_thesis: Raise the serving target concurrency to 8 so warm decode runs with larger effective batches and better amortizes the FP8 GEMM launch/memory overhead across concurrent requests. This is a request-shaping candidate, not a kernel candidate; the expected win is higher aggregate decode tok/s from batching pressure while preserving the shipped weights and sampling path.
- expected_affected_counter: Primary impact should appear in warm decode aggregate tok/s and request batching counters, especially average active sequences per decode step, scheduled tokens per decode iteration, and GPU utilization during decode. Per-request latency may move unfavorably at saturation, so ranking should use the controller's quality-bounded throughput gates rather than single-request latency alone.
- quality_risk: Low semantic risk because model weights, tokenizer behavior, logits, and sampling settings are unchanged. The main risk is operational rather than model quality: concurrent scheduling can alter request interleaving, tail latency, timeout exposure, or cache residency under memory pressure.
- why_not_prior_failure: Prior CUTLASS rounds mutated tile, schedule, stage, and caller details inside the same bandwidth-bound FP8 GEMM surface and repeatedly produced less than 0.25% lift. This candidate changes the serving surface by increasing concurrency and batch formation, so it tests whether the existing kernels become materially more efficient under higher decode occupancy instead of retrying an exhausted kernel-shape mutation.
