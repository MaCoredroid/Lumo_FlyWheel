- speed_thesis: Switch the repo-owned FP8 GEMM serving launch from CUTLASS to cuBLAS while keeping CUDA graph capture explicitly enabled through the supported string surface. The current bottleneck is warm decode FP8 GEMM work, and prior CUTLASS schedule/tile/stage mutations were exhausted without moving B-weight bytes; changing the serving kernel family is a materially different launch path that may reduce GEMM overhead without changing target weights or sampling.
- expected_affected_counter: Warm decode tokens/sec should rise if cuBLAS handles the dominant ffn_linear, deltanet_projection_linear, and gatedattn_projection_linear FP8 GEMMs more efficiently under vLLM serving. Secondary counters to watch are per-token GPU time, FP8 GEMM latency share, CUDA graph replay coverage, and any change in scheduler idle time.
- quality_risk: Low. This candidate does not enable speculative decoding, truncate lookups, alter prompts, change sampling, or modify model weights. The main risk is runtime compatibility or numerics differing slightly between FP8 GEMM backends, so B-1 distributional equivalence should remain the primary guard before any speed ranking.
- why_not_prior_failure: This is not another CUTLASS tile/schedule/stage mutation and not another ngram speculative decoding shape. Candidate 031 failed because `cuda_graph_capture` was submitted as a boolean, producing an unsupported surface before measurement; this candidate uses the supported quoted string value and keeps the surface focused on the unmeasured cuBLAS FP8 GEMM path.
