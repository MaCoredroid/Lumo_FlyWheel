- speed_thesis: Use the repo-owned vLLM launch selector to force the FlashInfer attention backend for warm decode. This changes an actual runtime kernel path without touching FP8 model weights, sampling, CUTLASS GEMM schedules, or request shaping. If the workload has nontrivial decode attention/KV-cache overhead around the FP8 MLP bottleneck, FlashInfer can reduce per-token attention launch and memory overhead while preserving the serving semantics.
- expected_affected_counter: Warm counted decode tok/s in the real vLLM workload window. Secondary counters likely to move are per-token decode latency and attention backend/kernel launch attribution; prefill and cold-start behavior are not the target.
- quality_risk: Low. This is a deterministic backend selection for attention execution rather than speculative token acceptance or prompt truncation. It should not alter target logits except for ordinary backend-level floating point differences, and it avoids the empty/truncated-output risk seen in aggressive ngram speculative decoding.
- why_not_prior_failure: This is not a CUTLASS tile/schedule/stage/caller mutation and does not revisit the exhausted FP8 GEMM negative-memory surface. It is also not another request_shaping-only or flat vllm_config capacity-only candidate, and it is distinct from candidates 031/032, which tested `fp8_gemm_kernel: cublas` with CUDA graph capture rather than changing the attention backend.
