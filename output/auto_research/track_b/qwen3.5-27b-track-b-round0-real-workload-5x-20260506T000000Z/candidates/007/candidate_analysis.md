- speed_thesis: Set request shaping to `target_concurrency: 4` so the four counted warm completions in the gate can run as concurrent decode streams instead of mostly serial work. This should improve aggregate decode throughput by giving vLLM a larger active decode batch while leaving the model weights, prompts, and sampling behavior unchanged.
- expected_affected_counter: Warm-window decode tokens per second should move first; secondary counters may show higher active sequence count, larger average decode microbatch size, and slightly higher GPU memory use during the counted completions.
- quality_risk: Low. This candidate changes serving concurrency only, so token probabilities and sampling settings should be preserved. The main risks are timing/order effects in request collection, higher tail latency, or an out-of-memory failure if the runtime has less headroom than expected.
- why_not_prior_failure: Prior failures were CUTLASS tile, schedule, stage, and caller mutations that left B-weight bytes and the FP8 GEMM bottleneck effectively unchanged. This candidate does not retry that exhausted kernel surface; it changes the available serving surface by increasing warm decode batching across the measured completions.
