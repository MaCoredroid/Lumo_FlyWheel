- speed_thesis: Use vLLM ngram speculative decoding with a four-token draft budget to preserve the only observed serving-side speed lever from candidate 020, while constraining lookup to a very narrow prompt window. The expected win is reduced accepted-token latency during warm repeated completions without changing model weights, sampling, kernels, or prompt content.
- expected_affected_counter: Warm decode tok/s in the real workload window should be the primary affected counter. Secondary counters likely to move are speculative draft acceptance rate, end-to-end completion latency, and any controller-side invalid/empty completion count from concurrent warm runs.
- quality_risk: Moderate. Candidate 020 showed that ngram speculation can create empty or truncated concurrent outputs under B-1, so this candidate raises `prompt_lookup_min` to 4 and caps `prompt_lookup_max` at 8 to require longer exact prompt matches before drafting. That should reduce accidental short-span matches while still allowing repeated-prefix tasks to benefit.
- why_not_prior_failure: This is not a CUTLASS tile, schedule, stage, or caller mutation, so it avoids the prior bandwidth-bound negative memory. It is also not a flat launch-capacity-only vLLM override. Compared with failed ngram candidate 013, it narrows the lookup window from 32 to 8 and raises the minimum match length. Compared with candidate 020, it keeps the stable narrow window but adds a stricter exact-match threshold to reduce the B-1 truncation risk.
