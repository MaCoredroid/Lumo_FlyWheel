- speed_thesis: Enable vLLM ngram speculative decoding so warm completions can accept short prompt-lookup continuations and reduce the number of full target-model decode steps per emitted token. A four-token proposal window is aggressive enough to test whether the real workload has reusable local ngrams across prompts or within generated text, while keeping verification overhead bounded for misses.
- expected_affected_counter: Warm decode tok/s should improve if the workload contains repeated phrases, boilerplate, code-like spans, list formatting, or answer scaffolds that ngram lookup can propose accurately. The most relevant counters are accepted speculative tokens per target decode step, target model forward calls per generated token, and end-to-end warm completion tok/s. FP8 GEMM kernel implementation and target model weights are not expected to change.
- quality_risk: Low. Ngram speculative decoding proposes draft tokens but still verifies them with the target model, so accepted outputs should preserve the target model distribution and sampling behavior. The main risk is performance-only: poor ngram hit rate or excessive proposal verification overhead could slow decode rather than speed it up, especially on diverse natural-language continuations.
- why_not_prior_failure: This is not a CUTLASS tile, schedule, stage, or caller mutation, and it does not repeat any request_shaping-only or vllm_config launch-capacity surface from candidates `001` through `012`. It also avoids the unsupported prefix-cache schema, invalid KV dtype attempts, and prior runtime override bundles; `spec_decode` is explicitly called out by the controller as supported and unmeasured in this round.
