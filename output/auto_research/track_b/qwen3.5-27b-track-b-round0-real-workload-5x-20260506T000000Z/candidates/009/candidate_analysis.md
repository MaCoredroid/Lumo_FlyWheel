- speed_thesis: Change the actual vLLM launch surface instead of outer request concurrency by allowing up to 16 resident sequences, enabling chunked prefill and native prefix caching, and storing the KV cache as supported `fp8_e5m2`. The main bet is reduced KV-cache bandwidth and higher scheduler headroom during the warm 5-completion workload, while keeping `max_num_batched_tokens` moderate enough to avoid over-reserving memory for long prefills.
- expected_affected_counter: Warm decode throughput should be the primary affected counter, with secondary changes in vLLM scheduler occupancy, resident sequence count, KV-cache memory footprint, and prefill/decode overlap. Quality counters may show small drift because KV-cache precision changes, so B-1 distributional checks are relevant before any ranking.
- quality_risk: Moderate. Target model weights and sampling behavior are preserved, but `kv_cache_dtype: fp8_e5m2` can perturb attention state versus automatic/full-precision KV cache. The risk is bounded to runtime cache representation and should be caught by the existing distributional and behavioral gates.
- why_not_prior_failure: This is not a CUTLASS tile, schedule, stage, or caller mutation, so it does not retread the exhausted Track A FP8 GEMM surface. It also avoids the prior invalid `fp8_e4m3` runtime failure by using only the controller-supported `fp8_e5m2` KV-cache dtype, and it is distinct from request-shaping-only candidates that already measured below target.
