- speed_thesis: Use vLLM fp8_e5m2 KV cache storage to reduce decode-time KV cache bandwidth and memory traffic per generated token. This targets the serving/runtime bytes-per-token surface rather than another FP8 GEMM tile or launch-capacity-only change, so any win should appear in warm decode throughput under the real workload window.
- expected_affected_counter: Warm decode tok/s should be the primary affected counter, with possible secondary effects in GPU memory pressure and scheduler headroom. Prefill and request-shaping counters are not expected to be the main source of improvement.
- quality_risk: Medium. Model weights and sampling behavior are preserved, but fp8 KV cache quantizes attention history and can shift long-context token probabilities. The B-1 distributional gate is the main risk check; this candidate avoids speculative decoding truncation/empty-output risk because it does not alter draft acceptance or output assembly.
- why_not_prior_failure: This is not a CUTLASS schedule/tile/stage/caller mutation, so it does not repeat the prior bandwidth-bounded GEMM negative memory. It also avoids exhausted request_shaping, capacity-only vllm_config variants, duplicate deltanet kernel selection, and the unstable ngram speculative-decode families that produced empty/truncated outputs or plateaued below the acceptance gate.
