- speed_thesis: Switch the vLLM runtime KV cache to FP8 E4M3 and cap active sequence capacity at the workload-sized window. This reduces KV-cache bytes moved and reserved per token while keeping enough scheduler capacity for the 5-completion warm workload, giving decode a serving-surface lever that request shaping alone did not expose.
- expected_affected_counter: `warm_decode_tps` should be the primary affected counter, with secondary movement in vLLM launch capacity / KV-cache allocation counters if the controller records them. The candidate is intended to clear the 9.000 tok/s acceptance gate by reducing runtime bytes per token rather than changing GEMM kernels.
- quality_risk: Medium. Model weights and sampling behavior are preserved, but FP8 KV cache changes attention-state precision and may alter long-context or numerically sensitive outputs. The B-1/B-2 quality gates should catch distributional drift before promotion.
- why_not_prior_failure: Prior failures were request-shaping-only repeats or CUTLASS tile/schedule/stage changes that left weight traffic effectively unchanged. This candidate uses a `vllm_config` runtime surface, not a CUTLASS mutation, and changes available serving memory/capacity through KV-cache dtype plus launch limits.
