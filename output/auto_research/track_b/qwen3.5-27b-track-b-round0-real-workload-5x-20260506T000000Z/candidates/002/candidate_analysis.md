- speed_thesis: Enable the controller's native prefix-cache serving surface so the four counted warm completions per task can reuse the cold completion's prompt prefix instead of rebuilding identical prefill/KV state. The expected gain is not from faster FP8 GEMMs during each generated token; it is from reducing per-completion prompt work and allocator/cache churn inside the real workload window while preserving the shipped model weights and sampler.
- expected_affected_counter: Warm-window aggregate decode tokens per second should improve most on tasks with repeated long prompts and five completions per task. Secondary counters to watch are prefix-cache hit rate, prefill tokens served from cache, time-to-first-token for counted warm completions, GPU KV cache utilization, and any scheduler stall or eviction counters that would show cache pressure offsetting the benefit.
- quality_risk: Low semantic risk because weights, tokenizer, prompts, sampling parameters, and generated-token decode kernels are unchanged. Main risk is operational rather than behavioral: prefix-cache hash collision, stale cache reuse across incompatible request attributes, or memory pressure causing evictions/stalls. The B-1 distributional gate should still run first because prefix reuse changes serving state across completions.
- why_not_prior_failure: This is not another CUTLASS tile, schedule, stage, or caller mutation, and it does not rely on the May 5 kernel surface that only moved warm decode by roughly 0.18-0.24%. It changes the serving surface exposed to the benchmark by exploiting the workload's repeated-prefix structure, so it can affect request-level work that prior FP8 GEMM experiments left untouched.
