- speed_thesis: Switch the repo-owned FP8 GEMM launch choice from the exhausted CUTLASS path to cuBLAS while keeping CUDA graph capture enabled for the warm decode window. The bottleneck is still ffn_linear, deltanet_projection_linear, and gatedattn_projection_linear byte/launch cost; this candidate changes the actual vLLM serving backend for those FP8 matmuls instead of mutating CUTLASS tiles, so it can expose a materially different kernel implementation and launch profile.
- expected_affected_counter: Warm decode tok/s should be the primary counter. Secondary counters to inspect are per-token FP8 GEMM wall time, CUDA launch count/overhead under graph capture, and any controller log evidence that `fp8_gemm_kernel=cublas` was selected for the target linear layers.
- quality_risk: Low. This preserves model weights, sampling behavior, concurrency shape, and output acceptance logic. Unlike ngram speculative decoding, it does not ask vLLM to draft or truncate tokens before verification; risk is limited to numerical drift from a different FP8 GEMM backend, which should be caught by the B-1 distributional gate.
- why_not_prior_failure: Prior CUTLASS memory says tile/schedule/stage/caller edits left B-weight bytes unchanged and yielded only sub-percent decode lifts, so this is not another CUTLASS mutation. Recent ngram candidates either plateaued below the new acceptance gate or failed B-1/measurement due to empty or truncated concurrent outputs; this candidate avoids speculative decoding entirely while still changing the available serving surface as requested by controller guidance.
