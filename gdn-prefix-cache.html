Bit-Exact Prefix Caching for a Recurrent Hybrid

Lossless GDN State Restore under Speculative Decoding in vLLM

Vol. III shipped a tree verifier with one standing caveat: prefix caching stayed off for this hybrid model, so every agentic turn re-paid prefill on an 11–14k-token conversation. This page turns the cache on and proves the state restore bit-exact. The contribution is a state-restore contract for recurrent hybrids: a cache hit must hand decode the exact committed GDN state, in the exact kernel realization, that a no-cache run would have produced.

TL;DR: attention KV is per-token addressable, so a prefix cache can just re-read it. Gated-DeltaNet state is one evolving vector, and under speculative decoding three different kernels write it. vLLM's align-mode cache restored a stale row in the wrong kernel realization, which poisoned the model into empty patches. The fix, EXACT_SEED, caches the chunked-prefill realization at 64-aligned positions, keyed by the prefix block hash, and restores it bit-exactly. Decode speed is untouched by construction; the entire payoff is prefill-side.

~4×

TTFT on every speculative arm in the matched tree×cache matrix: 11.78 → 2.60 s (chain5), 11.40 → 2.53 s (cat6root), 10.17 → 2.94 s (cat8), at 85–89% prefix hit on live SWE/Codex serving. Single task, one run per arm; decode throughput is flat by design, and TTFT plus hit rate are the un-confounded cache metrics.

Abstract

We present a lossless automatic-prefix-caching (APC) design for Qwen 3.6-27B-FP8, a hybrid model whose 64 layers include 48 Gated-DeltaNet (GDN) recurrent layers, served with MTP/tree speculative decoding inside a forked vLLM 0.19.2. Prefix caching is the default deployment lever for agentic workloads: the SWE/Codex loop resends an append-only 11–14k-token conversation every turn, and with the cache off, that prefill dominated task wall time. But for a recurrent hybrid the cache must store more than attention KV. It must checkpoint the GDN recurrent state, and under speculative decoding that state is written by three different kernels into two different layouts.

Turning on vLLM's align-mode cache as-is poisoned the model: acceptance collapsed, output garbled, and the coding agent gave up with empty patches. We root-caused this to a two-layer defect. First, a staleness bug: the align snapshot reads a block-aligned state row that the tree committer never wrote, so the cache stored a stale or branch-loser row. Second, a realization gap: even the correct row holds the recurrent-decode kernel's realization of the state, while a cache hit resumes through the chunked-prefill kernel; the two realizations differ by roughly 0.0078 per block boundary and the error compounds across boundaries. The fix chain — SNAP_FIX for staleness, EXACT_SEED for the realization gap — caches the chunked-prefill realization at 64-aligned checkpoint positions, keyed by the APC prefix block hash, and restores it verbatim. The L0 mechanism gate passed on June 29, 2026: the restored checkpoint is bit-exact, and across the live replay 47 of 48 GDN layers sit at floating-point-level drift, with the residual attributable to a measurement artifact that the no-cache control itself exceeds.

Lossless, as claimed here, is a ladder: L0 (mechanism) — the restored GDN state is bit-exact against a continuous no-cache reference; passed. L1–L2 (behavioral) — cache-ON preserves task resolution on every tree×cache arm; holds on the full 6/6 matrix, which is three matched pairs and not yet statistically powered. L3 (statistical) — an N-repeat Fisher-exact resolve-rate comparison; still open. "Lossless" in this page means L0 proven plus L1–L2 consistent, not a closed statistical claim.

Contribution

This page treats prefix caching for recurrent hybrids as a correctness problem first and a speed problem second. The contribution is the cache contract — committed state only, single kernel realization, aligned checkpoint positions, turn-stable identity — plus a working implementation of that contract inside vLLM's align mode, validated by a bit-exact state diff rather than by output vibes.

The tree verifier this cache serves is Vol. III's subject, with its own formal writeup, GDN Tree-Scan: Served Tree Verification for Recurrent-Hybrid Language Models. This page is self-contained: it states why recurrent state breaks prefix caching, shows the two-layer defect, gives the EXACT_SEED mechanism, reports the two-lens serving result, and records the failed routes.

The Cache Contract

Theorem style: this is the contract the implementation realizes. The proof obligation is structural; the bit-exact and behavioral claims are empirical gates.

Why a contract: every bug in this campaign was a violation of exactly one clause below, which is how we know the clause list is load-bearing.

A prefix cache for an attention-only model has an easy contract: cached KV rows are immutable per-token facts, so restoring them is a read. A recurrent hybrid adds a stateful clause. On a cache hit, decode resumes from a stored recurrent state, and that state must be indistinguishable from the state a no-cache run would have reached at the same position.

Restore contract, engineering form: assume checkpoints are taken only from committed tokens (never speculative candidates); every cached state row holds the chunked-prefill kernel's realization; checkpoint positions are multiples of the FLA chunk size (64) so the chunked scan is restartable bit-exactly; checkpoints are keyed by the APC prefix block hash, the only identity stable across turns; and the working state dtype is fp32 end-to-end. Then a cache hit followed by re-prefilling the tail through the same chunked kernel produces the same GDN state, bit-for-bit, as a continuous no-cache prefill of the full prefix.

The proof obligation is that these clauses compose: committed-only fixes what is written, single-realization and aligned-positions fix how it is written, stable-identity fixes where it lives, and the restore path re-runs the tail through the same kernel that produced the checkpoint. Under all clauses at once, restore is a restart of the same computation, which is why the gate can demand bit-exactness rather than a tolerance.

Prior Work

Fairness note: upstream issues are cited as evidence that this defect class is real and unsolved on our pinned stack, not as evidence that any project's current head is broken.

The anchor is vLLM issue #43559: accuracy drops ~20% when --enable-prefix-caching is combined with MTP speculative decoding on a Qwen3.6 GDN-hybrid (the reporter's model is 35B-A3B — same architecture family and feature combination as ours, not the same weights). Our root-cause read of that thread decomposes it into two carriers: a scheduler-level block-misalignment poisoning under short prompts plus concurrency, for which #45477 (keep chunk ends block-aligned) is the right fix; and the conv-window reconstruction non-invertibility in the mamba copy-specs, which we proved live on our tree committer (an 18.375 conv divergence at a multi-accept boundary while the recurrent state stayed byte-exact). At the time of writing, every fix PR in that cluster except #45473 (merged, DS-layout tail-copy; does not close the issue) remains open: #43650, #45477, #45614, #40738, #26807. Two adjacent vLLM behaviors shaped our gates: the silent zero-hit trap when align's single checkpoint boundary lands inside request-unique tokens (#45238), and the spec-reject SSM rollback gap (#39809).

The design we ported is SGLang's MambaRadixCache: recurrent state is not block-addressable, so SGLang stores a full state snapshot per radix-tree node in a decoupled checkpoint pool and copies it into a fresh active slot on a hit. The Hybrid Models Meet SGLang post is the production framing of the same point: attention masks and KV reuse alone do not serve hybrid models. SGLang issue #25587 documents conv-state restoration after partial acceptance as a live lossless failure mode; its own body scopes the divergence to Ascend NPU, so we cite it for the defect class, not as an NVIDIA claim. On the paper side, Execution-State-Capsules (arXiv:2606.20537) and Sparse-Prefix-Caching (arXiv:2605.05219) both cache recurrent checkpoints at aligned positions and restore through the same kernel — Sparse-Prefix-Caching's alignment remark is the formal basis for our 64-aligned clause — and SpecMamba is the closest speculative-decoding treatment of state backtracking for Mamba models. The AI21 mamba-debugging post is the methodology precedent: single-token state corruption in vLLM is found by state diffing, not output reading.

Why Recurrent State Breaks Prefix Caching

Plainly: attention remembers per token; GDN remembers in one running summary. You can re-read per-token memory from a cache. A running summary has to be checkpointed, and a checkpoint is only valid if it was taken at the right place, from the right tokens, by the right kernel.

For the 16 softmax-attention layers, APC is the classic win: KV rows for the shared prefix are content-hashed, found, and reused, and the model recomputes nothing. For the 48 GDN layers there is no per-token cache to re-read. The recurrent state at position t summarizes everything before it, and vLLM's align mode therefore keeps exactly one state checkpoint per request, at the last mamba_block_size boundary. A cache hit restores that single row and re-runs the remaining tail.

Speculative decoding is what turns this from delicate into broken. Under spec decode this model's GDN state has three writers: the chunked-prefill kernel writes boundary states during prefill; the recurrent-decode kernel (fused_sigmoid_gating_delta_rule_update) advances state token-by-token during decode; and the tree committer publishes per-node accepted states into a node bank whose layout no longer matches the linear block formula the align snapshot reads. The three writers produce two different memory layouts and two different numerical realizations of the same mathematical state. A cache that snapshots without knowing who wrote what stores the wrong row, the wrong numbers, or both.

The point is narrower: for attention layers a prefix cache is a lookup, while for GDN layers it is a checkpoint/restore system with three concurrent writers, and its correctness is a contract about who wrote the row, where, and with which kernel.

The Two-Layer Defect

Staleness: the cache saved a row nobody committed.

Realization gap: even the right row held the wrong kernel's numbers. Two kernels can compute the same math and still disagree by more than bf16 round-off.

Turning APC on with the tree verifier live poisoned the model within one evaluation arm: mean acceptance collapsed to 1.00, generation degenerated to 3.8 tok/s, a fraction of turns emitted repeated-token garble, and the coding agent gave up with zero-byte patches on three of four tasks. The root cause decomposed into two independent defects stacked on the same restore path.

Layer 1 — staleness. Align's snapshot formula reads state[block_ids[cur_block_idx + num_accepted_tokens - 1]]. That formula is correct for native MTP, which writes each speculative position's state to consecutive block-pool slots. The tree committer cannot keep that layout — a tree has branches — so it publishes per-node accepted states into a node bank. At any multi-accept boundary the formula reads a row the committer never wrote. Instrumented taps made this unambiguous: 480 of 480 postprocess snapshots read a stale row; in one traced event the snapshot took row 69 while the committer had written rows 35, 70, 37, 75, 39. SNAP_FIX repairs the write side by pointing the snapshot source at the committed accepted-leaf row (FAITHFUL 240/240 in the deterministic four-arm verify), and SNAP_FIX_ZEROACCEPT covers steps that accept nothing.

Layer 2 — the realization gap. With the row fixed, cache-ON tree runs at block 1024 still failed the proxy task 0/3. The reason, verified on the real deployed vLLM 0.19.2 source: prefill writes the cache with the chunked kernel, decode advances state with the recurrent kernel, and a cache hit can restore a recurrent-realization row and continue it through the chunked kernel. The two realizations differ by about 0.0078 per boundary — far above one bf16 ULP — and the error re-accumulates at every block boundary, roughly 30 of them across a 30k-token prefix at block 1024. Raising mamba_block_size to 8192 "fixed" the task by crossing ~3 boundaries instead of ~30, which is dilution, not repair: the same dial also forces up to a block's worth of mamba tail re-prefill per hit, taxing exactly the TTFT the cache exists to win. Block size was a lose-lose dial; the real fix had to make the cached row and the resuming kernel agree.

How We Arrived at EXACT_SEED

Reading the table: each row is a question the campaign had to answer, what was tried, what the instruments actually showed, and what survived into the final design.

The design was not derived; it was cornered. The cache went from NO-GO poisoning on June 19 to a bit-exact restore on June 29, and nearly every intermediate conclusion was overturned by a better instrument. The trail matters because the failure modes — scalar metrics that miss poisoning, gates that pass vacuously, headline drift numbers inflated by the measuring harness — are the reusable content.

State-diff

Exact-seed state diff

Replays a live agentic sequence (seq 49) with cache ON and diffs every GDN layer's restored state against a continuous no-cache reference. This is the L0 gate; it is also what exposed the layer-0 accumulator artifact (the no-cache control differs from itself by 38.44 across probe positions).

Stale-inject

Per-carrier stale injection

You cannot make one carrier fresh while keeping the rest cached — num_computed_tokens couples them — so isolation is inverted: force a full fresh re-prefill, then inject the stale value over exactly one carrier (conv / SSM / KV / position) and watch which one derails.

Shadow

Recompute shadow

On every cache-hit forward, dump both the restored state and a same-forward no-cache recompute. The carrier scorecard it produced — conv faithful 48/48, SSM faithful 48/48 post-fix, position faithful — is what narrowed the residual to the realization gap.

Defined to discriminate bug from fp machinery: ~0.0078 means kernel round-off, tens mean a wrong row. Three separate fixes "validated" while never firing: a flag not passed through docker, a flag dropped by the worker env bridge, and a code predicate that never matched. The engagement manifest asserts, per flag, worker-visible flag=1 AND an engagement counter > 0, or the verdict is untrusted.

EXACT_SEED: The Mechanism

One sentence: during prefill, at every 64-aligned block boundary, save each GDN layer's chunked-kernel state onto the prefix-hash cache block; on a hit, seed each layer from that checkpoint and finish the remainder through the same chunked kernel.

The mechanism is a checkpoint pipeline with one rule: nothing enters the cache except the chunked-prefill realization of committed tokens, at 64-aligned positions, under the prefix block hash. Six implementation facts make that rule hold in a real vLLM, and each one was a bug before it was a fact.

Algorithm 1 — EXACT_SEED (all behind FR13_APC_EXACT_SEED=1; default-off path byte-identical)
1  force block_size = 1024 = 16×64 (align's 816 = 16×51 is not a chunk multiple; not restartable bit-exactly)
2  prefill: chunked kernel runs; capture per-GDN-layer state at each 64-aligned boundary (capture in prefill, not decode — decode never crosses a boundary)
3  absolute position b0 := context_lens from the gdn builder (non-spec-sliced; fixes the stuck-at-0 base)
4  bind (req, pos) → block_hash bidirectionally (the insert runs one block ahead of the capture; either side completes the pair)
5  store {pos: {layer: state}} for all 48 GDN layers on BlockPool under the bare content hash; evict with the block; LRU-bounded, GPU-resident
6  hit: manager reconstructs the hash → worker seeds initial_state per layer → tail (<64 remainder + decoded suffix) re-runs through the same chunked kernel

Everything else is prefill-side plumbing, which is why the decode-cost table in the results is flat.

Two engineering notes survived deployment hardening. The checkpoint store is LRU-bounded on the BlockPool and kept GPU-resident — an early version leaked host RSS by never evicting, and a .cpu() copy per checkpoint was both the leak's amplifier and a needless sync on GB10's unified memory. And a decode-time committer that recomputed checkpoints during decode turned out to be vestigial: deleting its 608 lines removed 48 host-syncs per step and re-verified bit-identical, confirming the prefill-capture chain is the entire working mechanism.

The Arms: chain5, cat6root, cat8

Why three trees: the cache claim must hold on whatever the drafter is. The matrix crosses cache ON/OFF with the native spine and two tree shapes from Vol. III's verifier.

The tree×cache matrix uses three speculative arms, each run with the cache on and off. chain5 is the forked tree kernel run as a linear 5-node chain — native-MTP-5 topology on the tree code path, not the stock native kernel. cat6root is Vol. III's headline 6-node tree. cat8 adds siblings at depths 1–3. At B=1 the tree width up to 8 nodes is essentially free on forward time (~247–249 ms across all three), so the matrix isolates the cache axis rather than re-litigating tree shape. The stock native arm is separate: the deployment config called native MTP-5 + EXACT_SEED runs vLLM's own qwen3_5_mtp path with no forked kernel, under a different launcher from every matrix arm.

The Two-Lens Result

Why two lenses: nobody honest reports an agentic run as a single tok/s. Serving practice reports Output-Speed and TTFT separately; agentic practice reports wall-clock per task. The cache win lives in TTFT; Output-Speed being flat is the correct outcome, not a miss.

Read this result with its scope attached: one SWE-Verified proxy task (astropy-12907), temp 0.6, B=1, one run per arm, proven cache config on all six arms, thinking cap live on all six. Under that scope, the cache delivers TTFT ~4× on every speculative arm at 85–89% prefix hit, decode cost is unchanged, and every arm resolves the task with the cache on and off.

Headline

TTFT 11.78 → 2.60 s (chain5), 11.40 → 2.53 s (cat6root), 10.17 → 2.94 s (cat8): ~4× on every tree, at 85–89% prefix hit.

Decode view

Output-Speed is cache-neutral (±10% per tree, s_per_fwd flat ~247 ms) — by construction: a decode forward reads the same weights either way.

Agent wall-clock improved on chain5 (15.8 → 7.1 min) and cat6root (12.1 → 7.6 min) but reversed on cat8 — path-confounded by turn count and resolve variance, so it is a lens, not a claim.

Lossless Evidence and Gates

The metric trap: the residual drift number (30.11) looks alarming until you learn the no-cache control differs from itself by 38.44 under the same reducer. Layer 0 is a long-horizon accumulator; a flat absolute threshold cannot judge it.

The L0 gate replays a live agentic sequence (seq 49) with the cache on and diffs every GDN layer's state against a continuous no-cache reference. With EXACT_SEED at block 1024, 47 of 48 layers sit at floating-point-level drift (per-layer mean ≈ 0.0005 against an fp ceiling of ≈ 0.0078), and the checkpoint chain fires on 22 of 23 turns. The one apparent exception, layer 0, is a measurement artifact rather than a restore error: its forget gate is ≈1 (exp(A_log).min() = 0.0038), which makes it a long-horizon accumulator with state magnitude ~90 versus ~1 elsewhere, and the diff harness pairs snapshots from different sequence positions. The decisive control: two positions of the no-cache reference differ in layer 0 by 38.44 — more than the cache's 30.11. The restore introduces less layer-0 difference than the no-cache baseline's own position spread.

Measurement Discipline

The rule: a number is quotable only if its denominator survived red-team. This campaign retired more headline numbers than it kept.

The measurement stack is part of the contribution because the first version of nearly every number here was wrong. The two-lens convention (serving: Output-Speed and TTFT separately; agentic: wall-clock per task) replaced a string of self-inflicted artifacts — token-weighted throughput compared against per-request throughput, cross-boot walls compared as A/B, and engagement labels contaminated by warmup probes.

s_per_fwd = decode_forward_gpu_seconds / draft_events (drafts == forwards at B=1, verified to ≤0.1%)
Output-Speed = decode_tokens / decode_seconds (cache-neutral by construction)
TTFT = first-token latency per turn (the cache metric; pairs with prefix hit %)
wall_clock_per_task = agent minutes to resolution (deployment lens; path-confounded)

The vacuous-gate problem and the engagement manifest Three ways a fix flag can be ON and do nothing; the manifest that makes such verdicts untrusted.

Three separate fixes in this campaign "validated" while never executing. The flag was not passed through docker (-e missing); the flag was dropped by the worker environment bridge; or the code-path predicate never matched, so the flag was live and the fix never fired. The first two surface in a bridge marker; the third only surfaces in an engagement counter, which is exactly how two earlier fixes looked validated while inert.

Mode e

Flag never entered the container. EXACT_SEED's first launcher pass missed the -e passthrough.

Mode bridge

Flag dropped by the worker env sidecar's allowlist before reaching the process that needed it.

Mode predicate

Flag live, predicate never matches: a conv fix keyed on a function name that never appeared; a checkpoint store keyed by an identity that never recurred.

The manifest rule: for every active fix flag, assert worker-visible flag = 1 AND an engagement counter > 0, from the correct process domain, or mark the verdict UNTRUSTED. A zero counter must be made honest by preconditioning on the traffic that should fire it.

Failure Library: What Did Not Work

Not a graveyard: the ledger is the receipt trail for why the final design is committed-state, single-realization, hash-keyed — and why the measurement doctrine is as paranoid as it is.

The chase from poisoning to bit-exact took eleven days and burned through five fix designs, two carrier theories, and three headline numbers. The negative results are first-class content: they separate structural dead ends from bad evidence, and they are how the same mistakes stay dead.

Settled

Superseded

The 8192 block-size "fix", the VERBATIM publisher, and the early speed headlines were real observations whose framing did not survive better instruments.

Contaminated

The char-8 cache-conjunction verdict, the 30% decode-tax read, and a wrong-version source audit each had proof the measurement could not support its conclusion.

Conv-window fixes as the poison fix

settled

Why it looked plausible: the conv copy-spec reconstructs a non-invertible window by position-shifting, a provable wrong-state bug (18.375 divergence at a multi-accept boundary), and upstream discussion pointed the same way.

  • Evidence: two independent conv fixes left the garble count flat (6 → 8 → 12 of 3948 dumps) and the agent outcome unchanged.
  • Later check: the recompute-shadow scorecard measured the conv restore faithful 48/48 once the SSM fixes landed.

Conclusion: a real bug is not automatically the bug. The conv fixes stayed as hygiene; the carrier was the SSM temporal snapshot. Receipt.

Pointer-substitution SSM fix

settled

Why it looked plausible: if the snapshot reads the wrong row, redirect the copy-spec's source pointer to the committed leaf — minimal, surgical.

  • Evidence: diagnostics showed the substitution computed (will_sub=True) yet the agent still gave up empty; the reassigned spec never reached the batch copy's pointer buffer.
  • Extra trap: the stale-detector was index-based, so any value-level fix would read "stale" forever — an index-vs-value confusion that misdirected the whole option.

Conclusion: fix the value at the pointer the kernel will load, inside the function that owns the buffer — which is what SNAP_FIX does. Receipt.

VERBATIM publisher

superseded

Why it looked plausible: port SGLang's snapshot-verbatim discipline: at commit, copy the committed state into the exact row align will read.

  • Evidence: confirmed firing (48 diagnostic hits) but clobbered — the stock copy ran after it and overwrote the published row.
  • Later check: retired when SNAP_FIX won the same objective at the copy-meta layer; its publisher plumbing was deliberately kept and later reused by EXACT_SEED.

Conclusion: right discipline, wrong layer. Publishing before a stock overwrite is a race you lose; owning the copy source is not.

HIT_RECURRENT_SUFFIX (recurrent tail recompute)

settled

Why it looked plausible: on a hit, recompute the suffix token-by-token with the recurrent kernel — an exact-looking O(64) repair.

  • Evidence: baked, then un-baked within a day: solve rates did not move (0/2 with, 0/3 without), and the structural reason emerged — the recurrent kernel's realization is not the chunked kernel's, so the repair cannot be bit-exact even when correct.

Conclusion: the realization gap cannot be patched from the recurrent side; it defined EXACT_SEED's single-realization clause.

mamba_block_size = 8192 band-aid

superseded

Why it looked plausible: it was the first config that ever resolved the proxy task with spec and cache both live (1024 failed 0/3).

  • Evidence: it works by crossing ~3 boundaries instead of ~30 — diluting the realization error, not fixing it — and costs up to a block of mamba tail re-prefill per hit, taxing TTFT.
  • Later check: with EXACT_SEED, block 1024 is lossless; the "block-1024 bad zone" was a pre-fix artifact. The default reverted the same day the fix landed.

Conclusion: a dial that trades correctness against the metric you are optimizing is a symptom detector, not a fix. Receipt.

char-8 as a cache∧spec effect

contaminated

Why it looked plausible: a Fisher test on 1917 rollouts said the malformed-tool-call runaway co-occurred with engaged cache plus spec at p = 0.004.

  • Evidence: the "engaged" label was the per-boot cache maximum including the warmup probe; the smoking gun showed 82.4% "engaged" with 0.0% actual hit at the failing request. ~50 of 64 determinable breaks were cold-cache; char-8 fires cache-OFF too.
  • Later correction: root-caused as a truncated tool-call re-parse in the transcript renderer and fixed proxy-side (65/67 real poison strings repaired, 100% no-400).

Conclusion: the strongest-looking statistic of the campaign was a labeling bug. Engagement must be measured at the failing request, not the boot. Receipt.

The 30% cache decode tax

contaminated

Why it looked plausible: cache-ON decode read 16.8 tok/s against the historic 23.88 headline.

  • Evidence: basis mismatch — 23.88 was token-weighted, the comparison was per-request (same run: 18.51); on the matched task, cache-era decode beats historic (17.87 vs 17.61).

Conclusion: same basis on both sides of every comparison, or no comparison. Formally retracted in the results doc.

Per-request checkpoint keying

settled

Why it looked plausible: requests are the natural unit of serving state.

  • Evidence: no request identity survives prefill → decode → next turn (0/4 store∩drain overlap, 91k drain misses); a decode-side drain also never crosses a block boundary (~128 tokens/turn).

Conclusion: the only turn-stable identity is the prefix content hash the cache manager itself matches on — so that is the key.

Layer-0 drift as a restore bug

settled

Why it looked plausible: 30.11 max-abs on one layer screams corruption.

  • Evidence: layer 0 is a forget-gate≈1 accumulator with state magnitude ~90; the reducer pairs different sequence positions; the no-cache control differs from itself by 38.44 under the same pairing.

Conclusion: a flat absolute threshold cannot judge an accumulator; the artifact was in the diagnostic, and the verdict stood on the other 47 layers plus the control.

Decode-time checkpoint committer

settled

Why it looked plausible: checkpoints during decode would keep the cache fresh past the prefill boundary.

  • Evidence: it never fired in the working chain (publish counter zero), cost 48 host-syncs per step plus a leak and a per-token clone, and deleting its 608 lines re-verified bit-identical.

Conclusion: vestigial by measurement. The prefill-capture chain is the entire mechanism.

Root-causing on the wrong vLLM version

contaminated

Why it looked plausible: an early source audit cited exact files and line numbers — from v0.22.0, while the deployment runs 0.19.2rc1.dev134.

  • Evidence: the cited paths did not exist in the deployed build; the structural conclusions happened to survive re-verification on the real source, the citations did not.

Conclusion: version-pin the source you audit. Every mechanism claim in this page was re-grounded on the deployed 0.19.2 tree.

Blaming CUDA graphs for the garble

superseded

Why it looked plausible: full-graph capture plus cache-ON garbled while eager did not, so PIECEWISE capture shipped as a mitigation.

  • Evidence: the graph was amplifying the lossy cache, not causing it; with EXACT_SEED live, full-graph capture plus cache-ON runs coherent (46/55 cached turns, zero garble) and full graph mode was re-baked.

Conclusion: when two suspects co-occur, fix the state and retest the graph — the cheaper suspect was downstream.

Forked tree arms under a nudge-free harness

open

Why it matters here: on the qwen-code harness (no auto-continue net), native MTP-5 with the cache resolves 4/5 with zero char-8, while a forked-kernel tree arm stalls 8/8 with empty patches.

  • Evidence so far: the forked config degrades structured tool-call output; the cache is exonerated (ON in both arms). TREE_ATTN vs num_spec vs topology remain confounded.

Conclusion: the lossless deployment configuration today is native MTP-5 + EXACT_SEED; the forked tree arms wait on a de-confounding grid. Receipt.
