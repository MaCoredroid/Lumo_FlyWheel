## Pass 3 (~19:00Z) — self-inflicted download corruption, caught by fail-closed sha check

CONFESSION + DOCTRINE. Sequence: (1) observed 0 B/s over 80 s on the NVFP4 main shard while
the sibling FP8 stream progressed → diagnosed "hung connection"; (2) attempted
`pkill -f 'download unsloth'` in a compound command whose own text matched the pattern →
exit 144, the FR13 pkill-self-match fossil, re-committed verbatim; (3) killed the resumed hf
process and appended the "missing" 281 MB with `curl -C -` into the `.incomplete` file;
(4) size landed exact (22 568 192 096 B) but **sha256 MISMATCHED** the expected
`c473512c…` embedded in the incomplete-file name.

ROOT CAUSE: `hf_xet` is installed — hf 0.34 downloads via the xet protocol, which writes
verified chunks NON-CONTIGUOUSLY into the preallocated file. File size is NOT a contiguity
watermark, "0 B/s by stat()" is NOT proof of a dead transfer (xet verification phases look
identical), and appending with curl at the file's tail corrupts by construction.

RECOVERY: corrupt partial deleted; fresh xet download relaunched (verified-by-construction
chunks); smoke wrapper relaunched after it wrote a spurious DOWNLOAD_INCOMPLETE verdict when
the pkill gap made the downloader vanish mid-poll.

DOCTRINE (additions): (a) never mix transport tools mid-file — one downloader owns a file
from first byte to finalize; (b) file-size deltas are not a progress instrument under xet —
use the downloader's own log; (c) the pkill self-match rule now includes "the killing
command's own argv"; kill by PID, never by pattern, when the pattern appears in your own
command line; (d) the embedded-sha fail-closed check WORKED — it is the only reason the
corrupt shard did not reach the serve path. Always sha-verify any file a second tool touched.

### Pass 9 CORRECTION (~20:52Z) — cause found: qwen-code `web_fetch`'s hidden side query

My pass-9 "leading candidate" (a zero-token request at the bracket edge) is **WRONG** and is
retracted. The real cause, identified in parallel and now confirmed against this run's
evidence: qwen-code's `web_fetch` is not a retrieval tool — after fetching the URL it issues
a `runSideQuery` model call (purpose "web-fetch", main model, ordinary 32,768 max_tokens) to
extract the answer from the fetched bytes. That call never enters chat history, so it emits
no trace assistant record, but vLLM serves, bills and histograms it.

The tool census settles it, 1:1 on both tasks in the arm:

| task | `web_fetch` uses | engine reqs | trace turns | gap |
|---|---:|---:|---:|---:|
| astropy-12907 (control, reconciled) | **0** | 10 | 10 | 0 |
| astropy-13033 (failed) | **1** | 18 | 17 | **1** |

WHERE MY INFERENCE BROKE: I read trace `result.usage` matching the engine exactly
(595,503 / 9,417 on both axes) as proof the extra request carried no tokens. In fact
`result.usage` AGGREGATES every model call qwen-code makes, hidden side queries included —
so it matches the engine precisely while `num_turns` counts only the 17 chat turns. Equal
token totals were never evidence of a zero-token request; they were evidence that the hidden
call's tokens are already inside the aggregate. The count and the usage come from different
denominators in the same file.

DOCTRINE (o): a trace's aggregate usage and its per-turn records answer different questions.
Reconciling an aggregate against an engine counter cannot detect a request that the aggregate
already contains — only the RECORD count can. When two counters agree and a third disagrees,
the agreeing pair may share a denominator rather than corroborate each other.

This makes the finding a HARNESS-COMPLETENESS gap (an unmodelled qwen-code request class),
not an NVFP4 or Qwen3.8 defect at all — and the fail-closed validator was right to stop the
arm. The fix direction (model `web_fetch` as a third hidden-request class, counted
explicitly) is sound; it adds a request class rather than relaxing the identity, which is
exactly the distinction pass 9 asked for.
