Stateless Tree Speculative Decoding

A Branched Verifier That Caches and Commits Like Native

Vol. IV left the tree decode path as the open frontier: a branched speculative verifier that a prefix cache could poison, while the native linear path stayed clean. This page closes it, twice. A redesign makes the tree carry zero persistent state, so native's own cache owns correctness by construction. And the garble that had survived every numerical gate turned out not to be numerical at all — it was the attention KV of committed tokens, read from the wrong slot.

TL;DR: native decode gets caching for free because its accepted tokens form a linear chain; our token-tree verifier breaks that assumption in two independent ways. The fix for both is one principle: after a branched accept, re-linearize every committed state to the accepted path and burn the branch scratch, so the tree's data footprint is identical to native's. Applied to the recurrent state it is a stateless-tree lifecycle; applied to the attention KV it is the missing re-linearizer that had been emitting near-neighbor identifier garble the whole time. Net result: garble ~40% → 0%, resolve at native parity (8/16), and — on the deployment run — a slim decode-throughput edge: cat6 accepts more per event than native and forwards slightly cheaper, for 23.1 vs 22.4 committed tok/s (forward-limited, ~3% — not a reprise of Vol. III's +27%). Two honest asterisks stay open as future work: a branch-on-spine disturbance in which the wider tree accepts fewer tokens, and the per-step overhead a fully end-to-end wall clock would still charge the tree.

Abstract

Vol. III built a distribution-preserving token-tree verifier for Qwen 3.6-27B-FP8, a hybrid whose 64 layers include 48 Gated-DeltaNet recurrent layers. Vol. IV turned the prefix cache on and found it worked for the native decode path but not for the tree. This page resolves the tree path. The unifying observation is that native speculative decode is cheap to cache and commit for one structural reason: its accepted tokens form a linear chain, so every piece of committed state — the recurrent GDN state, the conv window, the attention KV — lands at a contiguous, linearly-addressed position that the framework already handles. A branched tree violates that assumption; its accepted path is a route through a per-node workspace, non-contiguous in the layout the next step reads.

We make the tree behave like native at the data layer along two axes. First, a stateless-tree redesign: the tree keeps no persistent state across steps. Each step initializes its scratch from native's running rows, drafts and verifies inside that scratch, copies the committed leaf back onto native's running rows, and burns the scratch to zero. Native's stock, request-keyed cache then owns snapshot, restore, and concurrency exactly as it does for native MTP — and the two cache carriers Vol. IV chased are eliminated by construction. Second, the garble hunt: a persistent near-neighbor identifier corruption (read_file → readFile, expected_row_count → expected_rowcount) that had defeated every numerical gate turned out to be a data-routing bug — the attention KV of committed tokens was being read from a sibling branch's slot. The fix re-linearizes it, mirroring the recurrent remap. Both are the same principle applied to different state, and together they take branched-tree garble from ~40% to 0% and SWE-Verified resolve to native parity.

The governing principle (the acceptance bar): the tree pipeline must be behaviorally indistinguishable from native MTP at the data layer — the same block-pool rows read and written, at the same times, holding no persistent state beyond what native holds. Only the speculative-decoding math may differ (the branched scan), and its workspace is burned every step. If the tree's persistent-data access pattern equals native's, a cache-behavior divergence is impossible, because native has none.

Contribution

Two fixes and one idea. The idea is that a branched verifier can be made cache-correct not by patching the cache to understand branches, but by making the tree stop asking the cache to — it re-linearizes to the accepted path and holds no state, so the stock cache never sees a branch. The recurrent half is a stateless-tree lifecycle; the attention half is a KV re-linearizer that also happened to be the root cause of a months-long garble.

This page is the sequel to Vol. III (the verifier) and Vol. IV (the cache), and is self-contained. It is also, deliberately, a research report rather than a results announcement: it records the week-long hunt attempt by attempt (The Hunt) and keeps a full failure museum of the roughly two dozen refuted hypotheses, because the reason the garble took so long to find — and the reason the recurrent fix took a graveyard of seam-patches before a redesign — is the most portable content here. Two framings from the earlier volumes are corrected in passing: the deployment committer is distribution-preserving (not a theorem-less greedy rule), and the elaborate exact-seed cache machinery that Vol. IV described was found dead and deleted, not shipped.

Five-Minute Reader Map

Read path: the principle, then the two fixes (recurrent, then attention), then the results and the debugging retrospective. The rest is appendix.

The shortest version: native speculative decode is a linear chain, so all its committed state is contiguous and the framework caches it for free. A branched tree is not a chain, so its committed state is scattered — and every place we read that state back at a linear position, we read a sibling branch's data instead. Re-linearize each committed state to the accepted path and hold nothing between steps, and the tree becomes native at the data layer. Doing this for the recurrent state is the stateless-tree redesign; the attention-KV twin was the garble bug.

The Contract: Two States, One Discipline

One idea, applied twice: the recurrent state and the attention KV are different tensors with the same problem — a branched accept scatters them, and a linear re-read grabs the wrong one. The discipline is identical for both.

A speculative step produces state that the next step must read back: the recurrent GDN state, the conv1d window, and the attention KV of the accepted tokens. Native writes those at contiguous positions and reads them from the same, so the stock cache is correct with no special handling. The tree writes them into a branched workspace and must move the committed ones onto native's linear positions before the next step — otherwise a positional read lands on a sibling. Everything on this page is one discipline applied to each cached state.

Why Native Caches for Free

Plainly: a chain has one path, so "the state after k accepted tokens" is always at slot k−1. A tree has many paths, so the accepted one is scattered, and "slot k−1" points at whichever branch happened to be sorted there.

vLLM's stock mamba cache rests on a single structural assumption: after a speculative commit, the accepted tokens form a linear chain. Two things follow, and native satisfies both, so it needs no extra code. First, linear accept means the row is right: the native verify kernel writes token t's running state into column t, so column-index equals chain-depth equals accept-order — an exact bijection. The committed state after num_accepted tokens is at the fixed row num_accepted−1, and the stock snapshot reads exactly there. Second, the producer and consumer share a numeric basis: native's cached boundary seed is produced by the same kernel family the cache-hit restore folds from, so restoring and recomputing reproduces the sequence — empirically native's cache miss and cache hit are byte-identical.

The tree fork breaks both, independently. The GDN kernel writes each tree node's state into a node-bank row keyed by node, not by accept order; the accepted tokens are a root-to-leaf path, so the k-th accepted token is node path[k], generally not k−1. Stock's linear formula therefore snapshots a sibling, cousin, or never-written row — measured wrong on every branched-accept sample (48 of 48, with divergences up to 23 at layer 0). That is a row-addressing failure: the stock save/restore does not apply to a branched accept, it is not merely imprecise. Separately, even the correct leaf row carries a value produced by the tree's own decode kernel, a different numerical realization than the chunked restore fold; that cross-basis delta compounds across 48 recurrent layers as a small within-floor residual. (A framing correction from Vol. IV belongs here: we once attributed this fragility to the committer, calling it a theorem-less greedy longest-prefix-match. At the deployment temperature of 0.6 the committer is in fact the canonical multi-draft rejection sampler and is distribution-preserving — the greedy rule is the temperature-0 degenerate case only — so it does carry a losslessness theorem. The residual is a cache-numerics story, not a committer-distribution one.)

Figure 1 is the whole paper in one picture. Native's accepted path is the slot order, so reading slot k returns token k for free. The tree's accepted path is a non-contiguous subset of the sorted node slots, so reading position 3 linearly returns whatever branch node was sorted into flat-slot-3 — a sibling. Every fix here is: move the committed nodes onto the linear slots before that read.

The Stateless Tree

The reframe: stop teaching the cache about branches. Make the tree stop keeping state, so the cache only ever sees native's linear rows — which it already handles perfectly.

The economics: the per-step state is a few megabytes; an HBM-to-HBM copy is microseconds against a ~98 ms decode forward. Copying is free. Avoiding it was a false economy that cost correctness.

Vol. IV's answer to the row-addressing problem was a stack of machinery that taught the cache to follow branches: a leaf map recording which node-bank row the committer wrote, a snapshot redirect pointing the cache at that row, a bias translation walking the accepted path, a stale-global cleaner, plus a second family of fixes (exact-seed, block-refold, a recompute suffix) for the numeric-basis half. It did not survive scrutiny. Instrumentation showed the intended bit-exact producer never fired — its checkpoint was captured about one percent of the time and used at restore zero times (redirect_used=0), so the deployed path had been riding a within-floor recurrent-leaf fallback the whole time — and the block-hash-keyed checkpoint store leaked to an out-of-memory kill after a few hours because its eviction reaper never ran. That family (roughly 1,170 lines across exact-seed, refold, and HRS) was code-level deprecated and then deleted. Before the redesign, the recurrent give-ups under concurrency were chased directly for a day and a half through a graveyard of seam-patches — clear-the-stale-globals, re-key the positional reader, fix the zeroed-source restore — every one of which landed in a dead code path or dissolved under a regime confound (the failure museum lists them). Every one of those patches existed only because the tree kept persistent state the cache then had to chase. The redesign deletes that premise instead.

The redesign deletes the premise. The tree pipeline maintains zero persistent state; each step is a pure function. It initializes its scratch from native's running rows, drafts and verifies inside that scratch, copies the committed leaf back onto native's running row, and burns the branch scratch to zero. After that, native's stock, request-keyed cache owns snapshot, restore, and cross-request concurrency for both recurrent states — exactly as it does for native MTP, because at the data layer there is now nothing to distinguish them. The two cache carriers Vol. IV chased are gone by construction: there is no tree-owned state left to go stale, be reused dirty, or bleed between concurrent agents.

Figure 2Every step is a pure function: seed from native's row, verify in scratch, commit the leaf, burn the rest

Figure 2 is the recurrent half of the discipline. The only state that persists past a step is native's own running row (column 0); everything the tree added — the branch scratch — is zeroed. Native's cache then does snapshot, restore, and concurrency with no knowledge that a tree was ever involved, which is the entire point.

The root the redesign closes. Column 0 of the state page is native's running row; columns 1 through num_spec are the tree's ephemeral drafts. But the tree deposited its committed leaf one column over and read it back positionally, so for two or more accepted tokens the running row was stale — it held the post-first-accept state while the true committed leaf sat in a branch column. That is exactly why tree-plus-no-cache had no give-ups (the leaf column survives within one continuous decode) yet the cache poisoned the tree under concurrency (the ephemeral column and the redirect are not request-owned across reallocation). Committing the leaf to column 0 and reading column 0 makes the running row the committed frontier again, for both the recurrent state and the conv window, in one write.

Two kernel facts make the write free and safe: the register holding the committed leaf at loop exit is byte-identical to what already gets stored to the branch column, so storing it to column 0 as well changes no values; and the initialization tile is loaded into registers before any store, so reading column 0 and then overwriting it in the same launch is safe. The three flags — commit-to-running-row, read-from-running-row, burn-the-rest — form one lifecycle, gated off by default to a byte-identical path, with a fail-loud guard that refuses any partial enable. That guard is not ceremony: the conv and SSM states share one physical page as strided views, and native's restore rewrites the whole page, so re-routing one without the other corrupts the page on the next restore.

The Hunt

Why this section exists: the two fixes are simple; finding them was not. This is the honest record — every attempt, the real signal it produced, and why it died — written for the next person debugging a branched verifier.

The shape of it: a day and a half chasing recurrent give-ups through a graveyard of cache patches, then four days chasing a garble that looked numerical and was not. The right answer was even proposed and talked out of, once, before an experiment named it.

Two defects ran in parallel and shared machinery. The first was the give-up: under concurrent caching the tree bailed with empty patches. The second was the garble: the tree committed plausible-but-wrong near-neighbor identifiers (read_file → readFile, expected_row_count → expected_rowcount, from_geodetic → from_geodentic) that raise a NameError and send the agent into a typo-fixing loop. Both trace to the same root — committed state read from the wrong place after a branched accept — but we did not know that, and the two hunts looked nothing alike from the inside.

Act I — the give-up, and a graveyard of cache patches

The decisive experiment was cheap once someone asked the right question: is the give-up single-agent or concurrent? Holding the agent fixed and turning only concurrency, the linear spine plus cache resolved four of four tasks with a single agent and zero of four with four agents sharing the cache. That split the world in two — a concurrent restore bug, not a per-request one — and it retired a confound: several earlier "single-agent" runs had actually been four agents sharing one cache, because "batch of one" and "one concurrent stream" had been used interchangeably. Pinning that convention reconciled months of contradictory numbers.

Then came the graveyard. The give-up seam looked, from a code read, like a set of never-cleared batch-position globals the tree committer wrote and never reset. Five successive localizations each produced a real-looking signal and each fell:

The graveyard ended in a more useful discovery than any of its patches: the bit-exact cache path everyone assumed was doing the work had never once executed. Its checkpoint was captured about one percent of the time and consumed at restore exactly zero times; the deployed cache had been riding a within-floor fallback all along, and its checkpoint store leaked to an out-of-memory kill after a few hours. That family of machinery was deleted, and the give-up was addressed not by a sixth patch but by the redesign above: make the tree hold no persistent state, and there is no stale global to chase. The recurrent give-up instrument went flat — sixteen of sixteen, cache-on byte-identical to cache-off — at a single agent. What remained was the garble.

Act II, Phase 1 — name the symptom, build a gate that can see it

The single most important call of the whole campaign was methodological: score code correctness, not per-token statistics. A within-floor token-distribution gate averages over the stream and is blind to one flipped identifier — but one flipped identifier is a NameError, and a NameError is the whole failure. The gate became an identifier-corruption rate over generated code. On it, native corrupted zero of forty-five samples; the tree corrupted at a 9.56% identifier rate, with thirty-two of forty-five samples flagged. A B=4 deployment matrix then set the honest stakes: the tree was a real decode speed win of about ten percent and a real quality loss — five give-ups to native's one on the same tasks, with native sometimes silently wrong-patching where the tree bailed. Worth fixing, not worth shipping as-is.

Act II, Phase 2 — the numerical hunt, and the wall that broke it

The near-neighbor symptom looked exactly like a numerical drift, so the search went numerical for days: batch-invariant GEMMs and reductions, a fixed-M projection pad, matching the tree's precision to native's, upcasting the conv state to fp32. A physics study even quantified the amplification — a systematic same-sign seed, re-injected coherently each layer, compounding layer over layer into a genuine ~492× error-vs-signal gain over the depth (honestly corrected down from a raw 14,800× ladder that double-counts the ordinary residual-stream growth native shares). Its one strategic conclusion held: the amplifier is the frozen trained network, identical for native and tree, so it cannot be lowered — native is clean only because native's seed is near zero, so attack the seed, not the amplifier.

Every seed lever failed, and one of them exposed the wall that had been quietly wrecking the measurements. A projection pad appeared to cut garble 68% (9.56% to 3.10%) — until the baseline was re-run on a fresh boot and came back at 2.96%. The tree's garble rate is set per boot by kernel autotuning, and swings between about three and ten percent for a fixed config; the pad's "fix" sat inside the baseline's own boot-to-boot swing. A cross-boot, single-lever A/B cannot distinguish a fix from luck. From that point the only trustworthy standard was elimination to zero, and one control did hold across the noise: native under real eight-way co-residency stayed at zero garble, and the tree garbled at one agent per server as much as at eight — so the defect lived in the tree path, not in batching.

The abandoned prophecy The exact right hypothesis, raised and reasoned away — one day early
Raised

A KV audit found it directly: the GDN recurrent state is re-linearized to the accepted path after a branched accept; the attention KV is not. It reconciled everything — why mamba was clean, why chains were clean, why the corruption showed up a step late.

Dismissed

A red-team argued it over-predicts: no remap should misplace most committed positions and garble nearly every token, but garble was only 8–11%. Verdict: capture to settle, don't build. The hypothesis was shelved.

The hidden flaw

The foreign K/V a node reads is a sibling draft's — a near-neighbor, not garbage — so it produces exactly a small, coherent, near-neighbor drift that the amplifier turns into an 8–11% flip. "Pervasive means garbage" was backwards; foreign-sibling KV is the near-neighbor symptom.

Act II, Phase 3 — eliminate every compute and state suspect

With the numerical levers exhausted, the day turned to systematic elimination, anchored by a decisive control: teacher-forcing the exact same prefix in isolation produced the correct identifier at near-certainty, while the same position in-trajectory produced the near-neighbor at near-impossibility. The only thing that differed between the two forwards was the accumulated state they consumed — so the corruption was carried state, not the verify compute and not the model. One by one, each state suspect was overwritten with a native-exact version, each with a fired engagement needle: the GDN scan output, the recurrent-state write, the conv window, the attention mask. Each engaged; each left the garble intact. A per-layer state diff even pointed a reproducible finger at the first recurrent layer — a genuine signal that later proved a comparison artifact. By the end of the day every forward operation validated correct and the argmax was still grossly wrong: a paradox that could only mean the error was in what the forward read, not in any op. A second insight landed the same day and would make the next one decisive: the greedy and temperature-0.6 accept rules read the same drifted logits and only manifest them differently, so the fast deterministic gate is a lower-sensitivity detector of the same defect — and the reliable temperature-0.6 gate (fifteen of fifteen when present, zero when fixed) is the instrument that beats the boot-variance wall.

Act II, Phase 4 — the kitchen sink, and the fix

The turning point was to stop bisecting. Testing one numerical fix at a time only ever proves "not this op," never "not compute." So every suspected compute and state fix was armed at once, every needle confirming it fired, and the reliable gate was run: fifteen of fifteen, unchanged. That single fifteen-minute experiment falsified the entire compute-and-state class and left exactly one thing none of the armed fixes touched — the attention KV content the forward reads. It re-found, now by data instead of by argument, the hypothesis that had been shelved a day earlier. Four independent lines converged: the kitchen-sink verdict, a grep confirming the recurrent state has a re-linearizer and the attention KV has none, topological counts showing accepts read foreign KV at every depth past the first, and the slot arithmetic below. The fix mirrors the recurrent one and took an afternoon; most of that afternoon went to three plumbing bugs that each made the remap fire but copy nothing, each caught by red-teaming the engagement needle rather than trusting the flag. Then fifteen of fifteen became zero of fifteen, eager and graph and cache-cold alike, and the agentic rate fell from about forty percent to zero.

The Root Cause: Committed-Token KV, Read From the Wrong Slot

The tell we had all along: a foreign K/V read grabs a sibling draft's K/V — and a sibling draft is a near-neighbor. So the drift was always going to look small and near-neighbor. The symptom was never evidence against routing; it was the fingerprint of it.

The recurrent state had a re-linearizer — the stateless-tree commit moves the accepted node's state onto the running row. The attention KV had none. Its cache is vLLM's sequential paged store, whose native slot mechanism is correct for chains, and nobody had revisited it for branches. Each tree node writes its K/V to a flat, sorted verify slot. For cat8 the accepted spine occupies flat slots 1, 2, 4, 6, 8, with the sibling branches interleaved at 3, 5, 7, 9. After the accept, the sequence length advances and the next forward reads the committed tokens at linear positions 1, 2, 3, 4, 5 — so position 3 reads flat-slot-3, which is a sibling branch node, not the accepted spine. The forward attends over a neighbor's key and value, its logits drift toward that neighbor, and it commits a near-neighbor identifier. Measured topologically, accepts read foreign KV at every depth past the first: depth 1 was clean, depths 2 through 5 read the sibling.

Figure 3cat8: the accepted spine sits at flat slots 1,2,4,6,8; a linear re-read of position 3 grabs the branch at slot 3

Figure 3 is the bug and its fix. The branch K/V was computed correctly; it was read from the wrong slot on the next step. The remap copies each committed node's K/V from its scattered flat slot to the linear slot the next forward will read — the exact twin of the recurrent commit in Figure 2. It runs in the sampler, outside the captured graph region, so it is graph-safe, and it moves under a megabyte per step against a ~99 ms forward, so its cost is noise.

The fix is launch_attn_kv_linear_remap: after a branched commit, copy each committed node's key and value from its flat verify slot to its linear committed slot, for every full-attention layer, inside the sampler. It is wiring and data movement, not a kernel change; it keeps all branches; and the capture that feeds it is exclusion-based — it grabs every attention group whose builder is not the recurrent kernel — so it is robust to any attention variant rather than a narrow whitelist. The measured cost is a 0.7% change in per-forward time, inside cross-boot noise.

Results

The bar: the tree should garble no more than native and resolve no worse. Both hold. The one number that is not a quality claim — the tree-shape accept difference — is called out as speed in the next section.

Two senses of “right tokens”: the tree resolves the same tasks as native and garbles no more than native on the token gate (0/15). Separately, the committer is verified token-lossless — it accepts at the target distribution, checked over 200k trials — so its accepts are not what garble; the corruption was upstream, in the state the verify read.

The remap and the stateless lifecycle ship together in the locked launcher. Measured across the token-level gate, the agentic gate, and the SWE-Verified eval, branched-tree garble is eliminated and resolve reaches native parity.

Failure Museum

Not a graveyard: every entry produced a real signal, and each refutation is why the final design and gate look the way they do. The through-line is that almost every dead end was a confound — of regime, of sample size, or of an overloaded label — not a wrong idea.

Well over a dozen hypotheses were refuted across the campaign. They cluster into four families: attempts to patch the concurrent give-up at the cache seam; attempts to make the boundary numerics bit-exact; numerical levers against the garble; and framings from earlier volumes that this work corrects (including a suspected accept-logic bug). The ledger below collects the most instructive, with what made each look right and what killed it.

Family A — concurrent give-up, patched at the cache seam.

Clear the stale globals on request-free

contaminated

Why it looked right: a code read localized the give-up to never-cleared batch-position committer globals; clearing them on request-free recovered the spine 0/4 → 2/4, give-ups 4 → 1.

  • What killed it: that run mis-served the tree (wrong tree size), the flag had no engagement needle, and the 2/4 was one noisy four-task point — a rerun gave 0/4. The claimed byte-identity was an easy-task diff, not a bug.

Lesson: never claim a fix on four agentic tasks without an engagement instrument; a silent flag that cannot prove it fired is untestable.

Re-key the positional reader by request

settled

Why it looked right: a clean code root — a spec-row reader indexed by full-batch position, a genuine cross-request mis-index at concurrency ≥ 2.

  • What killed it: the mis-index counter read zero over a full concurrent run — the path was dead; the real carrier was in the replay route.

Lesson: a clean code-read root cause still has to fire at runtime; instrument the counter before building the fix.

Zeroed-source restore under concurrency

contaminated

Why it looked right: the restore read a zeroed source block 68× more often at four agents than one (476 vs 7) — a clean concurrency-specific signal.

  • What killed it: a sample-size confound — the comparison mixed a partial one-agent run against a full four-agent run. Matched at equal resolve it was 616 vs 238, the other direction, and the spine resolves despite 616 zeroed reads. Worse, the tap that produced all of it is eager-only, and eager itself degrades the spine.

Lesson: a large ratio is meaningless across arms of different completion rates; and an instrument that changes the system under test cannot localize the bug it perturbs.

Copy the committed leaf into the block pool

settled

Why it looked right: depositing the committed state directly into the pool seemed a cleaner restore than the snapshot redirect.

  • What killed it: proven byte-identical to the existing redirect — the same request-keyed value into the same request-keyed row. It reproduces the give-up, it cannot remove it.

Lesson: prove value-equivalence before building an alternative; two mechanisms that write the same bytes cannot differ in outcome. The tree already caches like native on restore — the give-up was not a restore-keying bug, which is why only the stateless redesign closed it.

Family B — the boundary-numerics cache (exact-seed).

The bit-exact exact-seed restore

superseded

Why it looked right: keep the cache a pure chunked lineage so restore equals a cold prefill token-for-token, and a small block size would be lossless.

  • What killed it: instrumentation showed the checkpoint captured about one percent of the time and used at restore zero times (redirect_used=0) — the deployed path had ridden a within-floor recurrent-leaf fallback all along. Raising the block size to 8192 merely masked it, at a two-times speed cost and a single unconfirmed rescue.

Lesson: a bit-exact path that never fires is worse than none — it hides the fallback. Instrument used, not just engaged.

The whole exact-seed / refold / HRS family

settled

Why it looked right: it was the intended producer of a bit-exact cache; Vol. IV described it as the mechanism.

  • What killed it: beyond never firing, its block-hash-keyed checkpoint store leaked — the eviction reaper never ran — to an out-of-memory kill after a few hours that took down a resolve run. About 1,170 lines were deprecated and deleted.

Lesson: an unbounded keyed store needs an eviction path from day one; when a producer is proven non-functional, delete it rather than carry it.

Family C — the garble looked numerical.

The −68% projection-pad "fix"

contaminated

Why it looked right: a fixed-M pad on the verify projection cut garble 9.56% → 3.10%, a clean 68% reduction with acceptance intact.

  • What killed it: re-running the baseline on a fresh boot gave 2.96% — the "fix" sat inside the baseline's own boot-to-boot swing. Per-boot autotuning sets the garble rate between about three and ten percent for a fixed config.

Lesson: cross-boot A/B is worthless for a boot-variable rate. From here, eliminate-to-zero was the only trustworthy standard — and the variance itself was a lead toward kernel selection.

The batch-invariant "breakthrough"

contaminated

Why it looked right: the deterministic greedy garble vanished with full batch-invariance on, and a bisect said the carrier was a GEMM or reduction, not attention.

  • What killed it: the greedy gate has false negatives — the reliable temperature-0.6 gate showed 15/15 still garbled with batch-invariance on. A perturbation had nudged one greedy near-tie back to correct without touching the drift.

Lesson: a deterministic repro that "clears" can be a gate false negative, not a fix; validate on the sampled gate that sees the whole drift.

The 9e-4 amplification thesis (whole-GDN-native)

settled

Why it looked right: a roughly 9e-4 GDN-scan realization drift, amplified across the layers past the sampling margin, would explain a near-neighbor flip.

  • What killed it: making the entire GDN per-node path native-exact left the deterministic garble intact, and the output-probability probe measured the garbled token sitting 6.6 to 15.7 nats below the clean argmax — a gross structural error, where 9e-4 amplified ~492× is about 0.4 nats, fifteen to forty times too small to flip it.

Lesson: measure the effect size at the output in nats before chasing a ULP-scale seed; a fifteen-nat error cannot come from a sub-nat drift.

Precision-matching and fp32 seed fixes

settled

Why it looked right: matching native's bf16 round-trip on the replay path, or upcasting the conv state to fp32, would shrink a realization-bias seed.

  • What killed it: precision-matching made garble slightly worse (12.9% vs 9.6%) — by default the tree is more precise than native, not less — and a premise-check showed the garble is not first-layer-seed-dominated: fp32-conv buys about two times against the roughly six times needed, and the dominant amplifier is the full-attention stack, not the seed.

Lesson: premise-check the seed-dominance assumption against the amplification budget before building the fix; aligning to native's arithmetic is opt-in to reproduce native, not to beat it.

Family D — framings this work corrects.

The theorem-less greedy committer

corrected

The claim (from Vol. IV): the tree commits by greedy longest-prefix-match rather than exact rejection sampling, so it carries no losslessness theorem, and that is what makes tree-plus-cache fragile.

  • The correction: greedy longest-prefix-match is the temperature-0 degenerate case only. At the deployment temperature of 0.6 the committer is the canonical multi-draft rejection sampler, distribution-preserving under the verified accept rule, and does carry the theorem (its token-losslessness was checked over 200k trials). The residual tree-plus-cache sensitivity is cache-numeric drift, not a committer-distribution break.

Lesson: name the deployment temperature when reasoning about a spec-decode committer; a temp-0 property is not a temp-0.6 one.

The accept-logic over-commit

corrected

The claim: a "deciding result" — the verify scored the garble token at the true near-impossibility (1.99e-6) yet the multi-draft accept logic over-committed it, so the bug is the committer, and the drift chase is over.

  • What corrected it: an alignment artifact — the committer commits at exactly the post-constraint probability, and the near-neighbor had been top-p-masked to zero at the compared index. The garble is forward drift after all.

Lesson: a gather-then-commit index misalignment can manufacture a fake accept-logic bug; verify the committer reads the post-constraint probability at the right index.

KV-not-re-linearized (raised, then abandoned)

corrected

The right answer, one day early: a KV audit found the recurrent state re-linearized to the accepted path and the attention KV not, reconciling every observation.

  • Why it was dropped: an over-prediction argument — no remap should garble nearly every token, but garble was only 8–11%, so surely the framework re-points the slots. Verdict: capture to settle, don't build.

Lesson: the over-prediction had a hidden flaw — foreign KV from a sibling draft is a near-neighbor, so it produces the exact small, coherent drift observed, not garbage. The kitchen sink re-found it a day later. When an argument dismisses a hypothesis, check whether the symptom is actually consistent with it.

Reflection: Why It Took So Long

Worth stating plainly: once localized, the fix was obvious and cheap — mirror the recurrent remap, a small copy, no kernel work. Nearly all the cost was in localization, and localization was slow because the hunt fought the symptom's disguise instead of its structure.

The bug was a data-routing gap masquerading as a numerical one, and three things kept the disguise on. The recurrent state already had a working remap, so state re-linearization felt solved — and the symmetric missing piece was invisible precisely because its analog was done. The linear chain was clean, so garble read as "branches are just harder" rather than the structural fact that chains are contiguous and branches are not. And the near-neighbor symptom pulled every instinct back toward compute, when a foreign-KV read — a read of a sibling draft — produces exactly a small, near-neighbor drift. The clue was there the whole time; we kept reading it as noise.

Threats to Validity

Honest scope: the quality goal is met — committed tokens are native's, resolve matches native. The open item is speed, and the clean speed comparison has not yet run.

Speed, not quality

The residual is a speed effect

At greedy, adding branches slightly lowers the spine's acceptance (a roughly 0.09-token gap, cat6 over cat8), driven by how the forked attention kernel's key width perturbs its reduction. It is speed-only: the tree still commits the right tokens (the committer is verified token-lossless), so nothing is lost, and at deployment temperature the branches recover the gap. An earlier, 3.4×-larger version of it was a garble-composition artifact, not a real effect.

Superset unproven

The speed story is not the hoped one

The tree's justification is that its branches accept more tokens per forward than native's chain, and monotonically in node count. The clean three-arm run only half-supports that: cat6 does out-accept and out-throughput native on the forward-limited decode basis (3.594 vs 3.466; 23.1 vs 22.4 tok/s), but acceptance is non-monotonic — cat8, a superset of cat6, accepts fewer, not more. So the hoped “a wider tree is strictly faster” does not hold, and the end-to-end wall picture — which adds the per-step overhead the forward-limited number omits — was not cleanly isolated at B4. The residual — why cat8's extra branches lower its own spine acceptance — is now mechanistically localized but not yet fixed in production (see Future work).

Future Development: The Branch-on-Spine Disturbance

Status: not merged. This work lives on a branch, behind a default-off flag; the ship configuration is byte-identical without it. It is recorded here as the active frontier, in the same attempt-by-attempt spirit as the rest of the report.

The question: why does adding branches to the tree lower the acceptance rate of its own spine? cat6 already edges native on forward-limited decode throughput; answering this is what would make the wider trees deliver the superset advantage — strictly more accepts per forward — and carry that lead through per-step overhead to end-to-end wall.

The results above leave one honest disappointment: acceptance falls as node count rises — cat6 accepts more than cat8 (3.594 versus 3.336 on that run) — so the wider tree, which should be strictly faster, regresses instead. cat6 edges native on the forward-limited decode basis, but until the wider trees stop regressing and the per-step overhead is closed, the tree has not decisively out-run native end-to-end. The regression is counter-intuitive, because a wider tree is a superset of a narrower one; its extra branches should only ever add accepted tokens, never subtract. The subtraction is a numerical artifact, and the same six-day discipline that found the garble has now localized it, though not yet shipped a fix. Measured cleanly — at greedy, where drafts are deterministic and the superset test is exact — the true magnitude is a single bit of floating-point, about 0.09 tokens per event (the raw temp-0.6 gap above is larger and noisier; an even bigger earlier version was a garble artifact). It is a within-floor speed residual with the committed tokens still correct — but it is the difference between the tree earning its complexity and not.

Where the disturbance lives

Adding a co-resident branch changes the acceptance of the spine even though the branch's keys are correctly masked out of the spine's attention. We localized it the same way as the garble — overwrite each suspect with a native-exact version in an observe-only harness — and it resolved cleanly. The fused convolution is bit-invariant to branch count (elementwise math, no cross-row reduction). The in-projection is excluded by construction (the two tree widths share the same GEMM path). The carrier is the forked attention kernel: on the deepest spine node it drifts by exactly one bf16 unit-in-the-last-place at magnitude eight, in all sixteen full-attention layers, purely as a function of how many branches sit beside it.

The obvious fix — pad the query to a fixed width so the tile occupancy is branch-independent — was validated in the harness and genuinely refuted: query padding has zero effect. The carrier is not the query tile; it is the key width. cat8 presents nine suffix keys, cat6 six, and even though the extra branch keys are masked to negative infinity in the spine's score row, their presence changes the block iteration of the online-softmax reduction. A read of the vendored kernel source closed the mechanism: the reduction order is keyed by physical column. Interleaving branches places the surviving spine keys in different score-tile columns (spine-only occupies columns 0-4; the cat8 spine occupies 0, 1, 2, 4, 6), which produces a different lane-partial layout and therefore a different butterfly-reduction association tree — and floating-point addition is not associative, so the sum lands one unit-in-the-last-place away. It is not a masking bug: the masked keys contribute exactly zero. It is pure reassociation from column placement.

The fix, and why it is not yet in production

The mechanism dictates the fix: make the surviving spine keys occupy identical columns regardless of branch count. A call-site-local contiguous-spine reorder — permute the suffix keys, values, and bias so the spine comes first in depth order and the branches follow — does exactly that, and in the observe-only harness it is provably correct: every spine depth becomes bit-identical to the spine-only computation (zero difference), while an interleaved-identity control stays at the one-ULP drift, confirming that contiguity itself is the property. The fix is lossless by construction (an exact relabeling; the masked branch columns stay neutral) and carries no memory-bandwidth tax.

Landing it in the live server is the open problem, and three routes have each hit a wall — every wall caught by a gate before it could ship:

There is also a subtlety worth flagging for whoever picks this up: the reorder fixes the spine bit-exactly but only partly fixes the branches. A branch's ancestors are a subset of the spine, so the deepest, rarest branch still shifts about one ULP as its own column moves with the co-resident branches beside it. The effect is concentrated in the deepest branch, so its net speed cost is small, but a fully canonical layout — fixed slots for branches as well as the spine — is what a complete fix would need. The numerical fix is proven and the mechanism understood; the live delivery, and the branch half of it, are the work that remains.
