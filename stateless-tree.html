Stateless Tree Speculative Decoding

A Branched Verifier That Caches and Commits Like Native

Vol. IV left the tree decode path as the open frontier: a branched speculative verifier that a prefix cache could poison, while the native linear path stayed clean. This page closes it, twice. A redesign makes the tree carry zero persistent state, so native's own cache owns correctness by construction. And the garble that had survived every numerical gate turned out not to be numerical at all — it was the attention KV of committed tokens, read from the wrong slot.

TL;DR: native decode gets caching for free because its accepted tokens form a linear chain; our token-tree verifier breaks that assumption in two independent ways. The fix for both is one principle: after a branched accept, re-linearize every committed state to the accepted path and burn the branch scratch, so the tree's data footprint is identical to native's. Applied to the recurrent state it is a stateless-tree lifecycle; applied to the attention KV it is the missing re-linearizer that had been emitting near-neighbor identifier garble the whole time.

Abstract

Vol. III built a distribution-preserving token-tree verifier for Qwen 3.6-27B-FP8, a hybrid whose 64 layers include 48 Gated-DeltaNet recurrent layers. Vol. IV turned the prefix cache on and found it worked for the native decode path but not for the tree. This page resolves the tree path. The unifying observation is that native speculative decode is cheap to cache and commit for one structural reason: its accepted tokens form a linear chain, so every piece of committed state — the recurrent GDN state, the conv window, the attention KV — lands at a contiguous, linearly-addressed position that the framework already handles. A branched tree violates that assumption; its accepted path is a route through a per-node workspace, non-contiguous in the layout the next step reads.

We make the tree behave like native at the data layer along two axes. First, a stateless-tree redesign: the tree keeps no persistent state across steps. Each step initializes its scratch from native's running rows, drafts and verifies inside that scratch, copies the committed leaf back onto native's running rows, and burns the scratch to zero. Native's stock, request-keyed cache then owns snapshot, restore, and concurrency exactly as it does for native MTP — and the two cache carriers Vol. IV chased are eliminated by construction. Second, the garble hunt: a persistent near-neighbor identifier corruption (read_file → readFile, expected_row_count → expected_rowcount) that had defeated every numerical gate turned out to be a data-routing bug — the attention KV of committed tokens was being read from a sibling branch's slot. The fix re-linearizes it, mirroring the recurrent remap. Both are the same principle applied to different state, and together they take branched-tree garble from ~40% to 0% and SWE-Verified resolve to native parity.

The governing principle (the acceptance bar): the tree pipeline must be behaviorally indistinguishable from native MTP at the data layer — the same block-pool rows read and written, at the same times, holding no persistent state beyond what native holds. Only the speculative-decoding math may differ (the branched scan), and its workspace is burned every step. If the tree's persistent-data access pattern equals native's, a cache-behavior divergence is impossible, because native has none.

Contribution

Two fixes and one idea. The idea is that a branched verifier can be made cache-correct not by patching the cache to understand branches, but by making the tree stop asking the cache to — it re-linearizes to the accepted path and holds no state, so the stock cache never sees a branch. The recurrent half is a stateless-tree lifecycle; the attention half is a KV re-linearizer that also happened to be the root cause of a months-long garble.

This page is the sequel to Vol. III (the verifier) and Vol. IV (the cache), and is self-contained. It also records the debugging story honestly, because the reason the garble took so long to find is itself the most portable lesson here.

The shortest version: native speculative decode is a linear chain, so all its committed state is contiguous and the framework caches it for free. A branched tree is not a chain, so its committed state is scattered — and every place we read that state back at a linear position, we read a sibling branch's data instead. Doing this for the recurrent state is the stateless-tree redesign; the attention-KV twin was the garble bug.

The Contract: Two States, One Discipline

One idea, applied twice: the recurrent state and the attention KV are different tensors with the same problem — a branched accept scatters them, and a linear re-read grabs the wrong one. The discipline is identical for both.

A speculative step produces state that the next step must read back: the recurrent GDN state, the conv1d window, and the attention KV of the accepted tokens. Native writes those at contiguous positions and reads them from the same, so the stock cache is correct with no special handling. The tree writes them into a branched workspace and must move the committed ones onto native's linear positions before the next step — otherwise a positional read lands on a sibling. Everything on this page is one discipline applied to each cached state.

The recurrent and conv remaps are the stateless-tree redesign; the attention-KV remap is the garble fix. They were built weeks apart and diagnosed very differently — one from first principles, one after a long hunt — but the completeness argument at the end is simply that these are the only three cached states, and each now has a re-linearizer.

Why Native Caches for Free

Plainly: a chain has one path, so "the state after k accepted tokens" is always at slot k−1. A tree has many paths, so the accepted one is scattered, and "slot k−1" points at whichever branch happened to be sorted there.

vLLM's stock mamba cache rests on a single structural assumption: after a speculative commit, the accepted tokens form a linear chain. Two things follow, and native satisfies both, so it needs no extra code. First, linear accept means the row is right: the native verify kernel writes token t's running state into column t, so column-index equals chain-depth equals accept-order — an exact bijection. The committed state after num_accepted tokens is at the fixed row num_accepted−1, and the stock snapshot reads exactly there. Second, the producer and consumer share a numeric basis: native's cached boundary seed is produced by the same kernel family the cache-hit restore folds from, so restoring and recomputing reproduces the sequence — empirically native's cache miss and cache hit are byte-identical.

The tree fork breaks both, independently. The GDN kernel writes each tree node's state into a node-bank row keyed by node, not by accept order; the accepted tokens are a root-to-leaf path, so the k-th accepted token is node path[k], generally not k−1. Stock's linear formula therefore snapshots a sibling, cousin, or never-written row — measured wrong on every branched-accept sample (48 of 48, with divergences up to 23 at layer 0). That is a row-addressing failure: the stock save/restore does not apply to a branched accept, it is not merely imprecise. Separately, even the correct leaf row carries a value produced by the tree's own decode kernel, a different numerical realization than the chunked restore fold; that cross-basis delta compounds across 48 recurrent layers, and because the tree committer accepts by greedy longest-prefix-match rather than exact rejection sampling, it inherits no losslessness theorem to absorb it.

Figure 1A chain's accepted state is contiguous; a tree's is scattered, so a linear read lands on a sibling

Figure 1 is the whole paper in one picture. Native's accepted path is the slot order, so reading slot k returns token k for free. The tree's accepted path is a non-contiguous subset of the sorted node slots, so reading position 3 linearly returns whatever branch node was sorted into flat-slot-3 — a sibling. Every fix here is: move the committed nodes onto the linear slots before that read.

The Stateless Tree

The reframe: stop teaching the cache about branches. Make the tree stop keeping state, so the cache only ever sees native's linear rows — which it already handles perfectly.

The economics: the per-step state is a few megabytes; an HBM-to-HBM copy is microseconds against a ~98 ms decode forward. Copying is free. Avoiding it was a false economy that cost correctness.

Vol. IV's answer to the row-addressing problem was a stack of machinery that taught the cache to follow branches: a leaf map recording which node-bank row the committer wrote, a snapshot redirect pointing the cache at that row, a bias translation walking the accepted path, a stale-global cleaner, plus a second family of fixes for the numeric-basis half. It worked, but it was fragile — one intended piece (a chunked-realization producer) never fired at all, so the deployed path fell back to a within-floor-but-not-bit-exact seed, fed to a committer with no losslessness theorem. Every piece existed only because the tree kept persistent state the cache then had to chase.

The redesign deletes the premise. The tree pipeline maintains zero persistent state; each step is a pure function. It initializes its scratch from native's running rows, drafts and verifies inside that scratch, copies the committed leaf back onto native's running row, and burns the branch scratch to zero. After that, native's stock, request-keyed cache owns snapshot, restore, and cross-request concurrency for both recurrent states — exactly as it does for native MTP, because at the data layer there is now nothing to distinguish them. The two cache carriers Vol. IV chased are gone by construction: there is no tree-owned state left to go stale, be reused dirty, or bleed between concurrent agents.

Figure 2Every step is a pure function: seed from native's row, verify in scratch, commit the leaf, burn the rest

Figure 2 is the recurrent half of the discipline. The only state that persists past a step is native's own running row (column 0); everything the tree added — the branch scratch — is zeroed. Native's cache then does snapshot, restore, and concurrency with no knowledge that a tree was ever involved, which is the entire point.

The root the redesign closes. Column 0 of the state page is native's running row; columns 1 through num_spec are the tree's ephemeral drafts. But the tree deposited its committed leaf one column over and read it back positionally, so for two or more accepted tokens the running row was stale — it held the post-first-accept state while the true committed leaf sat in a branch column. That is exactly why tree-plus-no-cache had no give-ups (the leaf column survives within one continuous decode) yet the cache poisoned the tree under concurrency (the ephemeral column and the redirect are not request-owned across reallocation). Committing the leaf to column 0 and reading column 0 makes the running row the committed frontier again, for both the recurrent state and the conv window, in one write.

Two kernel facts make the write free and safe: the register holding the committed leaf at loop exit is byte-identical to what already gets stored to the branch column, so storing it to column 0 as well changes no values; and the initialization tile is loaded into registers before any store, so reading column 0 and then overwriting it in the same launch is safe. The three flags — commit-to-running-row, read-from-running-row, burn-the-rest — form one lifecycle, gated off by default to a byte-identical path, with a fail-loud guard that refuses any partial enable. That guard is not ceremony: the conv and SSM states share one physical page as strided views, and native's restore rewrites the whole page, so re-routing one without the other corrupts the page on the next restore.

The Garble Hunt

The symptom: the tree commits a plausible-but-wrong neighbor of the right identifier — read_file → readFile, expected_row_count → expected_rowcount, astropy → astrop. The code reads as correct; it just references a name that was never defined.

Running alongside the cache work was a stubborn quality bug. On code-heavy agentic tasks the branched tree systematically corrupted multi-word identifiers into near-neighbors: a dropped underscore, a truncation, an abbreviation, occasionally a wrong word. The model's comprehension was intact — it planned correctly and emitted the right structure — but emission degraded, and a single corrupted identifier raises a NameError, which sends the agent into a typo-fixing loop until it burns its budget and gives up with an empty patch. On a controlled identifier probe the native path corrupted nothing (0 of 45); the tree corrupted roughly one in ten. On real agentic tasks the gap was starker: a ~40% corrupted-identifier rate against native's ~1% floor.

The mechanism at the point of emission was clear and, it turned out, misleading. The tree's verify forward was numerically drifted: at a garbling position, the truly-correct next token — which a no-spec forward assigns near-certainty (probability around one in a million for the wrong neighbor) — had its margin compressed by roughly eleven nats until the near-neighbor sat inside the sampling nucleus at probability 0.08, and the committer accepted it. The committer itself was exonerated: an offline gate confirmed it accepts tokens at exactly the target distribution. So the corruption was upstream, in the verify logits — and drifted logits look, for all the world, like a numerical bug.

Dead end

The compute hunt

For weeks the search was numerical: GEMM batch-invariance, a fixed-M projection pad, GDN-scan nativeness, attention-compute alignment. Each looked plausible because a small near-neighbor drift is what a numerical bug produces.

The variance wall

A fix you cannot measure

The tree's garble rate is set per boot by autotune: the same config swung 2.96% to 9.56% across boots. A promising −68% pad-block "fix" landed at 3.10% — inside the baseline's own boot-to-boot swing. Cross-boot, single-lever A/B could not tell a fix from luck.

A control that held

Batching was not it

Native under real eight-way co-residency stayed at 0% garble; the tree garbled at one agent per server just as much as at eight. Whatever it was, it lived in the tree path itself, not in batching or concurrency.

The turning point was to stop bisecting. Instead of testing one numerical fix at a time — which, when garble survived, only ever proved "not this op," never "not compute" — we ran the kitchen sink: every suspected compute and state fix armed simultaneously, needles confirming each fired. Garble was unchanged, 15 of 15. That single fifteen-minute experiment exonerated the entire compute class at once and forced the conclusion the isolation grind had been avoiding: if no combination of numerical fixes moves it, the bug is not numerical. It is what the forward reads.

The Root Cause: Committed-Token KV, Read From the Wrong Slot

The tell we had all along: a foreign K/V read grabs a sibling draft's K/V — and a sibling draft is a near-neighbor. So the drift was always going to look small and near-neighbor. The symptom was never evidence against routing; it was the fingerprint of it.

The recurrent state had a re-linearizer — the stateless-tree commit moves the accepted node's state onto the running row. The attention KV had none. Its cache is vLLM's sequential paged store, whose native slot mechanism is correct for chains, and nobody had revisited it for branches. Each tree node writes its K/V to a flat, sorted verify slot. For cat8 the accepted spine occupies flat slots 1, 2, 4, 6, 8, with the sibling branches interleaved at 3, 5, 7, 9. After the accept, the sequence length advances and the next forward reads the committed tokens at linear positions 1, 2, 3, 4, 5 — so position 3 reads flat-slot-3, which is a sibling branch node, not the accepted spine. The forward attends over a neighbor's key and value, its logits drift toward that neighbor, and it commits a near-neighbor identifier. Measured topologically, accepts read foreign KV at every depth past the first: depth 1 was clean, depths 2 through 5 read the sibling.

Figure 3cat8: the accepted spine sits at flat slots 1,2,4,6,8; a linear re-read of position 3 grabs the branch at slot 3

Figure 3 is the bug and its fix. The branch K/V was computed correctly; it was read from the wrong slot on the next step. The remap copies each committed node's K/V from its scattered flat slot to the linear slot the next forward will read — the exact twin of the recurrent commit in Figure 2. It runs in the sampler, outside the captured graph region, so it is graph-safe, and it moves under a megabyte per step against a ~99 ms forward, so its cost is noise.

The fix is launch_attn_kv_linear_remap: after a branched commit, copy each committed node's key and value from its flat verify slot to its linear committed slot, for every full-attention layer, inside the sampler. It is wiring and data movement, not a kernel change; it keeps all branches; and the capture that feeds it is exclusion-based — it grabs every attention group whose builder is not the recurrent kernel — so it is robust to any attention variant rather than a narrow whitelist. The measured cost is a 0.7% change in per-forward time, inside cross-boot noise.

Results

The bar: the tree should garble no more than native and resolve no worse. Both hold. The one number that is not a quality claim — the tree-shape accept difference — is called out as speed in the next section.

Token-ledger: a byte-identical token-sequence compare against native, not just a gross-garble scan. cat8 fix-on scores 0/15 — the committed tokens are native's.

The trajectory change is the tell that this is a real fix, not a metric that happened to move. The no-fix tree was bimodally dysfunctional — a cluster of two-turn hard give-ups and a tail of eighty-to-a-hundred-turn garble-thrash. Fix-on, both modes are gone: a healthy median around fifteen turns, a minimum of eight with no give-ups, a maximum of thirty-five with no thrash, and fifteen of sixteen tasks editing the correct source file. Resolve tracks native task-for-task; the net movement was three garble-failures rescued against one temperature-noise regression, which is what a fix that removes corruption without injecting errors looks like.

Reflection: Why It Took So Long

Worth stating plainly: once localized, the fix was obvious and cheap — mirror the recurrent remap, a small copy, no kernel work. Nearly all the cost was in localization, and localization was slow because the hunt fought the symptom's disguise instead of its structure.

The bug was a data-routing gap masquerading as a numerical one, and three things kept the disguise on. The recurrent state already had a working remap, so state re-linearization felt solved — and the symmetric missing piece was invisible precisely because its analog was done. The linear chain was clean, so garble read as "branches are just harder" rather than the structural fact that chains are contiguous and branches are not. And the near-neighbor symptom pulled every instinct back toward compute, when a foreign-KV read — a read of a sibling draft — produces exactly a small, near-neighbor drift. The clue was there the whole time; we kept reading it as noise.

The portable lessons from the retrospective.
Lesson What it means here
Elimination-by-combination beats bisection for a class Testing numerical fixes one at a time only ever proved "not this op." The kitchen sink — every suspect armed at once — ruled out the whole compute class in fifteen minutes. Bisection is for finding a member, not falsifying a category.
A working analog is a map to the missing twin The recurrent remap should have prompted the question "what is the attention-KV analog, and does it exist?" Asymmetry between parallel subsystems is a high-yield place to look.
Framework assumptions break at the edge, silently "The framework handles the KV" was true for chains and false for branches. Audit such assumptions at the edge case (non-contiguity), not the happy path.
Match the instrument to the failure mode A scalar rate and a greedy near-tie gate had false negatives; the honest per-token gate at serving temperature was the instrument that held.
Distrust the symptom's surface "Small near-neighbor drift" felt like compute, but it was the fingerprint of a foreign read. The symptom was never evidence against routing.

Threats to Validity

Honest scope: the quality goal is met — committed tokens are native's, resolve matches native. The open item is speed, and the clean speed comparison has not yet run.

Speed, not quality

The residual is a speed effect

Different tree shapes accept at slightly different rates (a small, roughly 0.09-token gap between cat6 and cat8 at matched decode), driven by how tree width perturbs the attention projection. It is speed-only: the committed tokens are byte-identical to native, so nothing is lost. An earlier, larger version of this gap was a garble-composition artifact, not a real effect.

Speed A/B pending

The throughput headline is unproven

The tree's whole justification is that its branches accept more tokens per forward than native's chain. That superset win is not yet cleanly measured — the trustworthy per-forward cost is in hand, but the confound-free tree-vs-native throughput A/B is blocked on a serving-capture plumbing mismatch, independent of this fix. Do not quote a derived tokens-per-second number; the two GPU-time bases disagree in a way that flags an artifact.

Statistics

Sixteen tasks, one run each

Resolve parity is directional over sixteen SWE-Verified tasks at one run per cell. It tracks native task-for-task with an honest per-task rescue/regress ledger, but it is not a powered resolve-rate claim.

Simplification

The old machinery is now redundant

Once the stateless lifecycle owns correctness, the Vol. IV carrier machinery (leaf map, snapshot redirect, the dead chunked-realization producer) is dead weight. The access-equivalence proof gate and the physical deletion pass are the queued follow-ups; until they land, both paths coexist.
