Codex-Harness-Coupled Speculative Decoding for Qwen 3.5-27B on DGX Spark

A five-point ablation of a four-technique speculative-decoding stack, across 220 cells of a real coding-agent workload — and a closer look at what actually composes.

Mark Ma · coredroid0401@gmail.com · ML systems / inference

Summary

A four-technique speculative-decoding stack, co-designed with the agent harness, lifts decode throughput on a 27B coding agent from 5.6 → 17.0 tokens per second on a single consumer-Blackwell GPU. That is a 3.04× speedup at unchanged FP8 weights — and, more interestingly, it converts one of eleven benchmark tasks from 0 / 4 → 4 / 4 pass by giving an iterative multi-file refactor enough headroom to finish.

The headline number is one half of the story. The other half — which techniques carry the win, and why most of them don't compose — is what makes this an engineering result rather than a benchmark number.

  • T1 alone is the throughput winner (3.26× over baseline). Layering T2 + T3 + T4 on top of T1 is net negative for throughput in aggregate (−7%) — but flips a single hard task from fail to pass, which is why the full stack still ships.
  • T2 and T3 are mirror images on 5 of 11 tasks: when one helps, the other hurts by roughly the same amount. They appear to compete for a shared drafter-slot budget rather than tapping orthogonal sources of acceptable drafts, as the original design assumed.
  • Pass rate is largely orthogonal to throughput. 8 of 11 tasks pass or fail identically across all five spec-decode configurations — the model either solves them or it doesn't; how fast it writes doesn't change that.

01Why this matters

Coding agents are inference-bound. Each turn replays a multi-thousand-token context; many turns repeat structural patterns (JSON tool-call skeletons, file paths, function names, plan templates). A 27B model on a single consumer Blackwell GPU (DGX Spark, sm_120) decodes at ~5–6 tokens per second under base settings — slow enough that roughly three quarters of attempts run out the 30-minute wall budget before the agent finishes the task. The agent loses on the clock, not on correctness.

Speculative decoding promises to fix that. The hard part is making it actually compose with the harness. A generic spec-decode setting that ignores the agent's session state and tool-call structure leaves most of the available draft-acceptance on the floor. Conversely, a stack that over-couples to the harness produces techniques that fight each other inside the verifier's per-step token budget — which is exactly what this experiment found.

The contribution of this work is not just "we got 3×." It is the per-technique decomposition that lets future iterations know which knobs to leave alone and which to gate on workload.

02What I built before measuring anything

The "I got 3×" line in §1 buries the prerequisite work. Before any of the speculative-decoding measurements could exist there had to be (a) a benchmark to measure on, and (b) a serving stack that Codex CLI and vLLM could actually talk over. I authored both. They are the load-bearing artifacts of this project.

2.1 CNB-55: a benchmark I authored end-to-end

The eleven tasks measured in this report are my own benchmark, not a borrowed one. I designed it as CNB-55 — a Linux-only, offline, reproducible agentic eval built around codex exec as the reference runner — and authored every part of the stack:

  • Task content. Each family is a workspace bundle (real source tree, fixtures, AGENTS.md prompt, hidden state) plus a five-level variant progression (V1–V5) that hardens the task through a probe → harden → re-probe loop. The repository currently holds 39 verifier directories under verifiers/, with matching workspace bundles under scenario_families/ and per-family verifier_data/. Round 4b uses the eleven that have cleared the v4a_v2 freeze gate.
  • Deterministic judges. Every family gets a five-milestone Python scorer that runs against the agent's modified workspace — for example verifiers/dead-flag-reachability-audit/score_reachability.py, verifiers/multi-tool-transaction-repair/score_transaction_repair.py, verifiers/security-audit-hotfix-remediation/score_hotfix.py, verifiers/responses-sdk-adapter-cutover/score_responses_cutover.py. Scoring is local-Python, fully deterministic, and the test gates ride inside the same docker container that the agent ran in — no LLM-as-judge in the loop. P_benchmark ≥ 65 ⇒ pass.
  • Calibration. The whole pattern is calibrated so a frontier model — codex exec --model gpt-5.4 --reasoning-effort high — scores in the 15–25 band, with deliberate headroom. Not saturated (≥70) and not noise (≤5). The authoring spec, CNB-55-authoring-spec.md, locks the contract every family must meet before admission (workload type, hidden-state shape, milestone definitions, variant progression, freeze gate).
  • Why a new benchmark at all. SWE-Bench Verified is saturated (≈80% at frontier). The next-gen benchmarks (SWE-Bench Pro, ALE-Bench, BrowseComp-Plus, AppWorld, ToolSandbox) target the properties Verified under-tests: long-horizon reasoning, partial credit, contamination resistance, managerial judgment. CNB-55 lives in that next-gen space, Linux-native and Codex-first.

That is the substrate this whole report sits on. The numbers in §4 are not "what spec-decode does to a benchmark someone else built"; they are "what spec-decode does to the benchmark I built to stress-test Codex-style agents."

2.2 Engineering required to make Qwen 3.5 + vLLM + Codex actually run

Codex CLI talks the OpenAI Responses API with stateful event semantics; vLLM 0.19 does not natively speak it; Qwen 3.5-27B has its own quirks; the GB10 (sm_120 consumer Blackwell) is on a hardware tier that wants different fallbacks than the spec defaults. Getting from "vLLM serves Qwen on this GPU" to "Codex CLI can drive a real agentic loop against it for 30 minutes without a stall" was its own multi-week project. The headline fixes I shipped:

vLLM ↔ Codex Codex emits Responses-API requests; vLLM expects Chat Completions plus tool calls. Direct wiring fails on tool-call payload shape. Auto-continue workaround: when the model emits an empty or under-budget completion, the harness silently re-issues a continuation prompt with the prior previous_response_id. The repo's commit message records it bluntly: "auto-continue is load-bearing — qwen3.5-27b END-TO-END SUCCESS." ("§17") The investigation walked through three other dead-ends first (chat-template tweaks, non-streaming bypass) and ruled them out empirically.

Container build The stock vllm/vllm-openai image doesn't compose with sm_120; needed an NVIDIA-base image with CUTLASS FP8 paths enabled. Self-built image lumo-flywheel-vllm:26.01-py3-v0.19.0 from nvcr.io/nvidia/pytorch:26.01-py3 (docker/Dockerfile.nvidia-vllm).
Run isolation Codex's own docker containers, if reused across attempts, leaked workspace state and contaminated wall-clock numbers. Per-attempt docker isolation: each Codex run gets a fresh container, fresh workspace, fresh proxy capture file — verified via the contamination audit in §7.
Measurement substrate vLLM's built-in metrics don't break down per-call decode time or per-call accept rate; the data needed for this study didn't exist upstream. Proxy-side per-request capture (vllm_request_metrics.jsonl): one row per request with prefill_sum_s, decode_sum_s, completion_tokens, spec_decode_num_accepted_tokens, spec_decode_num_draft_tokens, plus session-prefixed X-Request-Id and synthesized X-Lumo-Oracle headers. That capture is what the canonical decode_tps numbers in §4 are computed from.

The commit history calls this the "Benchmark-validity §11–§19" series. Without it the speculative-decoding measurements simply don't exist — Codex stalls mid-task, the agent emits empty turns, and no attempt finishes inside the 30-minute budget. "auto-continue is load-bearing" is the most representative one-line summary of the work.

03The four-technique stack

The Round-4b configuration extends vLLM 0.19 with Snowflake Arctic Inference 0.1.2's SuffixDecoding backbone, then layers three harness-coupled drafters on top. (A fifth technique, T5, handles drafter lifecycle and is operational rather than throughput-bearing — out of scope here.)

IDTechniqueWhat it doesPredictedMeasured
T1 cross-turn SuffixDecoding Per-session suffix tree spanning all prior turns of an agent task. 1.4–1.6× 3.26×
T2 read_file proactive priming When the agent reads a file, fold its content into the session's suffix tree as drafts. ×1.10–1.20 −1.5% agg
T3 schema-aware tool-call drafter FSM (ToolSpec + XGrammar-2) alternates deterministic schema-token filling with free-text speculation. ×1.6–2.0 −5.0% agg
T4 plan-structure pre-drafter Fingerprints structural tokens (separators, headers, numbering) across plan emissions; pre-drafts them on subsequent turns. ×1.03–1.08 +4.3% agg

T1 is structural — the per-session router around SuffixDecodingCache — and cannot be toggled without relaunching the inference container. T2, T3, T4 toggle at request time via a JSON flag file the prelaunch helpers consult: /tmp/lumo_track_b_runtime_flags.json.

3.4 Metric definitions

To remove ambiguity about what is being optimized:

  • decode_tps = completion_tokens / decode_sum_s, computed per request, then medianed per attempt, then per cell. Numerator is accepted output tokens (rejected drafts excluded); denominator is GPU decode time. This is the canonical Track B target — final-output decode speed, not draft throughput.
  • accept_rate = spec_decode_num_accepted / spec_decode_num_draft. Approximates drafter precision.
  • P_benchmark = 0–100 score from a deterministic per-family grader. Pass = P ≥ 65.

Three distinct pass-rate regimes:

  1. Task-bound (8 / 11). Pass rate is identical across all five points. The model either solves them or doesn't; spec-decode is completely orthogonal.
  2. Technique-helped (2 / 11). sqlalchemy flips 0/16 → 4/4 only at D. Hypothesis: iterative multi-file refactor needs throughput headroom to finish all milestones inside the 30-minute wall. release-note picks up one pass at C/D.

5.1 T1 — cross-turn SuffixDecoding (the load-bearing technique)

A vs OFF isolates T1. Across every task in the corpus, A is 2.4–5.1× faster than OFF; the aggregate is 3.26×. Per-call acceptance rate climbs from 0.41 at turn 0 to 0.53 at turn 21+ on the same cell — direct evidence that the session-scoped suffix tree is doing what it was designed to do: get richer as the agent accumulates history.

T1's biggest wins are on tasks with high cross-turn structural repetition: sqlalchemy (4.84×), release-note (4.83×), responses-sdk (4.36×). All three involve the agent revisiting the same files, function names, and error patterns repeatedly.

5.2 T2 — read_file proactive priming (bimodal)

B vs A. T2 is the most interesting technique because it is simultaneously the biggest per-task win and a net-flat aggregate:

B's overall accept rate (0.555) is higher than A's (0.471) — T2 does generate more accepted drafts. But on tasks where T2 hurts decode_tps despite higher acceptance, the drafter is spending time proposing primed-text drafts that get accepted at high rate but compete for slots with shorter-but-higher-yield drafts from the suffix tree. Higher accept-rate is not the same as higher throughput when drafts vary in length and per-token yield.

5.3 T3 — schema-aware tool-call drafter (the mirror of T2)

C vs B. The three tasks where T2 won big (dead-flag, incident-evidence, transcript-merge) are the same three tasks where T3 reverts those wins. The two tasks where T2 hurt (responses-sdk, policy-aware) are two of the three tasks where T3 wins.

This is the cleanest single-table evidence for the slot-contention hypothesis (see §6). C's accept rate (0.554) is essentially identical to B's (0.555) — T3 produces equally-acceptable drafts, but they displace T2's on the wrong frames.

5.4 T4 — plan-structure pre-drafter (small-positive in aggregate)

D vs C. T4 wins on 7 of 11 tasks and meaningfully hurts on 3. It is the cleanest "composes positively" signature of the three additive techniques. Why doesn't it double-count with T1's suffix tree? Plans are emitted at irregular intervals; the suffix tree captures token sequences but not the meta-structure of "this is a plan, with this fingerprint, and the next plan emission should repeat this structure." T4 fingerprints structural tokens (separators, numbers, headers) and pre-drafts them with high confidence, which gives the verifier a fast path through the formulaic parts of plan emissions.

07The mirror-image finding

The single most interesting observation in this study is that T2 and T3 cancel each other on 5 of 11 tasks. Looking at the marginal-effect table side by side:

Read columns 2 and 3 together: where T2 is ≥+5, T3 is ≤−5; where T2 is ≤−5, T3 is ≥+5. That's not a model artifact — it's a resource-contention signature.

The original spec assumed T2, T3, and T4 tap orthogonal sources of acceptable drafts (file content, schema, plan structure). In practice they compete for the verifier's fixed num_speculative_tokens = 12 per-step budget.

Proposed mechanism: drafter slot contention

Each verifier pass has a 12-token budget. T1 produces N₁ drafts from the suffix tree; T2 produces N₂ drafts from primed file text; T3 produces N₃ drafts from the schema FSM. The drafter coordinator must pick which to emit. With T2 and T3 both active (C), the priming-buffer drafts and the schema-aware drafts compete for the same slots:

  • On file-edit-heavy frames (dead-flag, incident-evidence, transcript-merge), T2's drafts are highest-yield and T3 displaces them.
  • On tool-call-envelope-heavy frames (policy-aware, responses-sdk), T3's drafts are highest-yield and T2 displaces them.

Testable prediction: a workload-aware priority scheme (per-frame draft weights based on the predicted next-emission type) should let C match B-on-T2-tasks and B-on-T3-tasks simultaneously. That is the natural Round-5 follow-up.

08Hardware telemetry & contamination methodology

Telemetry on consumer Blackwell (sm_120) is limited: DCGM profile fields (sm_active_pct, dram_active_pct, tensor-pipe utilization) are unavailable on this hardware tier. NVML gives us three fields: power_w, gpu_util_pct, mem_copy_util_pct.

Two unexpected findings forced a methodological detour:

7.1 GPU utilization is uninformative

NVML's gpu_util_pct sits at 94–96% across all five points, including OFF. That field reports the fraction of time the GPU is processing any work, not actual compute intensity. With requests arriving constantly from the agent harness, the GPU is "busy" the same fraction of the time regardless of spec-decode setting. This metric is unusable for distinguishing techniques.

7.2 Power-as-contamination-detector caught 4 cells

Per-cell power_w analysis flagged 4 attempts with confirmed contamination: high power simultaneous with low decode_tps (a work–power inversion). All 4 originally clustered temporally on 2026-05-12 evening — a single ~3-hour window where external load on the host degraded those attempts.

Remeasured 2026-05-17 under a verified host-quiet relaunch (load 0.17, vLLM the only GPU compute process). Contamination did not recur; the cell-max-tps / cell-min-power reference detector caught all 4 contaminated attempts and zero false-positives on A/B/C/OFF.

The lesson is sharp: the pre-remeasure draft of this report cleaned the 2 contaminated cells by computing a 2-attempt median from the remaining clean attempts. That gave 22.78 and 18.86 tps — both substantial overestimates of the cells' true central tendency (true 4-attempt medians: 16.54 and 13.13). Small-sample medians on high-variance cells are not safe substitutes for full replication. The contamination fix must be re-measurement, not exclusion.

That single methodological move flipped the directional conclusion of the report from "+3% net gain from the full stack on top of T1" to "−7% net cost from the full stack on top of T1."

09Limitations & threats to validity

  1. Corpus size. 11 tasks × 4 attempts gives cell-level CIs of roughly ±2–3 tps. Differences smaller than that should be read as flat.
  2. Single hardware × single model. Results are specific to GB10 / Qwen 3.5-27B FP8. The slot-contention finding may relax on larger models with more per-token compute.
  3. Measurement-window confound. D was measured 2026-05-12 through 2026-05-13; A/B/C/OFF over the following three days. Host median power differed by ~5 W between the two windows, suggesting environmental noise. Within-block comparisons (A vs B vs C) are clean; cross-block A-vs-D should be read as upper-bound.
  4. OFF measurement timing. OFF ran after A/B/C with the same vLLM container instance, which had been serving warm-context requests for 3 days. OFF's anomalously low turn-0 prefill (0.38 s vs ~11 s on spec-decode points) suggests prefix cache leaked across rounds. Future protocols should clear it explicitly between points.
  5. Telemetry gaps on consumer Blackwell. Cannot distinguish "GPU is busy because spec-decode is working" from "GPU is busy because verifier pass is rejecting drafts."

Stretch (Round 5): implement per-frame draft priority and confirm the slot-contention hypothesis. If the mechanism holds, a workload-aware D could plausibly recover ~15% throughput on top of T1 while preserving the sqlalchemy pass-rate win.

11About this work

This page summarizes the Round 4b ablation from the Lumo FlyWheel project — a self-hosted serving and benchmark stack I built to study inference-time techniques for coding agents on consumer hardware. The repository contains the full vLLM serving layer, the proxy that normalizes Codex Responses-API tool calls, the eleven-family benchmark corpus and its deterministic graders, the run drivers and contamination detectors, and the formal report this page condenses from.

Over the seven-day measurement window (2026-05-11 through 2026-05-17) the repository accumulated roughly 90 commits, mostly attempt-level run logs that capture the round-by-round progression of the ablation. The full formal report (track-b-round4b-ablation-formal-report-20260516.md) is 1,029 lines; this page is the engineer-facing condensation.

What you're looking at, if you're a recruiter or hiring manager

This is end-to-end ML systems work: an inference-time research question (does harness-coupled speculative decoding actually compose?), built end-to-end on real hardware (a single consumer-Blackwell GPU), measured with an honest experimental design (cumulative ablation, sample-size-aware), and reported with discipline (contamination detected, retracted, re-measured rather than excluded; conclusions revised when the data demanded it). The most interesting result — the T2↔T3 mirror — surfaced because the ablation was prefix-cumulative; a one-shot A/B against baseline would have missed it.
