# Why native+cache needs no machinery but our tree+cache does

## 1. TL;DR

vLLM's stock mamba/GDN prefix cache is built on one structural assumption: after a spec-decode commit the accepted tokens form a **linear chain**, so "the recurrent state after `num_accepted` tokens" lives at the fixed linear row offset `num_accepted-1`, and that state was produced in the same numeric basis the cache-hit restore folds from. `native = naive_mtp/FLASH_ATTN` satisfies both halves and is therefore correct by construction — no extra code. Our `tree = tree_mtp/TREE_ATTN` fork violates both: the accepted tokens are a **branch/path through a per-node state bank** (a row-addressing mismatch), and the committed-leaf state is produced by a **different decode kernel** (`_tree_gdn_kernel`) than the chunked-prefill restore fold (a cross-basis numeric mismatch). Everything in the `FR13_APC_*` machinery exists to fix one or the other, and every piece is gated so that native — with an empty leaf map and a linear accept path — auto-no-ops back onto the stock restore.

## 2. The two decode paths + where the cache lives

- **native** = `naive_mtp` / `FLASH_ATTN`: vLLM stock MTP-5 linear-chain spec decode, unmodified GDN path. `native+cache` RESOLVES.
- **tree** = `tree_mtp` / `TREE_ATTN`: our forked branched-tree spec decode (chain5 spine + cat8/cat9 branch). `tree+cache` GIVES UP unless heavily patched.
- **The cache**: vLLM prefix caching with mamba block-aligned chunked prefill (`mamba_cache_mode="align"`, `MAMBA_BLOCK_SIZE=1024`). On a spec step, GDN metadata lays out `num_spec+1` consecutive block rows per request — `spec_state_indices_tensor = block_table_tensor[spec_masks, :num_spec+1]` (`vllm/v1/attention/backends/gdn_attn.py:256`), and the running-state row is `non_spec = block_table[:,0]` (`gdn_attn.py:207`). Both paths share ONE restore fold: on a cache hit, `initial_state = ssm_state[non_spec_state_indices_tensor]` (`vllm/model_executor/layers/mamba/gdn_linear_attn.py:984`) then the `<=block_size` suffix is rolled forward through `chunk_gated_delta_rule` (`gdn_linear_attn.py:990`). Only the *seed feeding that fold* and *which row gets snapshotted into the cache* differ between the two paths.

## 3. vLLM's stock mamba cache — why native is correct by construction

Stock restore is a single linear formula. In `get_temporal_copy_spec` the snapshot SOURCE is:

```
src_block_id = block_ids[cur_block_idx + num_accepted_tokens - 1]
```

(`vllm/model_executor/layers/mamba/mamba_utils.py:341`; the patch re-installs this verbatim at `scripts/fr10_phase4_patch_vllm_tree_gdn.py:14117`). This is correct **iff** two invariants hold — native satisfies both:

- **(i) Linear accept ⇒ the row is right.** The native spec-verify kernel `fused_sigmoid_gating_delta_rule_update` scans the one chain in sequence and writes token `i_t`'s running state into column `i_t`: per-timestep writeback `final_state_idx = ssm_state_indices[i_n*stride + i_t]; tl.store(p_ht, …)` (`vllm/model_executor/layers/fla/ops/fused_sigmoid_gating.py:159-166`), and reloads the committed initial state at the accepted leaf `i_t = num_accepted_tokens[i_n] - 1` (`fused_sigmoid_gating.py:106`). Column-index == chain-depth == accept-order is an exact bijection, so `block_ids[cur + num_accepted-1]` names the true post-accept row. The align-mode checkpoint save uses the same offset: `accept_token_bias = aligned_new_computed_tokens - num_tokens_running_state` (`vllm/v1/worker/mamba_utils.py:251-270`).

- **(ii) Producer basis == consumer basis ⇒ the seed is exact.** Native's cached boundary seed is produced in the same native/chunk numeric family the restore fold rolls from (linear-chain checkpoint, chunk-consistent basis). So the "resume-from-chunk-boundary + chunked suffix == cold full chunked prefill" identity holds and reload+recompute reproduces the sequence. Empirically native `MISS==HIT` is byte-identical (per MEMORY), which is the confirming evidence that native's seed and its on-hit recompute share one self-consistent stock route.

There is no special restore copy: the APC hash resolves the prefix to the cached aligned block, vLLM points `block_table[:,0]` at it, and the shared fold recomputes. No topology remap and no numeric re-anchoring are possible or needed.

## 4. What our tree fork breaks (two independent failures)

**(a) Branched-accept row addressing — WHY stock cannot be reused at all (write side).** Our draft is a tree; the GDN kernel writes each tree NODE's state into a node-bank row keyed by `spec_state_indices[b, node]`, NOT by accept order. The accepted tokens are a PATH root→leaf, so the k-th accepted token is tree node `path[k]`, generally NOT `cur+k-1`. Stock's linear formula therefore snapshots a sibling/cousin/never-written row into the cache block — a corrupted seed on the next hit. This was measured: the stock source row is "48/48 UNFAITHFUL, diff up to 23.05 at L0" and "stock postprocess 480/480 STALE = the residual-garble carrier" (`fr10_phase4_patch_vllm_tree_gdn.py:14297`, `:8978`). This is a hard correctness prerequisite, not a tolerance issue.

**(b) Align-boundary numeric reload — WHY even a correctly-addressed restore is only within-floor (read side).** Even with the right leaf row, its VALUE comes from a **different kernel** than the restore fold. Tree decode routes `h0=ssm_state` (`patch:5346`) through `launch_tree_gdn_prepared` / `_tree_gdn_kernel` — gated by `use_fr10_tree` requiring `_fr10_active_decode_mode=="tree_mtp"` (`patch:4490-4494`) — a per-node fp32-carry recurrence with a per-edge `state = state + 0.0` handoff (`fr10_gdn_tree_kernel.py:1136,1481`) and a measured leaf co-residency gather gap of 0.0289 (`fr10_gdn_tree_kernel.py:138,2021`). This is a *different realization basis*, not a sloppier one — our default replay is fp32-carry with `scan_align_on()` DEFAULT OFF (`fr10_gdn_tree_kernel.py:72-83`; the bf16-round-trip alignment seam is opt-in *to reproduce* native's SASS, so by default we are more precise than and simply differ from the native/chunk basis). Native decode instead uses the recurrent rank-1 `fused_sigmoid_gating_delta_rule_update` in the same numeric family as the fold. So on a tree cache HIT the seed's producer basis (`_tree_gdn_kernel`) differs from the consumer basis (`chunk_gated_delta_rule` fold), and that cross-basis ULP delta is folded forward through the suffix and compounds across ~48 GDN layers past the sampling margin (`FR13_TREE_CACHE_LOSSY_MECHANISM.md:99-104`). Aggravating factor: the tree committer is greedy-LCP (max over root-to-leaf paths), explicitly **not** the distribution-preserving rejection sampler, so it carries no spec-decode losslessness theorem — a within-floor seed perturbation can flip a near-tie sibling-depth argmax, whereas native's chain rejection sampler is theorem-protected.

**Verdict:** (a) is the ROOT — stock save/restore does not *apply* to a branched accept. (b) is the OCCASION — the chunk boundary is the only moment a save/restore happens, and it is where the cross-kernel seed delta gets amplified. Both contribute; they hit different machinery.

## 5. Each machinery piece (all tree-only; the gate)

The umbrella gate is `_fr10_tree_mamba_mode_active()` = `mode=="tree_mtp" and FR10_ENABLE_TREE_GDN=="1"` (`patch:13535-13548`); native returns False and the bias helper passes through `int(linear_bias)` unchanged (`patch:13635-13636`). Independently, every redirect reads `_FR13_APC_SSM_LEAF_BY_REQ`, which is **published only inside the tree committer** — `_fr13_publish_apc_ssm_leaf` (`patch:8972`) is called solely from the two tree replay/commit blocks (`patch:10761`, `:11447`), which native never dispatches. So native's leaf map stays empty and the `if leaf is not None` guards fail.

- **Leaf map `_FR13_APC_SSM_LEAF_BY_REQ`** [carrier (a)] — records `leaf_map[req] = spec_state_indices[b, accepted_len-1]`, the actual node-bank row the committer wrote (`patch:9080`). Native never runs the committer ⇒ map never created.
- **SNAP_FIX redirect** [carrier (a)] — in `collect_mamba_copy_meta`, source-only rewrite of `src_ptrs_np[…]` from the stock linear row to the published committed-leaf row, gated on `phase=="postprocess"` AND `get_temporal_copy_spec` (`patch:14294-14311`; comment: "Native MTP never publishes the leaf map -> auto-no-op (native-safe)"). Default ON. Native: empty map ⇒ redirect never fires. Its conv twin snapshots the whole conv row (SGLang recompute-not-copy, avoiding stock's non-invertible position-shifted suffix). Companion `FR13_APC_COPY_SRC_FIX` (`patch:13580-13618`) clears stale tree globals on a cold chunked-prefill step so a prior req's tree isn't stamped into a prefill carry.
- **Bias translation `_fr10_tree_accept_token_bias`** [carrier (a)] — translates the linear offset through the accepted path: `path_index = min(linear_bias, len(path)-1); tree_bias = path[path_index]` (`patch:13740-13741`), injected into stock preprocess/postprocess so `block_ids[cur+bias]` dereferences the accepted-NODE row. Native returns the untranslated bias (`patch:13635-13636`).
- **EXACT_SEED `FR13_APC_EXACT_SEED`** [carrier (b)] — keeps the cache pure chunked-lineage: capture the chunked-kernel realization only at 64/block-aligned boundaries and push the `<64` remainder through the *same* chunked kernel, so restore == cold prefill token-for-token (Remark 1). It FORCES the chunked branch and disables HRS (`patch:5995-6011`). Available on native but native's mismatch was eps-level, so it is only *needed* on tree.
- **REFOLD publisher `FR13_APC_BLOCK_REFOLD` / `REFOLD_TO_SNAPSHOT`** [carrier (b)] — the intended PRODUCER of a chunked-realization checkpoint for decode-crossed boundaries. **Confirmed non-functional**: it publishes to a channel the snapshot consumer never matches — `redirect_engaged=576` but `redirect_used=0`, "refold has NEVER consumed a state" across v1–v4 (`FR13_TREECACHE_CAMPAIGN_20260704.md:606-607`, `:448`). Shelved.
- **Recurrent-leaf FALLBACK** [carrier (b), used 100%] — because REFOLD never publishes, the consumer's chunked-checkpoint pointer stays None (reasons `no_pub_pos`/`no_aligned_pos`, `patch:14490,14493`) and the snapshot source falls back to the SNAP_FIX committed-leaf node-bank row — faithful within ~1-2 ULP, NOT the bit-exact chunked realization EXACT_SEED wanted.
- **HRS `FR13_APC_HIT_RECURRENT_SUFFIX`** [carrier (b)] — SGLang recompute-not-copy: on a cache-hit prefill, recompute the first `<=64`-token suffix RECURRENTLY with the bit-exact sequential rank-1 native kernel `fused_sigmoid_gating_delta_rule_update`, seeded by the restored boundary state, so no chunked WY touches the seed (`patch:5986`, recompute kernel ~`patch:6084`). Eliminates the chunked-prefill restart-fold artifact but is recurrent-not-chunked, so only partially consistent with the default chunked remainder.

## 6. Current state

- **REFOLD is broken** (`redirect_used=0` everywhere, `FR13_TREECACHE_CAMPAIGN_20260704.md:606-607`), so the pure-chunked-lineage path EXACT_SEED wanted never has a producer.
- **⇒ deployed tree+cache rides the recurrent-leaf FALLBACK 100%** (`patch:14382`): carrier-(a) addressing is corrected by the leaf map + SNAP_FIX redirect (the committed-leaf row is faithful), but the residual carrier-(b) chunked-vs-recurrent cross-basis delta is simply eaten.
- **⇒ tree stays sensitive**: that within-floor residual, fed to a greedy-LCP committer with no losslessness theorem, is what makes `tree+cache` fragile — tolerable now only via `ZERO_MAMBA_ON_ALLOC` + within-floor acceptance, not bit-exact.
- **HRS is the actual recompute fix** for carrier (b) (recompute-not-copy the suffix with the bit-exact rank-1 kernel), superseded on paper by EXACT_SEED (chunked-consistent by construction) — but EXACT_SEED depends on the non-functional REFOLD producer, so HRS remains the working recompute lever for the boundary numeric-reload half.
- **Native touches none of it**: linear accept ⇒ no leaf to mispick (empty map, redirect no-ops), and a chunk-consistent producer basis ⇒ no cross-kernel residual to amplify (`FR13_CACHE_FIX_KT.md:9,:18`). It rides the unmodified stock mamba cache restore.
## 7. Is the complexity worth it? (decision layer)

Sections 1-6 are the **cost** side: the tree carries forked TREE_ATTN + `_tree_gdn_kernel` + the tree committer + all the carrier-(a) machinery (leaf-map, SNAP_FIX, bias-translation, COPY_SRC) + the carrier-(b) machinery (EXACT_SEED, REFOLD[dead], fallback, HRS). Native gets caching for free (stock). So the tree must **earn** this with speed.

**The benefit is the superset** — the tree accepts a branch, not just a linear chain, so more accepted tokens/forward → higher decode speed. It is **content-dependent** (large when content has branch divergence to exploit; cat6-vs-spine5 showed bigger wins on some content). BUT the load-bearing number is **not yet cleanly measured**:
- Cache-ON accept is **contaminated** — the cache regresses acceptance (carrier b is literally an accept-regressing bug), so cat6/cat8/cat9 cache-ON accept (e.g. 2.8-3.1) is junk for this purpose.
- The trustworthy measure = **cat8 vs native-MTP accept/event, NO-CACHE**, which does not exist cleanly in the data (chain5 spine no-cache = 3.24-3.27 exists; cat8/native no-cache accept missing). Historic proxy = cat6root decode-TPS **23.88 vs spine 18.80 (+27%)** — but that is decode-speed not accept, cat6root not cat8. → **Task #15 measures it.** This doc cannot claim the complexity is justified until #15 lands.

**Simplification path (shrink the surface):**
1. **HRS > REFOLD.** REFOLD (the EXACT_SEED chunked-checkpoint producer) is confirmed non-functional (`redirect_used=0` v1-v4). HRS (recompute-not-copy, few lines, SGLang-aligned) is the working carrier-(b) fix. → **Delete refold / BLOCK_REFOLD / REFOLD_TO_SNAPSHOT + the EXACT_SEED chunked path; keep HRS.** (And rename: "exact-seed" bundles the redirect + the dead producer — the naming misleads.)
2. **Carrier (a) is unavoidable but cheap + already baked.** The branched accept genuinely cannot reuse stock's linear `num_accepted-1` formula (measured 48/48 unfaithful) — the leaf-map + SNAP_FIX redirect is a real requirement, and it works. Keep.
3. **The cache (shipment 2) covers BOTH pipelines.** native+cache = stock vLLM (free); tree+cache = our machinery. Since native caches for free, the tree machinery only earns its keep if #15's superset justifies it.

**Decision gate (once #15 lands):**
- cat8 accept **>>** native (a +27%-class win) → the superset justifies carrier-(a) machinery (unavoidable) + HRS (cheap); delete refold; ship tree+cache with HRS.
- cat8 accept **≈** native → simplify toward **native+cache** (stock, works) and keep tree as a research track — the complexity isn't buying speed.

**Bottom line:** the mechanism is understood and carrier (a) is solved; the only open engineering question for A' is whether HRS (carrier b) is enough or EXACT_SEED needs reviving (it doesn't, if we accept within-floor + HRS). The only open **strategic** question is #15 — does the tree's no-cache superset justify all of this over native+cache. Everything downstream (B=4 concurrency, graph/tool-call carrier) is gated behind those two.
