Lossless GDN Tree-Scan

A target verifier for token trees on a 75% recurrent hybrid model. The reusable result is the verifier contract: branch-local Gated-DeltaNet state, tree-aware attention, vLLM state publication, and measurement gates that make any future drafter accountable to native decode.

TL;DR: a draft tree is a menu of next-token guesses. The target model verifies that menu and publishes only the accepted prefix. On this Qwen hybrid, verification means two things at once: attention rows must see only their ancestors, and each GDN row must carry the recurrent state native decode would have produced on that branch. We use the native MTP head here, but the verifier can serve suffix decoding, MTP+suffix, or another drafter if it supplies the same tree contract.

Abstract

We present a tree verifier for speculative decoding on Qwen 3.6-27B-FP8, a hybrid model whose 64 layers include 48 Gated-DeltaNet recurrent layers and 16 softmax-attention layers. Tree verification in this regime is not an attention-mask problem alone. Each candidate row must carry the GDN state that native decode would have produced along that row's root-to-node path, while each attention row must see only the same ancestor tokens.

The implementation combines a forked FlashAttention-2 tree-bias path, a Triton GDN tree scan/replay kernel, vLLM tree-shape packing, device-side multidraft commit, and deployment-mode measurement gates. In the clean B=1/temp-0.6 deployment run merged to main on June 17, 2026, both depth-5 tree shapes beat native E5 and both are lossless within the native floor. On token-weighted decode throughput, cat6root reaches 23.88 tok/s versus 18.80 for native E5, a +27% gain. On the per-request-equal latency view, cat6root reaches 18.51 tok/s versus 17.80, a +4.0% gain.

Contribution

This paper treats the result as a systems proof, not a benchmark-only result. The contribution is a target verifier for recurrent hybrid models: it accepts a candidate tree from a drafter, verifies attention and GDN state branch-locally, and publishes only the accepted native-compatible prefix.

Earlier pages covered the search arc. This page is self-contained: it states the problem, names the prior work, shows the design trail, gives the kernel invariant, quotes the implementation seams, explains the hardware limitation, reports the merged B=1 speed/lossless result, and records the failed routes that shaped the final design.

Why This Matters

Drafter: the cheap source of candidate tokens. In this artifact it is Qwen's native MTP head.

Verifier: the target-model path that decides which candidates can be published without changing the model distribution.

The durable value is not a single caterpillar shape. The durable value is a verifier that understands both sides of this hybrid model: softmax attention and Gated-DeltaNet recurrence. Once that verifier contract exists, the drafter can change. The current paper uses Qwen's native MTP head because it is available inside vLLM, but the same verifier boundary can accept suffix decoding, an MTP-plus-suffix hybrid, n-gram candidates, or a learned external drafter if it emits the tree descriptor and candidate ids.

The second value is methodological. This work is a compact museum of how losslessness and speed were chased without letting one fake the other: scan A/Bs, replay byte gates, recurrent-oracle p-rescore, ON/OFF instrumentation separation, deployment-regime speed, shape sweeps, and failure records for approaches that were mathematically tempting but not shippable.

How We Arrived at This Design

Native MTP spine: Qwen's built-in speculative path verifies one linear chain of future tokens.

Our tree verifier: keeps that linear spine, then adds branches only if attention, GDN state, committer, and measurement all remain tied to native decode.

The final design is easiest to understand as a sequence of constraints. Native MTP already gives a strong depth-5 spine. The tree should therefore be a strict opportunity set around that spine, not a different model, a reward hack, or a looser acceptance rule. That premise forced the verifier to prove two things for every candidate node: the attention row is ancestor-only, and the GDN state is the same state native decode would have produced on that branch.

That is why the work is not just "make the attention mask wider." The intended WY-style tree algebra and STree-style state sharing were valuable references, but this deployment needed realization-level equivalence inside vLLM: fp8/bf16 kernels, FA2 attention, GDN recurrent state, sampled committer behavior, accepted-path replay, and durable state publication. Every time a shortcut passed one local test but failed a served-path gate, it became part of the design trail.

Design Question What We Tried or Compared Discovery Final Choice
Can we just use native MTP? Native E5 linear depth-5 spine. It is a strong baseline, but it has no branch opportunity. cat6root keeps the full depth-5 spine and adds only a root sibling. Use native MTP as the drafter source and baseline, then make the verifier tree-aware.
Can STree transfer directly? SSM/hybrid tree state sharing and accumulated transition thinking. It frames the right family of problem, but it does not close the served-realization gap: branch co-residency, bf16/fp8 codegen, and vLLM state publication can still diverge from native decode. Adopt the stateful-tree framing, then prove the serving path against native recurrent decode and deployment traces.
Can WY replace the sequential scan? Whole-tree algebra / one-pass state formulations. It was attractive for state traffic, but chunked WY is not the native verify oracle. Different summation trees and bf16 boundaries can change token decisions even when the real-number formula is equivalent. Use branch-local sequential scan plus accepted-chain replay; keep WY as an oracle/fallback, not the correctness contract.
Why fork FA2 attention? Default tree attention through a Triton unified_attention bias path versus native FA2. Triton tree attention can express the mask, but it is not native FA2's numerical realization. Stock FA2 keeps native numerics but cannot carry the tree mask. Patch FA2 so decode calls flash_attn_varlen_func(..., tree_bias=...) when FR13_FA2_TREE_BIAS=1; keep prefill native with FR13_FA2_PREFILL_NATIVE=1.
What made the result believable? Small probes, B=4 screens, raw prompt tests, big-denom deployment rescore, clean B=1 runs. Several earlier screens were confounded by trajectory, concurrency, or wrong denominators. The clean result needed deployment-regime runs plus separate lossless rescoring. Report speed, token-weighted throughput, per-request latency, and lossless gates as different measurements instead of collapsing them into one slogan.

Why the near-miss designs were not enough

The three tempting shortcuts failed for different reasons. STree answered the high-level question, WY answered a speed-shaped math question, and Triton tree attention answered the mask question. None of those alone answered the actual serving question: will the token that leaves vLLM be the token the native recurrent target would have emitted under the same sampled setting?

STree

State exists is not the same as state matches

STree is the closest prior-work lens because it treats tree decoding for stateful models. The missing piece for this system is realization. The literature survey notes that STree assumes the SSM tree forward equals the SSM sequential forward; our serving path had to prove that equality under vLLM, fp8/bf16 kernels, branch co-residency, and durable writeback. The practical warning showed up immediately: native vLLM tree attention was wired, but GDN recurrent state was still linear. On real Qwen tensors, non-linear branch nodes differed by 0.5618 until the FR10 GDN tree kernel was inserted. The custom kernel then matched the native production decode/update primitive at 7.45e-09 output max-abs and 7.63e-06 state max-abs.

WY

Equivalent algebra can still choose a different token

WY-style whole-tree algebra was tempting because the tree scan carries expensive state. It promised a cleaner one-pass formulation and a route around h_cache pressure. The blocker was the oracle. Native verify for this target is a sequential rank-1 recurrence. Chunked WY is a prefill formulation, and a different summation tree is enough to change low-bit bf16/fp32 boundaries. For lossless speculative decoding, those low bits matter only when they move argmax or sampling residual decisions, but that is exactly where this project spent its time. So WY stayed useful as an fp32 oracle and last-resort speed idea; the shipped contract became sequential branch-local scan plus accepted-path replay.

TREE_ATTN

A correct mask on the wrong kernel is still the wrong verifier

Triton unified_attention(..., qq_bias=...) could express tree ancestry, but native E5 used CUTLASS FlashAttention-2. The attention localization work found the mask/wiring could be right while the core attention op still differed: a post-fix attn_out_raw residual around 0.00195 per full-attention layer compounded across the 16 attention layers. Stock FA2 was not a drop-in answer either, because it had no tree-mask input; the plain flash path produced the wrong branch computation. The fork adds a real tree_bias input inside FA2 after QK and before softmax, preserving native FA2's MMA/reduction order while adding the ancestry constraint. Latest code verification says the deployed decode path uses that fork; unified_attention is only the fallback.

Prior Work

Speculative decoding: a cheaper draft path guesses future tokens, then the full model verifies them. If the verifier rejects a guess, the algorithm falls back without changing the target distribution.

Tree decoding: instead of one draft chain, the draft proposes several possible branches in one verification pass.

Tree speculative decoding is well studied for Transformer-style attention stacks. SpecInfer introduced tree-based speculative inference and parallel verification while preserving model quality. Sequoia made the tree shape hardware-aware. EAGLE-2 uses context-aware dynamic draft trees while keeping the output distribution unchanged. OPT-Tree frames the tree shape as an acceptance-versus-overhead optimization problem.

The closest prior work for this project is STree, which studies speculative tree decoding for state-space and hybrid models by exploiting accumulated state-transition structure. The key difference is the realization contract. For this vLLM/Qwen target, it is not enough to say that the algebraic state for a tree exists. The served verifier must reproduce native-path semantics through fp8/bf16 kernels, branch co-residency, durable state writeback, and rejection sampling.

Algorithm 1: Tree Verification on a GDN Hybrid

Algorithm box: this is the whole served path in paper form. The kernel section then zooms into the GDN scan step.

Inputs: prefix state, candidate tree T, candidate token ids, RNG state
1. Pack T into parent indices, visible/strict masks, path rows, and candidate ids.
2. Run attention layers with FA2 tree bias: each row sees prefix + ancestors only.
3. Run each GDN layer with branch-local scan: H_i = GDN_step(H_parent(i), x_i).
4. Compute verifier probabilities q_i for candidate rows.
5. Device multidraft commit applies the SpecInfer residual rule along T.
6. Replay the accepted path in native order through GDN/conv state.
7. Publish only the accepted-prefix tokens and durable state; discard rejected branch state.

The proof obligation is attached to the outputs of steps 2, 3, and 6. Step 2 must preserve attention ancestry, step 3 must preserve branch-local recurrent state, and step 6 must ensure the next decode event starts from the accepted native-compatible state rather than from a rejected tree row.

The key math relationship is that the tree verifier is not a wider version of native decode. Native MTP has one recurrence chain. The tree verifier has many candidate rows, but each row must be evaluated as if native decode had walked that row's root-to-node path. The FA2 fork solves the attention half of that sentence; the GDN tree scan solves the recurrent-state half.

Kernel and Math

GDN: Gated-DeltaNet is a recurrent layer. It carries a state tensor forward through the sequence.

Native path: the exact token order ordinary decode would have seen. A tree node is valid only if its recurrent state equals the native decode state for that node's branch path.

Qwen 3.6-27B is not an attention-only stack. Its recurrent layers mean that a tree verifier must compute one state per branch path. Sharing a single recurrent accumulator across flattened tree rows is wrong, because sibling rows would inherit state from branches that native decode would never have visited.

The kernel invariant is simple enough to state and hard enough to implement: for every node i, the state S_i used by the verifier must equal the native GDN recurrence evaluated over the tokens on path(root -> i).

GDN recurrence, one value tile
S'_t = exp(g_t) * S_{t-1}
delta_t = beta_t * (v_t - S'_t k_t)
S_t = S'_t + delta_t k_t^T
o_t = S_t q_t
Tree invariant: S(node i) == native_scan(tokens on root-to-i path)

Native decode

There is one chain: S0 -> F(x1) -> S1 -> F(x2) -> S2. The next token always inherits the immediately previous accepted state.

Wrong tree shortcut

A flat packed tree can run rows in parallel, but a shared accumulator makes sibling rows inherit impossible history.

Our tree scan

Each node selects its parent state from h_cache, applies the same rank-1 GDN step, and only the accepted path is replayed into durable state.

Source exhibit fr10_gdn_tree_kernel.py 
# shared by both tree scan and accepted-path replay
state_i *= tl.exp(b_g)
b_v -= tl.sum(state_i * b_k[None, :], axis=1)
b_v *= b_beta
state_i += b_v[:, None] * b_k[None, :]
out_i = tl.sum(state_i * b_q[None, :], axis=1)

The design choice is not a new recurrence. It is the same rank-1 update body, reused in scan and replay, with native-alignment seams gated explicitly.

Figure 3What the GDN tree scan does

The scan verifies the whole candidate tree. The replay route re-executes the accepted chain and publishes durable state. Rejected branches are evidence for the committer, not future model memory.

Why BV and h_cache limit the kernel

BV is the value-channel tile width, called BLOCK_V in the Triton kernel. One program holds a GDN state tile with shape [BV, DIM_K]. A tree scan needs a post-state for every padded node because each child must select its own parent state. That is the h_cache: [N_PAD, BV, DIM_K] in fp32.

This is why native-match geometry does not scale directly. Native decode uses BV32 / num_warps=1 / num_stages=3. A full tree with N_PAD=16 at that geometry would demand about 256KB of fp32 h_cache in one warp, roughly 2048 fp32 registers per lane, which spills. The deployed tree scan uses BV16 / warps=8 / pad16 to fit. Native-alignment experiments use recompute/replay with one [BV, DIM_K] tile instead of caching every node.

The native-alignment seams that mattered were concrete: beta's bf16 round-trip, q/k l2-normalization by division rather than rsqrt, and the carried-state bf16 boundary after the output is computed. Those details sound small, but a tree verifier lives on margins. A one-ULP branch-local difference can become a different accepted prefix after deep recurrent and attention layers amplify it.

Fresh-reader translation

BV is how wide a slice of model memory the kernel handles at once.

h_cache is a table of branch memories. More nodes make the table bigger. If the table is too big, the GPU spills registers into slower memory, and the "correct" kernel stops being fast.

Tree scan pseudocode

  out, state = gdn_node_step(parent_state, token_features[node])
  h_cache[node] = state
commit: replay accepted spine in native order, then publish state

These are not cosmetic differences. They are the explicit places where the served tree verifier can be aligned to the incumbent native packed-decode realization.

How the Kernel Connects to Attention and vLLM

FA2: FlashAttention-2. The attention layers need a tree-aware bias so each row sees exactly the ancestors it should see.

vLLM wiring: the page-level result depends on scheduler metadata, slot mapping, draft packing, sampling, and state publication matching the same tree.

The GDN scan is only one piece. The shipped tree path has to align five surfaces: the candidate tree descriptor, the forked attention kernel, the recurrent scan/replay kernel, the multidraft committer, and the durable state writeback. Most of the engineering effort was chasing cases where one of those surfaces agreed with the shape but disagreed with the path semantics.

Today the candidate tree comes from Qwen's native MTP head: root and spine tokens from the same logits tensor, with runner-up leaves as top-k reads. The verifier should not care whether tomorrow's candidates come from suffix decoding, MTP plus suffix, or another drafter. It should care that the tree has stable parent indices, visible/strict ancestry masks, candidate ids, and accepted-path rows that can be replayed into native state.

The attention side needed its own fork. Default tree attention could add a query-query bias through a generic Triton path, but that path was not the same realization as native FlashAttention-2. The fork instead keeps native FA2 prefill, then routes decode through the FA2 varlen kernel with an explicit tree bias. That gives the tree verifier ancestor visibility without changing the whole attention implementation underneath it.

FA2 fork fr13_patch_fa2_tree_bias.py

B=1: one request stream. This removes co-residency noise that can hide whether the tree itself is faster.

Measurement Infrastructure

OFF speed / ON lossless: speed runs disable heavy probes. Lossless runs enable oracle capture. Mixing them creates fake speed regressions or fake wins.

p-rescore: an offline recurrent-oracle check for the sampled setting. The exact B=1 depth-5 p-rescore is now closed within native floor.

The measurement stack is part of the contribution because several plausible wins were rejected by better instrumentation. The canonical rule is to measure deployment speed with probes off, then measure losslessness with probes on, and never let raw prompt-mode tests replace the real vLLM/Codex deployment path.

The latest correction is a units correction. per_request_decode_tps is useful latency evidence, but it weights every Codex turn equally. The SWE/Codex trace has many short tool-call turns: 24.7% of turns are at most 64 output tokens, but they account for only 3% of output tokens. Throughput is token-weighted by definition, so the paper headline uses total generated decode tokens over total decode time.

s/fwd_gpu = decode_forward_gpu_seconds / pure_decode_drafts
accept/event = accepted_tokens / draft_events
committed/event = accept/event + 1
deploy_TPS = request_decode_tokens / request_decode_seconds
Measurement code fr13_measure.py 
# SPEED and LOSSLESS are SEPARATE boots/numbers.

# LOSSLESS: instrument ON, full-stream q-capture + recurrent oracle.

This is why the paper reports speed and lossless as separate gates. Instrumentation changes the served path, so mixing modes would manufacture the wrong conclusion.

Lossless Evidence and Closure Gates

Lossless does not mean similar text. It means the speculative path preserves the target model distribution, up to native numerical floor.

BV A/B: a scan-only check showing whether different value-tile settings change the branch decision in a controlled regime.

The lossless chase found both numerical and wiring failure modes. A key lesson was that scan-only bit-exactness is not enough. BV A/B showed the scan op itself can be native-stable in a shallow single-forward regime, but live decode also feeds recurrent state through co-resident accepted chains, committer publication, conv prior windows, and deep attention layers.

The exact depth-5 B=1 p-rescore is now closed. Against each arm's own no-spec recurrent oracle, native E5 has 630 clear-margin flips over 4,883 positions, 12.90%; cat9 has 645 over 4,858, 13.28%; cat6root has about 636 over about 4,860, 13.09%. Both tree arms are within the native E5 floor by less than one standard error. The caveat is sample size: this is a 40-turn sample per arm, so the paper treats the result as a clean B=1 closure, not as a universal guarantee for every future batch/concurrency regime.

Failure Library: What Did Not Work

Failure library: not a graveyard. It is the receipt trail for why the final kernel and measurement contract look the way they do.

Most failures were useful because they separated three questions: is the verifier lossless, is the kernel fast, and is the measurement regime honest?

The path to the final verifier was not linear. The important negative results are part of the paper because they prevent the same mistakes from being rediscovered: attention-only fixes, native-looking kernels that spill, lossless gates that measure the wrong frame, and speed screens polluted by concurrency or instrumentation.

Attempt Why It Looked Plausible Why It Failed What Survived
Attention-mask-only tree Transformer tree verifiers mainly need ancestry masking. GDN layers also carry recurrent state. Sibling rows need different histories even when attention is masked correctly. Forked FA2 tree bias remains necessary, but only as one half of the verifier.
Shared packed recurrent accumulator Flattening the tree gives one efficient packed forward. Siblings can inherit state from branches native decode never visited. The branch-local h_cache scan and accepted-chain replay invariant.
STree-style state sharing as a direct transplant STree is the closest published hybrid/SSM tree-decoding regime. Our gate is served native realization, not only algebraic state existence. fp8/bf16 codegen, branch co-residency, and vLLM state publication matter. Use STree as motivation, then add realization-level gates.
WY / whole-tree algebra route It can be mathematically equivalent over real arithmetic and can reduce state traffic. Different summation trees and chunked realization missed the native bit/within-floor target; it was dominated by the sequential replay route for the current deliverable. Parked as a fallback idea; replay's accept-only and spill-free properties were retained.
Literal 0.0 max-abs as the only lossless bar It is easy to audit and sounds rigorous. Native itself has numerical floors. Chasing absolute zero can reject distribution-preserving routes and reward irrelevant kernel identity. The bar moved to recurrent-oracle, clear-margin, within-native-floor evidence.
BV=4 shrink Smaller tiles reduce h_cache pressure. It changes tensor shape and reduction structure, adds many more programs, and does not match native packed decode. Keep deployed BV16/warps8; use recompute/native alignment only when the gate requires it.
Native-match full-tree BV32/w1/s3 It matches the native packed-decode geometry. With N_PAD=16, the full h_cache register footprint spills catastrophically. Native-match remains a correctness probe; deployed scan uses BV16/w8, and recompute removes the full cache.
Multi-spine / copied-state routes Multiple chains can avoid branch-local tree state inside one packed scan. They duplicate KV/state work, do not scale on bandwidth-bound decode, and were closed as non-shippable for this target. The verifier can represent degenerate K-chain descriptors if a future drafter needs them, but the main mechanism stays tree-scan/replay.
cat3w and shallow width probes Shallower trees should reduce recurrent depth and kernel work. They did not recover the depth-5 accept economics and showed width/co-residency can hurt even when leaves are attention-invisible. Depth-5 spine stays important; cat6root trims leaves without giving up the depth-5 spine.
cat10 root-sibling expansion Add one rescue branch to cat9 and maybe improve step-0 rejection. No pad win and no clean speed win versus cat6root; earlier reads were confounded by trajectory and denominators. Root sibling is useful, but the leaner cat6root shape is the cleaner B=1 winner.
OPT-A fp8 GEMV path The lm-head/proposer path looked like a speed lever. Deployment screen showed it was neutral in the current bottleneck regime. Speed focus shifted to metric cleanup and direct phase timing; committer compute itself was later measured near E5.
Per-request TPS as the headline It is a real latency view and matches how many vLLM summaries are read. It weights a short shell-tool turn like a long edit turn, hiding where the generated decode tokens actually sit. Keep per-request TPS as latency evidence, but headline token-weighted decode throughput.
B=4 speed read as the primary verdict Serving wants batches, so B=4 seems more realistic. Effective-concurrency and prefill/decode denominator confounds made cat9 look slower than it was. B=1 isolated the tree mechanism. Use B=1 for clean mechanism attribution, then return to B=4 with the corrected gates.
Raw /v1/completions prompt probes They are quick to run and easy to script. They are off-distribution for the chat/thinking deployment and produced degenerate trajectories. Deployment-regime Codex/SWE measurements became canonical.
Suffix/MTP shortcut before verifier closure Suffix decoding could make drafting cheap and reduce overhead. Without the target verifier, a cheap drafter only produces untrusted candidates. Suffix decoding is now a good future drafter because the verifier boundary exists.

Threats to Validity

Honest scope: the result is strong for clean B=1 decode throughput and losslessness. It does not claim every deployment bottleneck is solved.

Sample

Lossless sample size

The exact cat6/cat9 p-rescore is a 40-turn sample per arm. It closes the clean B=1 table within native floor, with margins under one standard error.

Metric

Decode is not full task wall

The +27% number is decode throughput. SWE/Codex turns are prefill-heavy, and prefix caching is off for this hybrid model, so end-to-end wall gains are smaller.

Batching

B=4 needs refreshed treatment

The clean mechanism result is B=1. B=4 remains a separate deployment gate because co-residency, prefill, and scheduler effects change the measurement surface.

Attribution

Stage D timing is open

Drafter, verify forward, and isolated committer compute are near E5. The remaining live overhead attribution needs direct per-phase B=1 SWE timers.

Canonical Config Appendix

Why include config: for this kind of serving result, the flags are part of the paper. A missing flag can silently move the run onto a different kernel path.

cat6root and cat9 now share one shipped tree-serving configuration. The important per-arm difference is the tree shape: cat9 is a 9-node five-spine-plus-leaves tree; cat6root is a 6-node depth-5 spine with one root sibling. The forked launcher pins the tree verifier path, the FA2 tree-bias decode path, native FA2 prefill, GDN tree mode, and the fixed-row in-projection pad needed for the tree arms.
