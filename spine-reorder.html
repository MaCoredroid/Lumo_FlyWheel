One Bit in the Last Place

Why a Wider Speculative Tree Accepted Fewer Tokens — and the Contiguous-Spine Fix That Restored the Superset

Vol. V closed the correctness frontier and left one honest disappointment as future work: acceptance fell as the tree grew — a six-node tree (cat6) accepted more tokens per forward than the eight-node tree (cat8) that strictly contains it. That is impossible for a superset on matched inputs, so it had to be a bug. This page is the closed case. The disturbance decomposes into three parts — a garble artifact that inflated it 3.4×, ordinary temperature noise, and one genuine residual — and the residual is a single bf16 unit-in-the-last-place, from the forked attention kernel re-associating its online-softmax reduction when branch keys move the spine's columns. A call-site-local contiguous-spine reorder removes it. With the fix baked, the superset holds again: cat8 out-accepts cat6 by exactly the predicted margin.

TL;DR: the “wider tree accepts fewer” anomaly was never one effect. Peel off the garble bug of Vol. V (it had been deflating cat8's clean accept, exaggerating the gap 3.4×: raw 0.296 → true 0.087) and peel off temperature-0.6 trajectory noise (a ±0.25 band across independently-sampled arms), and what remains is a deterministic, greedy-measurable 0.087-token superset violation. Its mechanism is not arithmetic error and not a masking bug: floating-point addition is not associative, and interleaving branch keys places the surviving spine keys in different score-tile columns, changing the butterfly-reduction association tree by one ULP at magnitude eight, in all sixteen full-attention layers. The fix reorders the suffix so the spine keys are contiguous-first — a lossless relabeling, MAB-validated bit-exact vs the spine-only computation. Result on the baked B4 16-task run: the superset is restored, cat8 − cat6 = +0.166 accept/event (predicted +0.17), with a caterpillar 15-node tree (t33333) topping both accept (3.567) and resolve (11/16). The remaining tension is speed, not correctness: the wider trees now out-accept but not yet out-run native per token.

Abstract

A branched token-tree speculative verifier should never accept fewer tokens than a tree it strictly contains: on identical drafts and target logits, the bigger tree offers every path the smaller one does, plus more, so its accepted length is greater than or equal at every forward. Vol. III built such a verifier for Qwen 3.6-27B-FP8, a hybrid whose 64 layers include 48 Gated-DeltaNet recurrent layers; Vol. V made it cache-correct and garble-free, and reported a puzzle it deferred: the eight-node tree cat8 accepted fewer tokens per event than the six-node cat6 it contains. This page resolves that superset violation.

The apparent gap was a composite. Roughly 3.4× of it was an artifact of the very garble bug Vol. V fixed — the foreign-KV read had been over-accepting near-neighbors on cat8 and deflating its clean count, so removing garble shrank the raw 0.296-token gap to 0.087. Most of the rest is trajectory noise: at the deployment temperature of 0.6 each arm samples an independent token stream, and cross-arm accept differences under about a quarter-token are not signal. What survives — the only part measurable without noise, at greedy, where drafts and output are deterministic and the superset test is exact — is a real but small residual of 0.087 tokens per event. We localize it the same way Vol. V localized the garble: overwrite each suspect subsystem with a native-exact version in an observe-only harness. The convolution is bit-invariant to branch count; the input projection is shared; the carrier is the forked FlashAttention-2 tree-verify kernel, which drifts the deepest spine row by exactly one bf16 unit-in-the-last-place at magnitude eight, in all sixteen full-attention layers, as a pure function of how many branches sit beside it.

The mechanism is reduction reassociation, not error. The masked branch keys contribute exactly zero to the spine's score row, but their presence changes the physical column layout, and the kernel's online-softmax reduction is keyed by column; floating-point addition is not associative, so a different association tree sums one ULP away. The fix follows from the mechanism: a call-site-local contiguous-spine reorder permutes the suffix keys, values, and bias so the spine occupies identical columns regardless of branch count — a lossless relabeling, proven bit-exact against the spine-only computation in a multi-armed validation harness. Baked into the locked launcher and re-measured on the sixteen-task deployment run, the superset holds: cat8 out-accepts cat6 by +0.166 accept/event, matching the +0.17 predicted from its two extra branches. We close by reporting the honest remaining tension — the wider trees now accept more but do not yet run faster than native per token — and by scoping the next lever: merging the MTP spine with a real Snowflake Arctic suffix-decoding cache to fill the sixteen-slot register wall with higher-value branches.

The governing invariant (the acceptance bar): for two token trees where one is a subset of the other, the superset must accept ≥ the subset on identical drafts and target logits, at every forward — a structural property of the verify, independent of temperature. A measured violation is therefore a bug, not noise, only when measured on matched inputs: at greedy (deterministic) it is decisive; at temperature it is confounded by trajectory divergence and must be read against the noise band. This page respects that boundary throughout: the defect claim rests on the greedy number; the temperature numbers are confirmation, reported with their band.

Contribution

One diagnosis and one fix, and a methodological point that outlives both. The diagnosis is that a superset-violating acceptance rate, in a system with a known garble bug and a stochastic committer, is three effects wearing one number — and only the greedy, deterministic slice is a real defect. The fix is that the defect is not arithmetic but associative: it is removed by making the reduction see the same column layout, which a contiguous-spine reorder does losslessly, with no kernel math change and no memory-bandwidth tax.

This page is the sequel to Vol. V, whose “branch-on-spine disturbance” future-work section this closes, and is self-contained. Like the prior volumes it is a research report, not an announcement: it records the decomposition, the localization ladder, and a full failure museum of the levers that engaged and missed — a refuted query-pad fix, a fatal double-rounding hybrid, an overstated forward-only throughput, a dead depth lever — because the reason a one-ULP effect took a week to corner is the portable content. The new merge lever — MTP spine plus a real Arctic suffix cache — is scoped in future work, gated but not shipped.

The Anomaly: A Superset That Accepted Less

The invariant: if tree B contains tree A, then on the same drafts and the same target logits, B accepts at least as many tokens as A at every forward — B can always take A's best path, and might take a better one. So B's mean acceptance is ≥ A's on matched inputs. A measured reversal is either a real verify defect or an inputs mismatch.

The two production trees are nested by construction. Written as the set of accepted-path prefixes each admits,

cat8 is a strict superset of cat6: the same depth-5 spine and root sibling, plus two extra branch nodes.

cat8 is cat6 with two sibling branches added at depths 1 and 2. Every path cat6 can accept, cat8 can accept; cat8 additionally offers two more. So on identical drafts and target logits, cat8's accepted length ≥ cat6's at every forward, and its mean acceptance must be ≥ cat6's. That is not a heuristic; it is a property of the branched verify.

The live temperature-0.6 run reported the opposite. In the same-boot three-arm deployment measurement that Vol. V published, the wider tree accepted fewer tokens per event than the narrower one, and was the slowest arm:

cat6 − cat8 = +0.258 in cat6's favor — backwards. If branches only ever add accepts, cat8 would be highest; it was lowest. Something in the wider tree was lowering the acceptance of the very spine it shares with cat6, and the question that opens this page is exactly Vol. V's deferred one: is that a real, structural verify defect, or an artifact of how the measurement was taken?

The measured reversal — the wider tree accepting fewer tokens — is the defect this page decomposes and closes. The catch is the phrase “on matched inputs”: at temperature the two arms never see the same tokens, so the reversal must be re-measured where inputs are matched before it can be called a bug.

Three Effects Wearing One Number

The discipline: a superset violation is decisive only on matched inputs. The temperature run does not match inputs, so before believing any magnitude we split the raw gap into what the garble bug contributed, what trajectory noise contributed, and what survives at greedy — where inputs are matched.

The raw anomaly is not one effect; it is three, and only one of them is a bug. Peeling them apart is the whole diagnostic move.

Effect one: the garble bug had deflated cat8 (~3.4×)

The very corruption Vol. V fixed — the foreign attention-KV read, in which a committed token's key/value came from a sibling branch's slot — did not merely garble identifiers. Because the foreign key was a near-neighbor draft, it also nudged the verify into accepting near-neighbor tokens it should have rejected, and that wrong-accept rate was higher on the busier cat8 layout. The result was a systematic deflation of cat8's clean acceptance. The garble-era measurement put cat6 − cat8 at 0.296; re-measured after the remap, the true greedy gap is 0.087. The garble had exaggerated the disturbance by about 3.4× — the single largest component of the apparent anomaly was an artifact of a bug in a different subsystem.

Effect two: temperature-0.6 trajectory noise (±0.25)

At the deployment temperature of 0.6, every arm samples its own token stream. The moment two arms draw a different token — and the tree, drawing extra masked branch samples, advances its per-request generator differently from native on the very first step — they are on different trajectories, solving the sixteen agentic tasks along divergent paths. Cross-arm acceptance then differs for reasons that have nothing to do with the verify. The size of that noise is not small: the campaign's own working band is ±0.25 tokens per event. Two consequences follow, and both constrain how the results table may be read:

  • The per-task pattern is the tell. Across the sixteen tasks the mean of (cat8 − cat6) was −0.167 with cat8 ahead on only 6 of 16 — a ~2.1σ lean to cat6. But the lean is not uniform: the biggest cat6-favoring gaps land on the failing, meandering tasks (one at −0.83, one at −0.68, one at −0.52), while cleanly-resolved tasks sit near zero (+0.05, +0.07). A real verify defect would be task-independent; a gap that concentrates on divergent trajectories is trajectory divergence.
  • Two of the three arms are not even a clean comparison. native runs the native-MTP drafter on FLASH_ATTN; the trees run the forked tree drafter on TREE_ATTN. There is no subset relationship between native and either tree — different drafter, different attention, different committer path — so native vs cat6 or native vs cat8 carries no superset bound at all. Their accept gaps (native − cat6 = +0.109; cat8 − native = +0.057 on the baked run) sit inside ±0.25 and are not ranked in this paper. The only clean structural comparison in the whole matrix is cat8 vs cat6.

Effect three: the genuine residual (0.087, deterministic)

Strip both confounds by measuring where they cannot exist. At greedy — temperature 0 — drafts are deterministic and the target is deterministic, so cat8 and cat6 produce the same output; the tree only changes how many tokens commit per forward. There is no trajectory noise, and there is no garble (the remap is on). On a fixed prompt, same boot era:

The Mechanism: One ULP of Reassociation

The claim in one line: the masked-out branch keys contribute exactly zero to the spine's attention, and still change its answer — because they change the order in which the kernel sums a non-associative reduction, not any value in it.

The method: the same localization ladder Vol. V used for the garble — overwrite each candidate subsystem with a native-exact version in an observe-only harness, and watch which one moves the drift to zero.

With the confounds gone, the residual is 0.087 tokens per event at greedy, and it is deterministic, so it has a single physical cause. We find it by the ladder. In an observe-only multi-armed harness that overwrites one subsystem at a time with a native-exact computation, each Gated-DeltaNet subsystem is cleared in turn, and one is not.

In-projection

Full attention (FA2)

The carrier is the forked FlashAttention-2 tree-verify kernel, and the drift is one bf16 unit-in-the-last-place — 6.25e-2 at magnitude eight — on the deepest spine row, present in all sixteen full-attention layers and scaling with node count. That number is a fingerprint: a single ULP, not a growing error, and monotone in M — a codegen or precision fault would be non-monotone and larger. It says reassociation, and the source read confirms it exactly.

Why the branch keys move the sum without being in it

The obvious first suspect is masking — maybe the extra branch keys leak into the spine's score row. They do not: a masked key is exponentiated through exp2(−∞) = 0, an exact zero, and the served output on the widest arm matches the model bit-for-bit. The branch keys contribute exactly nothing to the value. What they change is where the spine keys sit. FlashAttention-2 computes its softmax as an online reduction whose association order is keyed by the physical score-tile column — a lane butterfly feeds a fixed four-way reduction tree, so which column a key lands in decides which partial sums it joins, and in what order. Interleaving branch nodes with spine nodes in the tree's breadth-first layout slides the surviving spine keys into different columns:

Figure 2Same keys, same values, different columns — so the online-softmax butterfly sums them in a different order, one ULP apart

Figure 2 is the whole defect. The spine keys and their values are identical between the two layouts; the masked branch keys contribute exact zero. The only difference is column placement — contiguous {0,1,2,3,4} versus gapped {0,1,2,4,6} — and because the online-softmax reduction associates by column, the deep-spine partial sums in a different order and lands one bf16 ULP away. At an acceptance near-tie, one ULP is enough to reject a token the narrower tree accepts, which is the 0.087 residual.

This also explains why every padding fix failed before the reorder (they are in the museum). The kernel anchors both its bias-column window and its causal diagonal to a derived length — the key length minus the query length — so padding the query moves the tile but not the columns (query padding was measured to have exactly zero effect on the cross-M drift), and padding the key width slides the anchor and corrupts the real rows. The carrier is the key/suffix width, and the only compute-only lever that touches it without desyncing the anchor is to reorder the keys themselves.

The Fix: Make the Spine Columns Fixed

The remedy the mechanism dictates: if the drift comes from the spine keys landing in branch-count-dependent columns, put them in the same columns every time. Permute the suffix so the spine is contiguous-first and the branches follow — a relabeling, with no arithmetic changed.

The mechanism names the fix. Make the surviving spine keys occupy identical columns regardless of how many branches sit beside them, and the reduction associates the same way for every tree, so the drift is gone by construction. Concretely, permute the tree suffix so the spine comes first in depth order and the branches follow: π = [spine depths] ++ [branches topological]. It is a lossless relabeling — the masked branch columns stay neutral, no value changes — and it carries no memory-bandwidth tax. In the observe-only harness it is provably exact: under the reorder, every spine depth becomes bit-identical to the spine-only computation (whole-spine difference 0.000e+00), while an interleaved-identity control stays at the one-ULP drift — confirming that contiguity itself, not the permutation, is the property that matters.

Figure 3Reorder the suffix spine-first, so the spine keys occupy the same columns for every tree width

Figure 3 is the fix. The permutation moves the five spine nodes to the front so they always occupy columns 0–4, whatever the branch count, and the branches follow. Because the reduction associates by column and the spine columns are now fixed, the deep-spine sum is bit-identical to the spine-only computation. It is a relabeling of where keys sit, not a change to what they are, so it is lossless by construction.

Landing it: two layers, one survivor

The reorder is abstract; where in the stack to apply it is the engineering problem, and the two obvious call-local routes both died on the same rock. Splitting the attention into a paged context pass plus a dense spine-first suffix pass and merging the two (FR13_FA2_SPINE_REORDER) re-quantizes each partial to bf16 separately and then again at the merge — a one-ULP double-rounding that the attention API cannot avoid, because it will not return fp32 partials, and that is fatal for speculative decode: it went degenerate at greedy, the very regime that is supposed to hide error. A two-K-source fused kernel that reads context then suffix in a single pass fares no better — a CPU model refuted it before any recompile, because introducing a second key block perturbs the context by the same one ULP from online-softmax rescale timing. Both are in the museum; both merely relocate the bit.

The route that ships avoids a second pass entirely. Instead of splitting the kernel, permute the KV cache slot mapping so the tree suffix is written spine-first; then a single fused paged attention call reads the spine contiguously and naturally, the context stays bit-identical, and there is no merge to double-round and no recompile. That is FR13_SLOT_REORDER, baked into the locked launcher after a four-arm campaign. It is not a kernel-math change; it is data placement, and it interacts with exactly the concurrency surface this series has been about — the cache slots the committer and the recurrent path read later — so it shipped only after an audit proved that surface safe.

The carrier-B audit and the five edits

Permuting cache slots is only safe if nothing else reads those slots positionally in a way the permutation breaks. The audit found two disjoint address spaces and confirmed the permutation threads through both: the attention KV addressed by the slot map, and the Gated-DeltaNet conv/SSM state addressed by a separate mamba bank that the reorder never touches. The rejection committer is node- and token-indexed, invariant to a slot permutation; the drafter is invisible to it because the reorder keeps the breadth-first node numbering and only moves the physical slots — the crux that distinguishes it from an earlier global-tree reorder that renumbered nodes and broke the drafter. The audit sized the change at three edits; a red-team pass added two more for hazards it missed, giving five:

The five edit sites of FR13_SLOT_REORDER — all Python, no kernel recompile.
#EditWhat it does
1PermuteIn-place spine-first permutation of the persistent slot buffer (pointer-stable for the full cudagraph).
2BiasPermute the tree-attention bias on its key axis once, to match the reordered keys.
3Committer destination“The one real edit” — the committed leaf's destination slot must be the flat linear slot, not the permuted one, or the committed prefix scatters. A genuine correctness dependency.
4RestoreUn-permute the stashed slot spans after the last verify-side consumer and before the drafter proposes, so the drafter sees canonical order.
5Causal offSet the decode tree call non-causal — provably redundant here (the tree bias already encodes causality), which is byte-identical and unlocks an arbitrary suffix layout.

The reorder requires the attention-KV remap of Vol. V to be on — the launcher refuses to enable one without the other — because the committed-destination edit sits inside the same re-linearizer. Validated end to end, the delivered fix reproduces the harness result in-process: the whole reordered spine is bit-exact against the spine-only computation, and the fix magnitude on the deep node is exactly the one ULP it was built to remove.

Results: The Superset Restored

The honest speed reading: out-accepts, does not yet out-run

Restoring the superset fixed acceptance; it did not, on this hardware and workload, make the tree faster than native per token. On the forward-limited GPU ceiling — committed tokens over verify-forward GPU time, the most generous basis for the tree — native leads at 76.3 tok/s, with cat6 at 72.7, cat8 at 70.6, and t33333 at 56.1. Acceptance rises with tree width; forward cost rises faster. The drafter and verify of a fifteen-node tree cost more per step (ms/draft 93.1 versus native's 59.3) than its extra accepts pay back, so the widest tree, despite the highest acceptance, has the lowest throughput. This is the same shape Vol. V measured under a different lens and is stated the same way here: the tree's advantage is an acceptance advantage, and turning acceptance into wall-clock throughput is a per-forward-overhead problem the accept gain has not yet closed.

Two cautions on that throughput column, both inherited and both kept. First, derived TPS is a ceiling, not a wall clock: it charges only the GPU forward, omitting the drafter, the rejection committer, and the remap — the very per-step overhead that most separates the tree from native — so the true end-to-end gap is at least this wide, not narrower. Second, the honest comparand for “is the tree worth it” is a clean end-to-end wall-clock A/B at B=1, which is scoped but not the subject of this page; here the claim is only the one the greedy and the baked runs jointly support — the superset is restored and correctness holds, and the speed lever now moves to lifting acceptance without adding forward cost, which is the merge in future work.

Failure Museum

Not a graveyard: the eventual fix came from the mechanism, and the mechanism came from the failures. Every refuted lever narrowed the carrier or killed a landing route; the map is the dead ends.

The through-line: almost every wrong turn was a one-sided confound or a broken test — garble deflating one arm, a padding convention corrupting the rows it measured, a forward-only metric reading a wall as a ceiling.

Thirteen hypotheses and levers were refuted across the disturbance hunt and the drafter-speed campaign that framed it. They cluster into four families: attempts to believe the anomaly's magnitude before the confounds were stripped; attempts to locate the carrier; attempts to land the reorder in the live kernel; and the parallel speed levers that were measured-refuted around the accept fix. The ledger records what made each look right and what killed it.

Family A — believing the anomaly before stripping the confounds.

“cat6 is faster than cat8” — the raw 0.296 gap

contaminated

Why it looked right: the live aggregate had cat8 at 3.336 and cat6 at 3.594, and the first controlled greedy A/B seemed to confirm it hard — cat8 3.368 vs cat6 3.664, a 0.296 gap, and greedy is deterministic, so it reads as the clean superset test. A 0.296 violation of a set-theoretic bound looks like a large, real defect.

  • What killed it: that controlled run had the attention-KV remap off — both trees were garbling, and the wrong-accepts deflated cat8 specifically. Re-run clean (remap verified engaged), the greedy gap is 0.087; the confound had exaggerated the true effect by 3.4×. The live 3.594 was later shown to be structurally-impossible trajectory noise (the matched post-fix cat6 is 3.333).

Lesson: a dramatic deterministic number is worthless if a correctness flag silently flipped the arm under test; check the engagement log before trusting the delta, because a one-sided confound can manufacture a 3.4× exaggeration out of a real-but-small effect.

The per-task cat6 lean (−0.167 mean, 2.1σ)

contaminated

Why it looked right: across the same sixteen tasks, the mean of (cat8 − cat6) was −0.167 and cat8 won on only 6 of 16 — a ~2.1σ lean to cat6. A uniform verify defect would produce exactly this systematic pattern.

  • What killed it: per-task at temperature is not matched — the arms diverge within a task once any token differs. The tell is the distribution: the biggest cat6-favoring gaps land on the failing, meandering tasks (−0.83, −0.68, −0.52) while cleanly-resolved tasks sit near zero (+0.05, +0.07). A real M-dependent defect is task-independent; concentration on diverging trajectories is noise.

Lesson: “systematic across N tasks” is not “matched”; when an effect concentrates on the runs that were already diverging, you are measuring trajectory spread, not the mechanism.

“The shared spine is M-invariant, so the bound must hold”

superseded

Why it looked right: pure set theory — cat8 offers every cat6 path plus two, so on identical inputs its accepted length is ≥ cat6's. The working premise was that the spine verify is M-invariant: cat8's spine equals cat6's equals native's.

  • What killed it: the greedy matched test violated the bound by 0.087, which is impossible if the spine were M-invariant. A direct pure-spine measurement at B=1 confirmed it: cat6's spine out-accepts cat8's by ~0.29 clean — the two extra branches earn +0.167 per forward, which almost exactly cancels cat8's larger-M spine perturbation. The premise “spine == native” is false; adding branches perturbs the shared spine's numerics.

Lesson: a set-theoretic bound on outputs does not bound a floating-point accept count when enlarging the set perturbs the numerics of the nodes it shares — superset ⇒ ≥ accept holds in exact arithmetic and fails at the ULP.

Family B — locating the carrier.

“The FA2 query-tile is the carrier”

superseded

Why it looked right: the forked FA2 decode keys its tile predication off the query length (6 vs 8), and the multi-armed replay returned M-dependent with a clean fingerprint — 6.25e-2, one bf16 ULP, in all sixteen full-attention layers, monotone in node count. Named, on-device, reproducible; it looked airtight.

  • What killed it (twice): in the garble era a first-nonzero ladder put the earliest divergence at a recurrent layer upstream of the first full-attention layer — a fix downstream cannot remove an error already born earlier. And in the accept era, granting FA2 is where the M-dependence shows, the fix-axis was still wrong: a front-pad test proved the carrier is the key/suffix width, not the query tile.

Lesson: “layer L is M-dependent” is not “layer L is the carrier” — trace divergence to its first-nonzero origin, because a real downstream ULP wiggle will happily masquerade as the root cause.

Re-landing the query-pad fix (QPAD)

settled

Why it looked right: query-padding to a fixed tile makes occupancy M-invariant and is lossless by construction (a CPU oracle read 0.0 across every M and precision). A spine-M-dependence localizer even recommended re-landing it after reading the “built” comment in the source — a pre-built, lossless, named fix for the confirmed carrier.

  • What killed it: the commits that followed its build already refuted it — QPAD zeroed the named carrier layer but left the end-to-end flip count unchanged and dropped accept below the native floor, and a later commit explicitly rejected re-landing it. The definitive cat8 refutation: a valid front-pad self-check showed the cross-M drift stays 6.25e-2 at every pad width, identical to unpadded. Query padding has zero effect.

Lesson: before re-landing a “built but not merged” fix, read the commits after its build — a source comment says it exists, not that it worked; and when a padding test refutes a lever, run the same-M self-check first, because the padding convention itself can corrupt the rows you measure.

Key-width padding (dummy −∞ suffix keys)

settled

Why it looked right: if the carrier is suffix width, pad every tree's suffix to a fixed width with negative-infinity dummy keys so both arms run the same block iteration — M-invariant, near-zero bandwidth tax. A clean mechanistic follow-on to the query-pad refutation.

  • What killed it: the same-M self-check was 0.82 typical and 16.3 worst — the dummy keys are not math-neutral in the forked kernel. The reason, from a source read: the kernel anchors both its bias-column window and its causal diagonal to a derived length (key length minus query length), so raising the key length without matching the query length slides the anchor and the real keys lose their mask. Holding the anchor means padding the query too — which is QPAD, already dead.

Lesson: a “just pad it wider” fix assumes the padded region is inert; in a fused kernel the mask geometry is often anchored to a derived length, so padding one dimension silently desyncs the other. Prove your dummy elements are neutral with a same-M self-check first.

Family C — landing the reorder in the live kernel.

Dense-suffix hybrid (split context + suffix, then merge)

settled

Why it looked right: to get the spine keys into contiguous columns without a recompile, split the attention into a paged context call and a dense spine-first suffix call and combine them with the shipped merge kernel — reusing tested cascade infrastructure, with the reorder itself already proven bit-exact.

  • What killed it: the split double-rounds. A single call accumulates in fp32 and rounds to bf16 once; the split rounds each partial separately and then again at the merge — ~1 ULP relative on every forward. The fp32-partial rescue is refused by the API (the attention op requires the output dtype to equal the query dtype), so double-rounding is fundamental to any two-pass merge. And one ULP is fatal for speculative decode: the split-driven path went degenerate at greedy, inflating accept on looping garbage — the regime that is supposed to hide error.

Lesson: splitting one fused reduction into two passes plus a merge re-quantizes each partial independently, and the merge cannot un-round what the halves already lost; in speculative decode a single ULP of wrong-accept compounds into degenerate output at greedy.

Two-K-source fused kernel (one pass, two key blocks)

settled

Why it looked right: after the split double-rounds, avoid the merge — modify the vendored kernel to read two key sources in one online-softmax pass (paged context, then dense spine-first suffix), single accumulator, one rounding, no merge. Backed by a research pass confirming the reduction is column-keyed, so context “should” be untouched.

  • What killed it: a CPU model with a realistic unaligned block showed that reading the suffix as a separate block perturbs the context by ~1 ULP for every row — the same magnitude as the double-round — purely from online-softmax rescale timing. It relocates the bit from the merge to the block boundary; it does not remove it. Refuted before spending a GPU recompile.

Lesson: “single pass, one accumulator” does not guarantee bit-identity when the pass has a block boundary — rescale timing depends on block structure, so any new block edge pays a rescale-timing ULP. Model the realistic, deployed block layout on CPU before committing a recompile.

Family D — the drafter-speed levers, measured and refuted.

“The tree is at throughput parity” (forward-only ceiling)

contaminated

Why it looked right: the forward-limited GPU throughput read the tree at parity with native, and the tree's verify-forward is actually cheaper per token (accept plus amortized drafts spread the weight read). By that metric the branches cost nothing.

  • What killed it: the metric charges only the verify forward — a ceiling, blind to drafter, committer, and scheduler gaps. Real wall clock is the opposite: the tree is ~12% slower per committed token, and 100% of the deficit is non-forward host overhead; the ceiling reads 64–72 where the real wall throughput is 15–17. A single-prompt probe even manufactured a phantom native win by saturating the chain drafter.

Lesson: a forward-only throughput metric is a ceiling, not a speed — when the regression lives entirely in non-forward host overhead, the ceiling reads at parity while the wall is slower; speed verdicts belong on matched live runs.

The depth lever (go deeper for free drafter savings)

superseded

Why it looked right: if the drafter ran one sequential call per spine level, a shallower-wider tree would cut drafter cost roughly linearly with depth, and a calibrated shape model ranked a deeper spine highest on acceptance.

  • What killed it: path-map elimination showed the fork drafts the tree in one parallel pass, so depth buys no drafter savings; and the shape model found the shipped tree near-optimal within depth five, the best deeper variant a wash. The deeper-spine ranking lived entirely in an unmeasured tail-probability extrapolation.

Lesson (with a twist): don't cost a lever against an assumed execution model — and note the “parallel drafting” premise that killed this lever was itself later corrected: the spine runs sequential forwards, “parallel” was only ever true of the branches. That correction is what reopened the speed frontier (Family D's last card).

FR-Spec: truncate the draft vocabulary

settled

Why it looked right: a dimensional decomposition made the shared output-projection read 83% of the per-level draft weight, paid four times; a truncated draft vocab would cut ~8.8 GB per step for a lossless ~+7% — the top-ranked drafter lever, since the rejection sampler commits target-correct tokens regardless of the draft set.

  • What killed it: direct GPU-event spans showed the drafter is host-bound, not bandwidth-bound — 23 ms of GPU compute inside a 140 ms step, the other 117 ms host orchestration. The output projection is 11% of the wall; halving it buys ~2%. The whole HBM ceiling assumed a weight read that isn't on the critical path.

Lesson: an HBM-bandwidth ceiling computed from weight dimensions is a fiction until you measure GPU-busy versus GPU-idle; if most of the step is host orchestration, the biggest weight read is still a small slice of the wall.

“The 16-node cap is a soft warmup guard”

superseded

Why it looked right: a B=1 sweep looked smooth and cliff-free — nine nodes 131 ms, sixteen nodes 145 ms, ~2 ms per row, accept rising with width — and the cap traced to a guard that reads like a warmup convenience. A prior pass even “verified” no SRAM spill by reading the stock recurrent kernel.

  • What killed it: the wrong kernel was read. The actual tree verifier holds a register-resident cache of all padded node states — 128 KB per block at sixteen nodes, half the register file; thirty-two nodes is the whole file and spills to HBM. The “smooth” sweep never crossed the boundary: both arms round to a padded width of sixteen, so the delta was unmasked nodes inside the same tile. A twenty-six-node tree boot-fails at engine init, below the separate tile boundary the alternative blamed.

Lesson: “no cliff in the sweep” can mean the sweep never crossed the boundary — a padded quantity hides the real step; and verify which kernel actually runs before reasoning about its register footprint.

“The drafter host gap is structural — earned cost-gate”

superseded

Why it looked right: after the committer, shape, drafter-model, and vocab levers were all measured-refuted, the campaign honestly declared the remaining ~12% wall gap structural — the 117 ms host cost is the drafter's per-step orchestration, and closing it looked like a weeks-long framework change. It banked the accept fix and closed the ledger.

  • What killed it: a later probe measured that the host cost is ~19 ms per spine level, not a fixed setup — so shortening the spine loop shortens it proportionally. Drafting one level instead of four projects a −53% drafter and ~−18% decode, a lever the campaign never tried because it held tree shape fixed. The “structural” verdict closed the levers it had enumerated, not the one it hadn't thought to vary.

Lesson: “structural” is a claim about the lever space you searched — a host-orchestration cost is only structural if the orchestration is fixed; if it scales per step, a lever that changes the step count you held constant can still move it. That reopened lever is the merge in future work.

Reflection: Why One Bit Took a Week

Worth stating plainly: the defect was 6.25e-2 — one bf16 ULP — and the fix, once localized, is a permutation with no math in it. Almost the entire cost was in believing there was a bug at all, then measuring it where it could not hide. Both steps fought the same enemy: a number that was really three numbers.

The disturbance resisted for a structural reason, not a difficulty reason: the quantity everyone was staring at — a superset accepting less — was a sum of a garble artifact, a noise band, and a genuine bit, and any two of the three could flip its sign. Chase the raw temperature number and it is 0.258 one week and 0.19 the next; attribute that swing to the fix under test and you have manufactured a result. The move that broke it was refusing to measure at temperature at all until the confounds were gone: greedy makes drafts and output deterministic, which collapses the noise band to zero and exposes the one part that is a real, matched-input violation. Only then is 0.087 a fact rather than a mood.

Threats to Validity

Honest scope: the correctness claim is settled — the superset is restored, deterministically at greedy and on the baked run — and the committed tokens are unchanged (the reorder is a relabeling). The open items are all speed, and the widest-tree win is a single sample.

Accept, not wall-clock

Restored acceptance is not yet restored throughput

The fix makes the wider tree accept more, as a superset must; it does not make the tree out-run native per token. On the forward-limited ceiling native still leads, because the wider verify's per-forward cost outruns the accept gain. The clean end-to-end wall-clock A/B at B=1 is the comparison that would settle “is the tree worth it,” and it is not this page.

One sample

t33333's 11/16 is a standout, not a ranking

The fifteen-node caterpillar tops both acceptance and resolve, two tasks above the others. It is one run per cell at temperature 0.6, inside the same noise band as everything else; it is reported as a promising lead for the merge below, not as an established “wider is better” ordering.

The branch half

The reorder fixes the spine exactly, the branches only partly

Making the spine keys column-contiguous is bit-exact for the spine, but a branch's own column still moves with its co-resident siblings, so the deepest, rarest branch still shifts about one ULP. The effect is concentrated where it is least sampled, so its speed cost is small, but a fully canonical layout — fixed columns for branches as well — is what a complete fix would need.

Delivery route

One route shipped; two others walled

The mechanism admits more than one landing, and only one survived. The cache-slot reorder ships baked (FR13_SLOT_REORDER) after its carrier-B audit — a single fused paged call keeps the context bit-identical. The two call-local alternatives — a dense-suffix split-and-merge and a two-K-source fused kernel — each hit a fundamental one-ULP double-rounding wall (museum) and are dead. The branch-complete variant is still open work.

Future Work: Suffix Decoding Merged With MTP

Status: designed, seam located, three correctness gates passed on CPU; no serving code edited. The one open gate is a live A/B, and the flags default to the current byte-identical behavior.

The link to the results: the fifteen-node caterpillar that topped both accept and resolve above is exactly this design's target geometry — the merge is a bet that we can fill its branch slots with better tokens than the MTP head drafts today.

Restoring the superset settled correctness and left the honest speed tension: the wider trees out-accept but do not out-run native per token, because acceptance rises with width and per-forward cost rises faster. The next lever attacks acceptance and drafter cost together, without widening the tree past the sixteen-node register wall. The idea is to keep the model's own confident near predictions from its multi-token-prediction head, but replace the weak deep draft tokens — the ones the MTP head is least sure of — with retrieved historical continuations from a real Snowflake Arctic suffix-decoding cache, and assemble both into the same fifteen-node caterpillar tree that feeds our proven-lossless committer.

Figure 4MTP drafts the confident near tokens; Arctic retrieves the deep spine and branch alternatives; our committer verifies both

Figure 4 is the merged drafter. The MTP head drafts the shallow, confident spine; Arctic retrieves the deep spine and the branch alternatives from the request's own history; both assemble into the sixteen-node caterpillar and feed our committer, which is verified to output exactly the target distribution regardless of what the sources propose. On cold context the assembly falls back to the pure-MTP tree byte-for-byte, so the merge can only ever add.

Why it is the right lever

Two things make this the axis to push rather than a wider tree. First, acceptance is the one lever the speed campaign did not exhaust. Every cheap drafter-cost lever was measured-refuted (the museum), and widening the tree is blocked by the sixteen-node register wall — the verifier holds all padded node states in registers, so thirty-two nodes spills to HBM. So the win has to come from putting better tokens in the sixteen slots we already have, and a suffix cache does exactly that on agentic coding workloads, which are dense with repetition — re-read files, repeated identifiers, boilerplate paths — where a retrieved continuation is both high-acceptance and free of any forward. Second, the deep spine is where the MTP head is weakest and Arctic is strongest, so the swap is targeted: keep the near tokens the head is confident about, retrieve the far ones it is guessing at.

The speed half is a measured premise, not a hope. The drafter's spine is not one parallel pass — it runs one sequential model forward per spine level, at ~19 ms of host-orchestrated cost each. Drafting only the first level with the MTP head and filling the deep spine from Arctic's host-side lookup skips the rest: a projected −53% on the drafter and ~−18% on the decode step, for a plausible ~+22% throughput — if acceptance holds. That conditional is the whole bet, and it is the open gate.

Why it cannot regress: the committer contract

The reason this is a pure-upside bet rather than a risk is the committer, and it was proven before any of it was built. Against the exact deployment rejection rule, four properties hold over analytic and Monte-Carlo checks: the output distribution is exactly the target for any candidate set — adding suffix candidates, or even garbage, never changes what commits; acceptance equals the target mass on the distinct candidate set and is monotone — a real candidate can only raise it, which is the speed-win mechanism; a garbage token commits at exactly its own near-zero target probability, so suffix decoding carries zero garble risk by the committer math; and the whole thing is deterministic. Because that contract is source-agnostic, it survived the pivot from a hand-rolled n-gram cache to the real Arctic cache unchanged — only the source swaps, never the guarantee.
