# Proposed GDN Tree-Scan v2

Prepared 2026-09-21. This is a proposal for revising the existing preprint, not a new experimental result or a revised manuscript.

## Recommendation

**Suggested title: GDN Tree-Scan: Correct State Commitment and Performance Limits of Tree Speculation in Recurrent Hybrids.**

The strongest v2 connects three things the existing work already documents: the state a served tree verifier must OKpreserve, numerical failures that survive an apparently correct ancestry mask, and the conditions under which additional accepted tokens repay the complete serving cost. Retain the original implementation and its narrowly scoped June B1 observation, then replace its now-outdated list of future work with the later evidence.

This should be a coherent systems paper with a small set of reproducible results. The eleven report volumes are the supporting archive, not eleven sections of the paper. My assessment is that they contain enough material for a substantial revision without another broad kernel search. A new claim that the *current optimized system* beats native MTP still needs a matched current experiment.

The proposed three contributions are:

1. **A complete accepted-prefix state contract and its regression witnesses.** GDN recurrent state, convolution history, attention KV entries, and cache restoration must all represent the selected prefix. Rejection sampling must then use the intended target probabilities. Show concrete failures and repairs across this boundary.
2. **A finite-precision layout failure and a scoped repair.** Explain how adding masked tree positions changed the attention reduction order on the shared spine; show the fixed-layout repair and the recovered acceptance opportunity. Limit byte-exact claims to the paths and configurations actually checked.
3. **A measured account of acceptance versus serving cost.** Separate drafting, verification, commitment, host work, batching, and cache effects. Include both the later chain advantage and the independently measured B4 attention improvement. Treat the unsuccessful optimizations as causal evidence, not as a universal lower bound on tree decoding.

## Results already available

### State integrity and numerical behavior

The original paper explains why attention ancestry alone is insufficient. The later work makes that argument much more concrete:

- Accepted-path publication must cover **both recurrent/convolution state and attention KV**. A correct recurrent commit can still leave a sibling's KV entry in the continuation path. The remap report records a token fixture moving from 15/15 failures to 0/15, and served script checks with 0/84 cat8 and 0/61 cat6 garble observations after the repairs. These are observed regression outcomes, not a general distribution-equivalence proof. See [FR13_REMAP_SHIP_RESULTS.md](../../../FR13_REMAP_SHIP_RESULTS.md).
- The durable state should represent the accepted prefix; rejected state must be unobservable by future computation. Do not make mandatory memory zeroing part of the mathematical contract: later analysis found some burn/zero operations redundant once the readers were controlled.
- The wider-tree acceptance problem had several causes, including a deterministic layout effect. Masked positions changed the online-softmax reduction association. Fixing the physical spine layout removed the measured shared-spine discrepancy. In the recorded B4 comparison, cat8 accepted 3.4996 drafts/event versus cat6's 3.3332, recovering a 0.1664 advantage. See [slot-reorder verdicts](../../../FR13_SLOT_REORDER_ARTIFACTS/VERDICT_TABLE.md).

The paper should distinguish four different claims: algebraic equivalence; numerical agreement with a chosen implementation; sampler correctness given its probabilities; and deployed output-distribution or task-quality agreement. Success at one does not automatically establish the others.

### Performance: keep the generations and denominators separate

The existing manuscript reports a June B1 result of 23.88 versus 18.80 token-weighted request-decode tokens/s, with a smaller per-request-equal improvement of 18.51 versus 17.80. This is a historical, configuration-specific observation. It is not a measurement of the current tree stack, an end-to-end task speedup, or the same metric as the later table below. The sampling provenance audit described below is required before reusing its temperature label.

The later postfix3 campaign already includes the important depth-matched control. Do **not** propose MTP-11 or B4 as if they have never been run:

| --- | ---: | ---: | ---: | ---: | ---: |
| Native MTP-5 | 3.422 | 4.422 | 103.45 ms | 42.74 | 10/16 |
| Native MTP-11 | 4.923 | 5.923 | 148.28 ms | 39.95 | 8/16 |
| Tree, tail6 | 4.286 | 5.286 | 160.88 ms | 32.85 | 10/16 |

Sources: [campaign closeout](../../../FR13_POSTSNAPFIX3_CLOSEOUT.md) and corrected raw JSON for [native MTP-5](../../../output/fr13_kvremap_tail6/native5_control_kvr1/deploy_speed_kvr1.json), [native MTP-11](../../../output/fr13_kvremap_tail6/native11_control_kvr1/deploy_speed_kvr1.json), and [tree](../../../output/fr13_kvremap_tail6/kvremap_tail6_kvr1/deploy_speed_kvr1.json).

These time values normalize complete physical-step costs by request verification events. The realized events/step were approximately 2.79, 2.74, and 2.80 respectively, not four throughout. The tokens/s column is consequently a decode-step accounting metric, not aggregate output divided by the full campaign wall clock. Cache, prefill, request latency, and task wall time need separate reporting. Equal 10/16 outcomes do not prove quality equivalence.

The useful conclusion is that extra tree acceptance did not pay for this implementation's extra cost in this campaign. Native MTP-11 also accepted more drafts than the tree. A blanket explanation that tree depth alone would reverse the result is unsupported.

There is also a positive later optimization worth retaining: B4 FA2 query-head pairing reduced the measured step time from 408.313 to 381.284 ms, **27.03 ms / 6.6%**, across four paired passes in its own configuration. Its mechanism is better use of the query tile. It is a local implementation improvement, not evidence that the resulting tree beats native MTP. The [August closeout](../../../results/fr13_series_closeout_20260815/README.md) distinguishes this result from the still-unsealed approximately 8.98 ms single-pass scan improvement and the unpriced batched tree-accept walk.

### Corrections to make before writing v2

1. **Correct the break-even arithmetic.** For ordinary nonterminal verification events, committed tokens are accepted drafts plus the correction/bonus token. Using the raw postfix3 values, the conditional break-even equation is

   `A_tree_required = (A_native + 1) * T_tree / T_native - 1`.

   This gives **5.8766 accepted drafts/event**, not approximately 5.3, at the historical 160.879 ms event-normalized cost. Alternatively, at the observed tree acceptance, cost must fall to approximately **123.658 ms/event**, a **23.1% reduction**. This is a calculation at fixed comparison conditions, not a prediction that acceptance can rise without changing cost. Use actual committed-token counts for EOS and other boundary events. See the historical [break-even note](../../../FR13_TREE_THROUGHPUT_BREAKEVEN.md).

2. **Retire the outdated timing-mismatch warning.** The blog still describes an approximately 0.53 GPU/wall alignment problem. The stored JSON includes the July 22 correction for physical-step versus per-request-event normalization. Its current GPU-derived/wall ratios are 1.0169 for tree, 1.0253 for MTP-5, and 1.0153 for MTP-11. Reuse this correction; there is no reason to commission another experiment solely to resolve the old discrepancy.

3. **Audit effective sampling parameters.** Volume VIII documents a double-temperature application: nominal 0.6 became effective 0.36 on an affected path. Trace each proposed paper row to the actual code, flags, and sampling path before labeling it. Do not assume either that all historical rows were affected or that the original manuscript's label is safe.

4. **Keep withdrawn measurements withdrawn.** Do not use the profiler-induced graph gap, obsolete host-tail estimates, the counterfactual floor labeled non-citable, or a sum of separately observed optimization wins. Use Volume X's corrections over earlier narrative claims.

5. **Bound quality claims.** The historical 21-arm summary covers the same 16 Astropy tasks; seven always resolved, four never resolved, and five varied. These are neither 21 independent replications of one configuration nor a diverse 16-repository benchmark. NVFP4 reports also disclose a gold-patch retrieval through external networking. Audit provenance before using affected task outcomes. See [quality audit](../../../results/fr13_b4_exact16_qc_20260814/fr13_b4_exact16_qc.json) and [NVFP4 campaign](../../../results/fr14_nvfp4_port_20260816/promotion_ab_campaign.md).

## Related work changes the claim

[Bole](https://arxiv.org/html/2608.01651v1), posted August 3, directly addresses parallel GDN tree verification, factorized speculative states, accepted-state reconstruction, and SGLang integration. Its evaluation includes **27B on GB10**, although with unquantized weights. It also evaluates serving through replayed agent traces. This overlap is substantial: hardware alone and the generic ability to serve hybrid token trees cannot distinguish v2. Its alternative state representation also means our replay costs cannot establish a lower bound for all implementations.

[TreeWY](https://arxiv.org/html/2608.20961v1), posted August 21, provides another direct GDN tree verifier using WY reconstruction. It evaluates greedy decoding and explicitly distinguishes algebraic equivalence from finite-precision identity. Our stricter shared-spine checks do not establish that its implementation is incorrect.

The [ReplaySSM RFC](https://github.com/vllm-project/vllm/issues/47572) also covers input caching and recurrent-state reconstruction for standard and speculative decoding. The fact of replay itself is not a new contribution.

Rewrite the original paper's related-work table and “not aware of a prior public served implementation” language. The defensible emphasis is the particular numerical and lifecycle failures, reproducible witnesses and repairs, and carefully bounded live-serving evidence. This is a proposed positioning, not a verified claim that no prior work studies any of those individual issues. Preserve implementation chronology through commit dates without substituting private development dates for public priority.

## Additional work I would prioritize

### P0: Recover and package existing evidence first

This can proceed without new GPU runs. Create one manifest per proposed result containing run ID, source and compiled-extension identities, checkpoint/tokenizer, actual sampling parameters, tree shape, cache mode, realized batching, instrumentation, metric denominator, and contamination status. Link each row to raw evidence and mark older rows superseded where appropriate.

Recompute uncertainty from comparable archived runs, using requests/tasks/independent boots as the sampling units. Do not bootstrap dependent tokens as independent observations or pool changing implementations. Logits that were never captured cannot be recovered by statistical reanalysis.

Reuse the existing [multidraft sampler tests](../../../tests/test_fr10_tree_rejection_sampler.py), [attention-KV tests](../../../tests/test_fr13_attn_kv_remap.py), [convolution-path tests](../../../tests/test_fr13_conv_committed_path.py), and fixed32 commitment tests. The sampler suite already includes analytic tiny-vocabulary checks, multistep checks, and a biased-selector negative control. Package these as a small public regression artifact rather than writing another equivalent reference suite. Verify a fresh checkout can build the required native extensions; this review did not execute that build or the tests.

### E1: One matched comparison of the final stack — highest performance value

**Question:** After the banked optimizations, does the selected tree beat a strong chain under the same serving conditions, and where does any difference originate?

- Freeze one checkpoint, quantization, effective sampler, and software stack. I would use the original FP8 lineage for the core same-paper revision; include NVFP4 only as a separately labeled extension unless we explicitly choose to move the whole evaluation.
- Compare native MTP-5, the depth-matched chain, and the selected tree at B1 and actual B4. MTP-11 is already a historical control for tail6. An autoregressive baseline is useful context but cannot replace a strong speculative chain.
- Use fixed-prefix/context/draft replays for operator costs, a fixed-arrival request trace for cache/serving behavior, and separate live agent runs for task outcomes. These answer different questions. Include short and long contexts and controlled cold/warm cache conditions without multiplying every exploratory dimension into one huge sweep.
- Use balanced paired run order and independent boots. Estimate variance in a pilot, then choose repetition counts and a practically meaningful interval width before inspecting the final comparison. A single best run is insufficient.
- Report physical-step and per-request-event timing; draft/verify/commit/host breakdown; committed tokens; actual batch occupancy; per-request TPOT/TTFT; total output over union wall time; and cache capacity/hits/prefill work. Keep profiler runs separate from timing runs.

SGLang comparison work already exists. The [August calibration](../../../results/fr14_nvfp4_port_20260816/ablation_a_step2.md) is partial and uses different model/KV configurations, so it cannot establish engine superiority. There are also four later native MTP-5 task probes; they are not a full matched performance sweep. Finish a fair control where feasible. Include Bole/TreeWY implementations if available and runnable under sufficiently matched conditions; otherwise disclose the gap and avoid competitive superiority claims. Porting another entire engine is not a prerequisite for a scoped artifact paper.

**Decision:** A repeatable win supports a current acceleration claim. A repeatable loss still supports the state-integrity and performance-analysis paper. It should not trigger an indefinite search for a favorable task or tree shape.

### E2: Check composition of the current correctness path

**Question:** Do the existing fixes remain correct when the current sampler, kernels, batching, and cache lifecycle operate together?

First map existing coverage, then run only missing combinations: sibling acceptance and rejection, deep accepted paths, zero/full draft acceptance, next-token continuation, cache hit/eviction/page reuse, B1/B4, and the actual graph route. Compare all three state surfaces and next-step outputs with an explicitly chosen native reference under fixed prefixes. Distinguish byte identity, bounded numerical differences, and target-distribution checks.

Trace the analytic sampler fixtures into the deployed GPU implementation. If the paper retains a strong stochastic-equivalence claim, add controlled conditional-distribution captures and a prespecified statistical tolerance, accounting for request dependence. The approximately 13% historical native rescore flip floor, zero observed garble, and a matching task count do not prove distribution preservation.

**Decision:** The publication claim must match the strongest completed gate. If distribution evidence remains incomplete, state this and retain the narrower implementation-regression claim.

### E3: Small optional experiments for a stronger positive result

Finish the paired deployment check for the already-built B4 single-pass scan and measure the batched tree-accept walk. Then measure the **composed** stack; do not add their individual deltas to the head-pairing result.

For an NVFP4 extension, repeat the promising split-K result, compare against matched native MTP-5, and measure split-K plus the other enabled optimizations together. The reported approximately 18.34 ms full-step improvement is from one paired B1 observation with different trajectories; it is not yet a stable general speedup. B4 served evidence and a calibrated model-quality reference remain missing for that extension.

If claiming task-quality parity, use a held-out task mix selected before results are seen, with controlled network access and a justified non-inferiority margin. Repeating the same 16 tasks alone is unlikely to settle it. A second hardware platform, another architecture, a trained drafter, or a different state-reconstruction algorithm would support additional claims, but none is required just to revise this preprint honestly.

## Proposed manuscript structure

1. **Problem and contract:** the minimal wrong-history example, then the complete state/sampler/cache boundary.
2. **Implementation:** branch-local verification, accepted-path commitment, and physical spine layout, with a precise reference implementation.
3. **Correctness evidence:** small reproducible witnesses, fixes, composition coverage, and explicit numerical/statistical limits.
4. **Performance model:** committed tokens divided by complete event-normalized cost, plus separate cache and service-level effects.
5. **Evaluation:** historical B1 and B4 in distinct blocks, the final matched comparison if completed, one reliable optimization, and a compact table of failed hypotheses.
6. **Related work and limitations:** direct Bole/TreeWY comparisons, scope of replay, task/precision/hardware limits, and reproducibility.

Use roughly six principal visuals: the state contract; the masked-slot numerical witness; acceptance before/after spine repair; the three-arm full-cost decomposition; a controlled cache/serving comparison if measured; and the paired optimization result. Put the chronological investigation, unused tree shapes, withdrawn measurements, and optional NVFP4 exploration in the appendix/archive.

**Practical stopping point:** complete the evidence manifest and claim corrections first. That yields a defensible archival v2 from work already done. Add E1 and E2 to support claims about the current implementation; run E3 only if we want its additional performance claim. No GPU experiment or submitted-paper edit was performed as part of this proposal.
