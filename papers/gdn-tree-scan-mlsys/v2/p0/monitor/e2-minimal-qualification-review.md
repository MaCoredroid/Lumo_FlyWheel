## A concrete current KV wiring gap

The r16 `none` boot at `experiments/out-20260922T071945Z-e7b-r16-p072-commit-batch/e7b_001_p072_arm1_none-B_fs_ieee-all/` records no `FR13_ATTN_KV_REMAP` or `FR13_SLOT_REORDER` in `docker_inspect.json`; its `docker_logs.txt` has no KV-remap engagement. `experiments/e7a/e7a_capture_launch.v3.sh` also has no pass-through for these flags. In the emitted runner, `vllm/v1/worker/gpu_model_runner.py:7027` enables the plain remap only when `FR13_ATTN_KV_REMAP` is `1`, defaulting to `0` (same gate in patcher line 41750). The relevant helper explicitly documents that noncontiguous accepted cat10 nodes must be copied to committed linear slots before the next forward (`src/lumo_flywheel_serving/fr10_gdn_tree_kernel.py:9793–9810`).

Thus the available source/environment closure does not establish an active KV repair for this fresh route; it points to the default-off path. Verify the actual worker path and explicitly freeze/forward the intended remap setting before whole-model qualification. Slot reorder is optional for the proposed eager configuration: leave it off and qualify flat-layout remap if that is the selected route. Turning remap on changes the serving configuration relative to the current layer-62 diagnostic boot, so a small subsequent state/next-forward check must use the resulting configuration. This finding does not invalidate the local arithmetic comparisons on previously captured operands.
