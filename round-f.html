Where Tree Speculative Decoding Breaks: the Gated-DeltaNet Wall

Abstract

The Round-4b mini paper (Vol. I) recommended shipping speculative-decoding config D on Qwen 3.5. This volume reports what happened next on Qwen 3.6-27B-FP8. Four threads — config/quantization tuning, a SWE-Bench baseline campaign, tree-shaped speculative decoding (Round F), and the FR7→FR9 multispine line — converge on one architectural fact: Qwen 3.6 is a hybrid in which 48 of 64 layers are Gated-DeltaNet (linear, recurrent). A speculative tree can only be made lossless on the 16 softmax-attention layers; the 48 recurrent layers process the flattened tree in order and corrupt every depth-≥2 candidate. The net result, after 24+ kernel commits: linear MTP (E3) remains the fastest lossless arm, the paper's config-D win does not transfer, FP8-KV cache regresses 8–10%, and the most recent work is a correctness reckoning — the multispine "winner" selector turns out not to be distribution-preserving. The honest deliverable is a clean architectural diagnosis and a stack that is faster and provably correct, not a hero number.

Read me first · a plain-language key

The cast of characters — in human words

A large language model writes one word at a time, which is slow. Speculative decoding bolts on a fast "drafter" that guesses several words ahead; the big model then checks the whole guess in a single pass. Correct guesses are kept for free — same exact output, less waiting. Everything below is a different strategy for guessing, and this whole paper is about which strategy actually pays off on one specific model. You don't need the jargon to follow the story; this key is here whenever a letter stops making sense.

MTP · multi-token prediction
The model's built-in drafter — a small head that ships with the model and guesses the next few words in one shot. The "native" way to speculate.
Config A & D
Two guessing recipes from Vol. I. A = one trick (reuse text the agent has already seen). D = A plus three more drafting tricks stacked on top. Vol. I shipped D; this volume shows A alone is enough.
E · (E3, E5)
Use the native MTP drafter to guess a straight line of N words ahead. E3 = guess 3 ahead, E5 = guess 5 ahead. This is the baseline everything tries to beat.
F_a & F_b
The experiments that guess a branching tree of possibilities instead of a straight line. F_a packs the whole tree into one pass; F_b runs each branch separately. Both guess wider — both lose on this model.
Spine
One straight branch of a tree — a single guess from start to finish. Multispine = run two spines at once and keep whichever guessed better.
Gated-DeltaNet (GDN)
The "recurrent" layer type that makes up 75% of this model. It reads words strictly in order and remembers as it goes — which is exactly why a branching tree confuses it. The wall this paper runs into.
§1 — Why this volume exists

The headline that didn't hold

Vol. I closed on a clean recommendation: across a 220-cell ablation on Qwen 3.5-27B, the full four-technique stack (config D) was the one to ship. The single most persuasive cell was a benchmark task — sqlalchemy-2-session-modernization — where D resolved 4/4 attempts while the leaner config A did not. That one effect carried the "ship D" conclusion.

Re-running the same OFF/A/D ablation on Qwen 3.6 at temperature 0.6 was supposed to be confirmation. Instead the load-bearing effect evaporated: Q3.6-D scored 0/4 on the very task that justified the recommendation, while configs A and D tied on every aggregate metric. The paper's headline was an artifact of one non-transferring result on one model.

Vol. I concluded
Ship config D — the full T1+T2+T3+T4 stack; the sqlalchemy 4/4 effect proves the deeper techniques earn their keep.
→
Vol. II concludes
Ship config A — T1 (cross-turn SuffixDecoding) alone. On Q3.6 it is +23% faster than Q3.5-A, ties D on everything, and the 4/4 effect does not replicate.

That reversal set the tone for everything after: trust nothing that hasn't replicated on the production model, and chase a faster decoder only where it can be proven lossless. The rest of this volume is four threads pulling that string until it hits an architectural wall.

§2 — Thread I

Knobs that did nothing, a cache that hurt, and a reversal

A vs D, quickly: two speculation recipes. A = one trick (reuse seen text). D = A + three more drafting tricks. Vol. I shipped D; here A ties it and is simpler.The first thread asked whether any cheap serving knob could tame Qwen 3.6's habit of writing to the full token budget. Three were tested — model_reasoning_effort, preserve_thinking, and sampling temperature. All three are inert: reasoning_effort is silently dropped on the non-Harmony path, preserve_thinking was already on via the custom chat template, and temperature moved no metric outside sampling noise. Verbosity is intrinsic to the model. That is itself a finding — there is no free serving-side lever here.

The Q3.5-D pass count of 14/44 — the headline of Vol. I — was almost entirely the sqlalchemy 4/4 effect. On Q3.6, D drops to 9/44 and A edges it at 10/44. The deeper drafting techniques (T2/T3/T4) contribute nothing measurable on this model; they add complexity, drafter-slot contention, and variance for no throughput.

FP8-KV cache: realized at last, and it regresses

Every historical "FP8-KV" run had been silently downgraded — the launcher rewrote fp8_e5m2 to auto, so the cache was BF16 all along. A new --kv-cache-dtype fp8_e4m3 override finally realized a true FP8 KV cache. The result was not the expected throughput bump:

Figure 2 · same-duration windowsFP8-KV crosses into regression after the first hour
Decode tps over equal wall-time windows from run start. FP8-KV starts +1.5% but falls to −8.4% @ 1h and −9.6% @ ~67min — driven by a +60% prefill cost (the head_dim=256 FP8 prefill caveat), not by acceptance or idle time. It fails the +5% gate. Verdict: do not promote.
Methodological honesty The published "0.548 accept / 22.46 tps" for Q3.6-A is warm-biased: the proxy derives session_id from first-user-text, so all four --repeat attempts of a task share one suffix-tree partition and acceptance climbs monotonically. Cold-only is ≈0.46 accept; cold-only at temp=1.0 lands near 0.32 accept / 16–17 tps. The headline numbers are real but upward-biased, and the reports say so out loud.
§3 — Thread II

A defensible SWE-Bench number — and the aarch64 wall

To gate the spec-decode work against real quality, the second thread ran Qwen 3.6 (driven by Codex CLI) on SWE-Bench Verified under a pre-registered, bounded-time protocol. Tier 0 (a 20-instance smoke screen) passed cleanly: 10/20 resolved (50%) against a ≥4/20 gate. The published anchors for context: Qwen's own scaffold reports 77.2 Verified; Claude 4.5 Opus, 80.9. The campaign reports its number honestly as "Q3.6 on the Codex loop," which a different agent harness can swing 5–15 points.

Key finding · the carve-out is Python-version-driven SWE-Bench rebuilds each instance's original conda environment. Old instances pin Python ≤3.6 and deps (cdms2, ancient scipy) that conda-forge never built for linux-aarch64. On the GB10's ARM cores, an estimated 20–35% of the benchmark simply cannot build — and it fails by Python version, not by repository.

The fix was an x86 eval-offload over SSH: the Codex agent step stays on the DGX (it needs the Q3.6 vLLM server), while the evaluation step ships its patch to a native x86 box and returns a verdict. The contamination question — does the architecture change the grade? — was answered decisively: 17/17 buildable instances agree between arm64 and x86, zero flips. The six arm64 crashes recovered to real verdicts on x86.

Figure 3 · 273 GB/s memory boundBatching helps sub-linearly
Aggregate decode speedup vs concurrency on the GB10's 273 GB/s unified memory. ≈2.6× at B=4, ≈3.5× at B=8, asymptotic ceiling ~5.4×. Per-stream tps degrades past B≈3–4, which can cost agentic fix-revise iterations. The earlier "B=4 → 4×" claim was audited as false. This bandwidth ceiling is exactly what motivated the tree spec-decode line in Thread III.

The thread then pivoted — rather than burn weeks finishing a full 500+731 headline, it became the substrate for config comparison. A fixed 16-instance subset at batch-4 ranked the MTP depths, and E3 (native MTP head, depth 3) emerged as the leader on combined resolved-rate and decode tps. E3 is the baseline every subsequent tree variant had to beat.

§4 — Thread III · the central result

Tree speculative decoding meets Gated-DeltaNet

The depth sweep had plateaued (E3 > E6), so the obvious next lever was width: instead of one linear draft chain, draw many candidates from the MTP head's top-k, arrange them as a branching tree, and verify them in one pass. A verified tree is mathematically guaranteed to raise accepted tokens per step. It did not raise throughput. Understanding why took the whole thread — and the answer is in the model's architecture.

The wall · Qwen 3.6-27B layer composition
48 of 64 layers are recurrent. A tree mask only fixes 16.
Gated-DeltaNet · linear / recurrent · 48 (75%) Softmax attention · 16 (25%)

MTP & E: MTP is the model's built-in drafter. E3/E5 use it to guess a straight line of 3 or 5 words ahead — the baseline the tree experiments must beat.A tree-attention mask corrects the 16 softmax layers. But the 48 Gated-DeltaNet layers carry a recurrent state: they process the breadth-first-flattened tree in order, so sibling branches contaminate one another's hidden state. Every candidate at depth ≥2 is verified against a corrupted state. As the report puts it: "a packed tree cannot be made lossless by attention masks alone."

Figure 4 · the smoking gunDepth-2 acceptance collapses under the tree
Per-depth accept rate. At depth 1 the packed tree (F_a) matches linear E3 exactly (89.1% vs 88.9%) — the drafts are provably correct. At depth 2 the tree collapses to 8.2% while E3 holds 74.5%. The drafts are right; the recurrent verifier rejects them.

F_a vs F_b: two ways to guess a tree. F_a packs every branch into one pass; F_b runs each branch as its own row. Both try to guess wider than a straight line — both lose here.The batched-paths variant (F_b) fares no better: submitting even a path that is an exact duplicate of the top-1 chain collapses its acceptance from 2.667 to 0.286 — proof that the mere presence of a second speculative row in the GDN forward destroys the top-1 invariant. And block-aligned pointer-swaps (the zero-copy commit trick) almost never fire, because vLLM's 816-token block dwarfs the ~5-token accepted suffix.

A parallel literature survey (the K≥2-vs-K=1 question) grounded the result: a wider tree always wins on accepted tokens, but only wins on throughput while the verify pass is memory-bandwidth-bound. At agentic batch on this stack it is not — so the literature's own prediction is parity-or-regression, exactly as observed. The matching SOTA reference, STree (NeurIPS 2025), confirms that lossless tree decoding on SSM hybrids needs a bespoke tree-aware recurrent scan kernel that does not exist in this vLLM line.

§5 — Thread IV · the live frontier

FR7 → FR9: a correct superset that isn't (yet) a win

Spine: one straight branch — a single guess from start to finish. Multispine runs two at once and keeps whichever guessed more, so it can never do worse than one. In theory.If a packed tree corrupts the shared recurrent state, give each draft chain — each "spine" — its own independent vLLM sequence with its own native GDN state. That is the FR7→FR9 arc: FR7 proved the shared-state ceiling (free-running path-0 collapses to 1.66/event vs E5's 3.15), FR8 red-teamed the broken condense path into failing closed, and FR9 (independent rows) is the design that actually runs.

And on a micro-probe, it works: spine-0 stays byte-identical to E5, the 2-spine "winner" reaches 3.442 accept/event with zero superset violations and a +6.85% tok/s edge. Correctness is settled — it survives 19,307 winner events under temperature-0.6 rejection sampling with no engine death. But scale tells a different story:

Figure 6 · the win that doesn't scale+7% on the bench, −21% in the field
A second spine wins by +6.85% on the low-batch micro-probe but loses the speed gate at agentic B=4 (0.79× and 0.74× of the spine-1 baseline). The extra row nearly doubles draft tokens/step (17.6 → 34.1) for only ~16% more public tokens — verifier cost eats the accept gain.

The current blocker is correctness, not speed The HEAD commit (c22a0859, June 2) is a reckoning: the 2-spine public-commit logic does argmax(accept_counts) over two independently-sampled target trajectories and publishes whichever accepted more. That is a best-of-spines selector — not distribution-preserving speculative sampling. It is why the spine-2 quality dropped to 4/16: the flips were distribution-shift divergences, not infra crashes. The spec now collapses every policy to one launchable mode, LUMO_IR_PUBLIC_COMMIT_POLICY=lossless (commit spine-0 only), and fails closed on anything else until a true distribution-safe multi-draft selector passes five verification gates.
§6 — Synthesis

The verdict ledger

Two weeks, 24+ kernel commits, and one durable engineering conclusion: linear MTP at depth 3 is the lossless speed leader on this stack, and every alternative is correct-but-slower or fast-but-lossy. The value is the map of dead ends — each one is a load-bearing negative result, not a failure.

The one-line state of the art on this stack: the multispine superset is correct and stable but not yet a net speed win, and the immediate next action is to make its public stream provably lossless before any further tuning is trusted. The architectural diagnosis — a 75%-recurrent hybrid needs a tree-scan kernel that does not exist — is the result that will outlast every number on this page.

§7 — For the reader

What you're looking at

If you hire ML-systems engineers

This is two weeks of inference-stack work that produced no hero number on purpose. The skill on display is the discipline to refute your own published headline when the production model disagrees, to localize a throughput regression to a specific architectural cause (48 recurrent layers, not a tuning miss), and to fail closed on a tempting-but-lossy optimization rather than ship a distribution shift. The deliverable is a stack that is faster and provably correct, plus a clean map of which optimizations are dead on this architecture and why.

If you work in this space

The transferable result: on Gated-DeltaNet / SSM-hybrid models, attention-mask-based tree speculative decoding is not losslessly viable — the recurrent majority corrupts depth-≥2 verification, and pointer-swap commits don't fire at realistic block sizes. Independent-row multispine is the correctness-clean route, but the win is bandwidth-gated and the public-commit selector must be distribution-preserving (a naive longest-accepted selector is not). Anyone porting Medusa/Sequoia/EAGLE-style trees to a hybrid will hit the same wall; the kernel-level fix is STree-shaped and currently bespoke.

§8 — Receipts

The paper trail, at altitude

None of the above is a tidy retrofit. Every finding is the residue of roughly 50 reports — design specs and pre-registrations written before a result was known, and closeouts and post-mortems written after. Rather than enumerate them, here is the shape of that trail at a high level, thread by thread.

Thread I Config & quantization

A knob-screening experiment and a 132-cell ablation closeout bookended a specification for realizing a true FP8 KV cache and the regression analysis that explained why it backfired. The collective verdict: no serving knob moves this model, and FP8-KV trades decode throughput for prefill cost at a net loss.

Thread II SWE-Bench campaign

A pre-registration fixed the tiers, gates, and instance lists before any data was read; a bounded-time protocol defined what "done" meant; a bandwidth analysis explained why concurrency saturates well short of linear; and a config-comparison spec set up the D-vs-E race that crowned E3. The discipline was refusing to move the goalposts after seeing the numbers.

Thread III Round F · tree speculative decoding

Design-status notes forked the work into packed-tree (F_a) and batched-path (F_b) routes; a rejection-sampler post-mortem found vLLM's tree path half-built; a unified propose-and-verify spec tried to salvage it; a cost-gate closeout killed it on memory traffic; and a literature survey confirmed the theory predicted exactly the parity-or-regression that was measured. This is the thread that diagnosed the wall.

Thread IV FR7 → FR9 · multispine

A pointer-swap closeout showed the zero-copy commit was correct but inert; a superset closeout proved the two-spine mechanism while the agentic route dead-ended; a token-tree ceiling note and a red-team hardened the path and named the STree-shaped fix; and the final spec turned a tempting speed win into a correctness reckoning. Specs going in, post-mortems coming out — every dead end documented.

The throughline is method over outcome: pre-register the gates, freeze the benchmark, red-team your own win, and write the dead ends down as carefully as the wins. The reports live in the repository for anyone who wants the depth behind these summaries.
